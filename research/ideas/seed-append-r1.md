# Seed 的追加优势：接近固实的压缩率，追加时免于重新搜索（r1 计划）

状态：**计划，尚未实现、尚未运行**。日期：2026-11-15。任务：DEV-017。前序：[seed-g5-r1](seed-g5-r1.md)（Seed 在小空间里没有搜索优势，H2 不成立）、[shared-dictionary-r1](shared-dictionary-r1.md)（固实压缩列为后续）。

## 1. 用户的定位（2026-11-15，原话要点）

> seed 方案就是可以减少追加文件的重复搜索时间，而分组压缩本质就是为了更小的压缩率，固实压缩用于最小的压缩率（一般情况下），seed 方案就可以在压缩率接近固实压缩的基础上，加快追加压缩文件的速度。

此前用户还指出：Seed 的优势区间在大文件、无法完全遍历的场景，小文件没有优势；另一个优势是可复现性。

用户进一步说明（2026-11-15）：

> 可复现性包含两方面，一方面是同一份文件再次压缩（其实也就是我刚才说的追加文件），另一方面是解压，因为如果没有 seed，解压会变得比较困难。

### 1.1 两种可复现性的落地方式

- **再次压缩 / 追加（编码端）**：同一个工具版本、同一个 Seed、同样的输入，得到逐字节相同的产物，不需要重新搜索；追加时，新文件按 Seed 的规则直接确定位置和参数。这对应第 5 节的 H-append 和 H-generalize。
- **解压（解码端）**：Seed 是**解码计划的紧凑描述**。解码端用版本化的、确定性的规则，从 Seed 加上索引里的路径和大小，就能算出每个文件属于哪个组、用哪个字典，不必为每个文件显式存一张表。G5 的容器 v2 已经实现了“从 Seed 重算分组，并与组表核对”。
- **必须守住的边界**（AGENTS.md 第 6 节）：解码所需的信息必须能从归档里读到，或者从归档里的元数据确定性地重建。所以说“没有 Seed 解压会变得困难”，准确的意思是：Seed 就是这部分解码元数据，它**必须存进归档**；不用 Seed 的方案，则必须把等价的显式表存进去。Seed 不是密钥，不能从 Seed 恢复文件内容。不能出现“归档里只有数据，Seed 由外部提供才能解压”的设计。
- **代价与风险**：
  - 解码端要重新执行分组规则，这需要计时；
  - 规则的实现一旦改变，旧 Seed 必须仍能按旧修订解释，所以解释器要带修订号，不能静默改变语义；
  - Seed 和显式表要么二选一存储，要么同时存储用作校验，两者的元数据大小都要计入。

### 1.2 新增假设（与第 5 节一起在 dev 上确定门槛后冻结）

- **H-meta**：用 Seed 加组键映射代替逐文件组表，元数据至少减少 X %（文件越多越明显），而解码端重算分组的额外时间不超过 Y 毫秒，或不超过解压时间的 Y %。
- **H-decode-repro**：同一个 Seed 和归档，在两个平台（Windows / Linux）、两种编译器上重算出的分组完全相同，跨平台确定性已经有测试。

## 2. 要回答的问题

不是“Seed 能不能搜得更好”（G5 已回答：在小空间里不能），而是：

- **Q-A（追加）**：已有压缩包追加新文件时，基于 Seed 规则的追加，能否在**接近固实的压缩率**下，比固实追加和全量重建快得多？
- **Q-G（推广）**：Seed 产出的是一条**规则**，能把没见过的新文件放进合适的组；直接搜索产出的是一张**逐文件分配表**，新文件没有现成的位置。这种推广能力是否带来可测的收益？

## 3. 对照组（暂定）

| 组 | 首次压缩 | 追加一个或一批新文件 |
| --- | --- | --- |
| R 全量重建 | 任意方法 | 对旧文件和新文件一起重新压缩（压缩率最好的参照之一，最慢） |
| S 固实 | 每组一个连续流 | 二选一，都要测：重新压缩整组的流（压缩率保持，代价大）；或者追加一个新的固实段（快，但压缩率下降） |
| D 直接搜索 + 分配表 | G5-coord 的结果 | 新文件没有规则可依：(a) 为新文件单独重新搜索；(b) 用最近似的组（启发式） |
| Seed | G5-seed 的结果 | Seed 规则直接决定新文件属于哪个组；用该组已有的字典编码，旧数据块原样保留；可选：以旧 Seed 为起点，做小预算的热启动再优化 |
| LZMA2-6 | 生产 CLI | 全量重建 |

## 4. 指标

- **压缩率**：每次追加后的完整大小，以及与固实（整组重压）的差距百分比；连续追加 N 次后的漂移（字典逐渐过时）。
- **追加耗时**：只计追加操作本身（读入、编码、写出、索引），与全量重建、固实整组重压比较；同时记 CPU 时间和墙钟时间。
- **单文件解压延迟与峰值内存**：固实会牺牲随机访问，这是分组和 Seed 方案的对价。
- **正确性**：每次追加后逐字节往返；“按历史可复现”是否成立，即同一个旧包、同一个新文件、同一个工具版本，得到的新包逐字节相同。

## 5. 可证伪的假设（数值门槛在 dev 上确定后、看留出集之前冻结）

- **H-ratio**：Seed 方案首次压缩的大小，与固实（同分组、整组一个流）的差距不超过 X %。
- **H-append**：单次追加的耗时不超过固实整组重压的 Y %，也不超过全量重建的 Y %；而追加后的大小，与“全量重建得到的 Seed 包”的差距不超过 Z %。
- **H-drift**：连续追加 N 次后，Seed 方案相对全量重建的大小漂移不超过 W %；超过时，热启动再优化能把差距收回到 Z % 以内，且耗时远小于从头搜索。
- **H-generalize**：在追加的新文件上，“Seed 规则分配”的大小不劣于“D(b) 最近似组启发式”，并且不需要 D(a) 的重新搜索时间。
- **H0**：所有产物逐字节往返；“按历史可复现”成立。

## 6. 必须先解决的设计问题

1. **分组规则必须对插入保持稳定**。G5 的规则是“按总字节数排名，前 k−1 名各自成组”，加一个大文件就可能改变排名，从 Seed 重算出来的分组会和已存的组表对不上，G5 容器 v2 的“Seed 与组表一致”校验也会失败。r1 的候选做法：把“组键到组号”的映射存进包里，新的键按 Seed 规则落进固定的组或“其他”组，不再每次重新排名。
2. **两种“可复现”分开承诺**：“按历史可复现”可以做到；“追加结果等价于全量重建”一般做不到，因为字典是按当时的文件训练的。格式契约里必须写明承诺的是哪一种。
3. **追加的安全性**：按项目底线，不就地修改旧包；写出新文件（旧数据块原样流式拷贝，不重新压缩），再原子发布；中途失败时旧包保持不变。
4. **对生产格式的影响**：如果字典或固实要进生产，“支持增量追加”应写进那份 ADR 的需求，避免格式定型后返工。

## 7.1 语料设计：append-r1（2026-11-15，构建前确定）

四个池，每个池都按整组划分成 dev 和 holdout，内容 SHA256 不相交；每个划分再切成“初始集”加 3 批追加。

| 池 | 来源 | 分组单位 | 每个划分的上限 |
| --- | --- | --- | --- |
| linux-src（公开） | Linux 6.12 源码 | 前两级目录（如 `drivers/net`） | 48 MiB |
| native-bin（本机） | MSVC `lib/x64` 的 `.lib`；MSYS2 UCRT64 `bin` 的 `.dll` / `.exe` 和 `lib` 的 `.a`；每个文件 64 KiB – 32 MiB | 文件名中第一个 `-` / `_` / `.` / 数字之前的前缀（近似软件包） | 64 MiB |
| silesia（公开） | Silesia 的 12 个文件 | 每个文件一组 | 无（约一半进 dev，一半进 holdout） |
| wiki-text（公开） | enwik8 按顺序切成 100 段，每段 1,000,000 字节 | 段 | 前 50 段为 dev，后 50 段为 holdout |

- **路径**：每条路径都用 `seedarc_path_check` 检查（ADR-0005）；每个划分的完整清单还要用 `--manifest` 模式过一遍生产的大小写冲突检查。Python 先用 `casefold()` 把可能冲突的一对都排除，这比简单大小写折叠更严，宁可多排除，被排除的逐个列出。
- **追加顺序**：wiki-text 按段的自然顺序（模拟日志按时间追加）；其他池按 `sha256("append-r1:<路径>")` 排序。按字节累计：前 70 % 是初始集，其后三个 10 % 各成一批。
- **enwik8 切段是人为构造**，用来模拟“新数据不断追加”的场景，记录里会注明。
- 原始文件和切出来的段只放在被忽略的 `research/local/append-r1/` 下，仓库里只存清单。

## 7.2 研究容器 v3 与工具设计（2026-11-15，实现前确定）

- **新工具 `research/tools/append_study.cpp`**。`g5_study` 随冻结配置 g5-r1 定型，**不再修改**，以保证 G5 的结果可复现。新工具复用 `study_common.hpp`，计划的字段（规则、k、每组 D / T）与 G5 相同。
- **对插入稳定的分组**：首次压缩时，按字节数排名，前 k−1 个组键各自成组；把这 k−1 个“组键到组号”的映射写进包里的**组键表**；其余的键，以及以后追加时出现的新键，都落到最后一个“其他”组。追加时不重新排名，旧文件的分组永远不变。
- **两种元数据模式**（用来检验 H-meta）：
  - **显式**：每个文件 1 字节组号，加组表；
  - **Seed**：只存 4 字节 Seed 加组键表，解码端按规则从路径和大小重算每个文件的组。

  两种模式下，数据与字典完全相同，只有元数据不同。
- **追加操作** `append OLD NEW_DIR OUT`：旧字典和旧数据块按字节原样拷贝，不重新压缩；新文件用所属组的现有字典编码；重写组号表 / 组键表和索引；写成新文件（目标已存在就拒绝），再在内存里把全部文件逐字节核对。新文件归哪一组：
  - Seed 模式：用 Seed 的规则加组键表决定；
  - 显式模式的 **D(b)**：不用规则，按启发式归入“已有文件里与它路径公共前缀最长的那个文件所在的组”。
- **固实对照**：每组的文件按顺序拼接成一个 Zstd-9 帧，窗口取 `min(27, ⌈log₂ 组字节数⌉)`，并记录每个文件在流中的偏移。追加有两种：
  - 整组重压：压缩率保持，代价是整组；
  - 追加新的固实段：快，但不能利用旧段的内容。

  单文件解压必须从帧头开始解码，延迟会单独测量。Zstd 的参数化帧编码只在 `core/codec/dictionary.cpp` 的研究适配器里调用（ADR-0003：zstd 头文件不出 codec 边界）。
- **全量重建参照**：在“初始集 + 已追加的各批”上，从头搜索再打包。

### 7.3 Seed 放在哪里（用户 2026-11-15 决定）

- **明文放在文件尾部的索引区**，带修订号、长度（有上限）和值，由尾部的 CRC32C 一起保护。头部只放格式版本和“含 Seed”的标志。
- **追加只追加**：新包 = 旧包的全部字节 + 新数据 + 新尾部。旧包是新包的逐字节前缀，旧尾部作废但留在原处（它的字节也计入大小）。新尾部带上历次的 Seed 记录（第几代、Seed、覆盖到第几个文件），支撑“按历史可复现”。
- 计划的来源：在初始集上用冻结的 `g5_study` 搜索得到计划（它的按字节排名分组，与 v3 首次压缩时的排名一致），再由 `append_study pack` 按该计划生成 v3 包。

### 7.3.1 实现（2026-11-15）

- **`research/tools/append_study.cpp`**（`seedarc_append_study`），研究容器 v3（`SADXR003`，结尾魔数 `SADXEND3`）：
  - 头部 32 字节（格式版本、块大小、等级、模式标志）；
  - 第 0 代的字典和数据，之后各代追加的数据；
  - 尾部：组表（字典偏移 / 大小 / CRC32C）、组键表、Seed 记录（修订号 1、长度 4、值）或逐文件组号、历代记录、带显式数据偏移的索引；固实模式另有帧表；
  - 24 字节结尾：尾部偏移、尾部大小、尾部 CRC32C、魔数。
- **命令**：`pack seed|explicit|solid PLAN 输入 输出`、`append 旧包 新文件目录 输出 [segment|regroup]`、`verify`、`peek`（冷启动单文件解压）、`selftest`。
- **追加**：
  - Seed 模式按规则加组键表定组；显式模式和固实模式按“路径公共前缀最长”的启发式；
  - 旧包始终是新包的逐字节前缀（solid 的 `regroup` 除外：它重写受影响的组，生成一个全新的包）；
  - 路径已存在就拒绝；目标已存在就拒绝。
- **固实编解码**：在研究适配器 `core/codec/dictionary.{hpp,cpp}` 中新增 `compress_solid` / `decompress_solid`：单个 zstd 帧，窗口不超过 2²⁷，内容大小写进帧头，拒绝多帧、尾随字节和用了字典的帧。`codec.dictionary_research` 加了相应的测试。
- **作废尾部**：追加后，旧尾部成为不再被读取的字节，校验不覆盖它。自检确认在那里翻转字节不影响解压；其他所有区域的损坏都必须被拒绝。
- **测试**：
  - `research.append_study`（`check_append.cmake`）：三种模式下打包都是确定性的；追加后旧包是前缀，有两代记录；单文件解压正确；拒绝重复追加、覆盖和非规范计划；校验时缺文件会报错；Seed 模式的元数据小于显式模式，而数据字节完全相同；`regroup` 生成全新的包。
  - `selftest` 在 r2 dev config 上：208 个损坏样本全部被拒，18 个作废尾部的翻转确认不影响解压。
- **构建**：MSVC Release、GCC UCRT64、Linux GCC Release、Linux Clang ASan+UBSan 都是 0 警告；Linux 两套配置都是 42/42，无 sanitizer 报告；Windows 主测试 39/39。
- **路径检查工具**：`seedarc_path_check --manifest` 会补上隐含的父目录，再调用生产的清单检查。

  - Seed 只有约 29 位，可以穷举；
  - Seed 只决定分组和字典分配，字典和压缩数据仍在包里，攻击者可以对每个块逐个试字典，绕过 Seed 恢复内容；
  - 所以“去掉 Seed”只是增加了麻烦，不是加密。而且 AGENTS.md 第 6 节写明“Seed 不是密钥”。
- **可行的方向**：由用户密码经 KDF（如 Argon2id）派生密钥，用认证加密（如 XChaCha20-Poly1305）加密整个索引和数据，Seed 在被加密的索引里。保护来自加密本身，而不是 Seed。这属于 C 级协议决定，要单独写 ADR，并做威胁模型和依赖审查。

### 7.5 尾部单点失效与容器 v4（用户 2026-11-15 提出并同意，实现前确定）

> 用户（从 WinRAR 学来）：seed 放在末尾就完全没有冗余，尾部一坏整个包就没用；顺序下载最后才到尾部。能不能只下载了前面一部分，也先解压前面一部分？

v3 的 Seed、组键表、字典位置和索引都只在尾部，这个顾虑成立。生产格式的索引也在尾部，有同样的问题（写字典 / 固实的生产 ADR 时一并处理）。v3 保持已提交的样子，作为对照；新做 **v4**，在跑 dev 实验之前定下来，因为它改变元数据开销，会影响 H-meta 等假设的数字。

**用户同意的范围**：先做第一、二层；第三层（恢复记录）以后单独立项，需要 C 级 ADR。

- **第一层：代头**。每一代的数据前面先写代头：魔数、代号、规则修订号、Seed 记录（修订号、长度、值）、组键表、本代的字典表（新字典直接跟在代头后面；也可以引用更早一代的字典），代头自带 CRC32C。只追加，旧包仍是新包的逐字节前缀。
- **第二层：本地头**。每个文件的数据前面写本地头：魔数、代号、路径、大小、组号、各块的存储大小 / 类型 / CRC32C，头本身带 CRC32C。没有尾部时，从前往后扫，每个完整到达的文件都能解出并核对；遇到损坏，跳到下一个魔数继续。只靠扫描解出的路径同样要过 ADR-0005 的路径检查和整份清单的大小写冲突检查。
- **尾部**仍保留完整索引和每代 Seed 的副本，用来快速随机访问；与代头、本地头不一致时报错（fail closed），不挑一个“看起来对”的。
- **固实模式**：一组一个帧，截断后只能流式解出帧的前一部分；文件边界表放在帧前面（打包时在内存里已知），每个文件解完即用文件 CRC 核对。它在截断场景下天生吃亏，这也是要比的一点。
- **研究工具的简化**：本地头要先知道各块的存储大小，研究工具在内存里先压完一个文件再写头。生产格式不能整文件缓存，届时改为按块的本地头，写进那份 ADR。

#### 7.5.1 代就是一个队列：每一代可以有自己的 Seed（用户 2026-11-15 提出）

> 用户：按照第一层的做法，这其实就是一个队列，追加部分的 seed 可以和原本的不一样，也可以把追加的和原本的一起，根据原本的 seed 来搜索一个更优的压缩 seed。

代头让每一代自带 Seed，于是包就是一串 `(Seed_i, 组键表_i, 字典_i, 文件_i)`。**一代的 Seed 只管这一代的文件**，解码时绝不拿新 Seed 去重新解释旧文件（AGENTS.md 第 6 节：不能静默重解释）。字典只能引用本代或更早的代，不能向后引用，否则前缀解压就做不到。由此追加有三种做法，都要在 dev 上比较：

| 做法 | Seed 与字典 | 旧数据 | 搜索代价 | 前缀性质 |
| --- | --- | --- | --- | --- |
| **A 沿用** | 新代沿用上一代的 Seed 和字典（v3 的做法） | 不动 | 无 | 保持 |
| **B 新代新 Seed** | 只在新文件上搜索，从上一代 Seed 热启动；每组可选沿用旧字典或训练新字典 | 不动 | 只看新批次 | 保持 |
| **C 整体重搜（合并）** | 在旧文件 + 新文件上搜索，从上一代 Seed 热启动 | 结果变了就要重压旧数据，生成新包 | 全部数据，但热启动应能省预算 | 失去（和固实的整组重压一样） |

- **热启动**：以旧 Seed 为起点，只在它的邻域（改一个组的 D / T、改 k）里试，预算用完就停；旧 Seed 本身永远是候选，所以结果不会比 A 差（在评估器的口径下）。
- **新增假设**（门槛在 dev 上确定后冻结）：
  - **H-warm**：热启动用不超过冷启动 Y % 的预算，就能拿到冷启动 X % 以上的收益；
  - **H-queue**：B 相对 A 的体积收益，值得它多花的搜索时间；并报告批次越多、漂移越大时这个差距怎么变；
  - **H-partial**：在 x % 处截断，能恢复的文件字节比例接近 x %；v4 相对 v3 的额外开销不超过 Z %。
- **C 什么时候做**（何时合并重写）先不定规则，dev 上看漂移（H-drift）再决定，可能是“旧数据按新 Seed 估算能省超过某个比例才重写”。
- **诚实的预期**：G5 留出集上 Seed 搜索没有赢过简单基线（H1、H2 不成立）。所以 B、C 相对 A 能不能多省体积并不确定；热启动可以肯定的好处是少花搜索时间，体积收益要实测。

#### 7.5.2 小文件时的浪费：按大小推荐，用户可以自己选（用户 2026-11-15 提出）

> 用户：如果文件很小，v4 的做法就有些浪费了，所以要能识别文件大小，给出推荐，同时也要能让用户自主选择是否用 v4 这种策略。

- **开销在哪里**：代头每代只有一个，开销很小，**始终写**（Seed 和字典放在前面，本来就是前缀解压的前提）。贵的是第二层的本地头：每个文件多一份路径加约 20 字节，在几万个小文件（比如 Linux 源码）上可能占到压缩后体积的可观比例。
- **把第二层做成可选，分三档**，选哪一档写进头部标志，解码端据此知道能不能前向扫描：
  - **关**：只有代头和尾部索引。截断后只能拿到 Seed 和字典，文件要靠尾部；开销最小。
  - **检查点**：数据每满约 N 字节（候选 1 MiB，在 dev 上定）写一个小索引，列出上一个检查点以来的文件（路径、大小、组、块大小和 CRC），自带 CRC32C 和魔数。开销按数据量摊薄，与文件个数关系小；截断时最多损失最后一个检查点之后的内容。
  - **逐文件**：每个文件一个本地头，恢复粒度最细，开销随文件个数增长。
- **推荐规则**：打包前已知文件个数和大小，先估算各档的元数据开销，相对估算的压缩后体积给出比例，然后推荐：
  - 包本身很小（下载快、截断不常见），推荐“关”；
  - 文件平均很小而包很大，推荐“检查点”；
  - 文件平均很大，逐文件的开销可以忽略，推荐“逐文件”。

  具体门槛（多小算小、开销比例上限）**不拍脑袋**，在 dev 上按 H-partial 量出来的开销和恢复率确定，然后冻结。
- **用户自主选择**：工具显示每一档的估算开销和推荐档，用户可以用参数指定任一档覆盖推荐；不指定时用推荐档，并把实际用的档和“是推荐还是用户指定”写进记录。
- **H-partial 的比较对象**相应变成三档：每档在 x % 截断时的恢复率和额外开销，按池（小文件多的 linux-src、大文件的 silesia 等）分别报告。

#### 7.5.3 实现（2026-11-15）

- **新工具 `research/tools/append4_study.cpp`**（`seedarc_append4_study`），研究容器 v4（`SADXR004`，结尾魔数 `SADXEND4`）。v3 工具不改行为，作为“只有尾部”的对照；两者共用的计划、分组、字典训练和分块编码移到 `append_common.hpp`。移动后用旧二进制和新二进制对同一输入打包 / 追加，7 个 v3 包逐字节相同。
- **记录**：`标签(8) | 长度(4) | 内容 | CRC32C(4)`，内容的第一个字段是记录自己的偏移，所以记录只在它声称的位置上有效；数据里原样存着的别的 v4 包、作废的尾部，都不会被误认。四种记录：
  - **GEN（代头）**：代号、首个文件序号、Seed 记录、组键表、组表（字典偏移 / 大小 / CRC）。本代新字典紧跟其后；沿用的字典只能指向更早的位置，并且必须与更早某一代的组完全相同。
  - **FIL（逐文件）**：路径、大小、（显式模式下的）组号、各块的存储大小 / 类型 / CRC，块数据紧跟其后。Seed 模式不存组号，由本代 Seed 重算。
  - **CKP（检查点）**：覆盖范围的起点，以及这一段文件的清单（用 zstd 压缩）。数据每满 N 字节（参数，默认 1 MiB）或到一代末尾就写一个。
  - **FRM（固实帧）**：帧前的文件表。固实模式下“检查点”和“逐文件”两档相同，都是每帧一个 FRM。
- **头部**写冗余档和检查点大小；头部本身没有 CRC，它的 CRC32C 放在尾部里。尾部带每代 GEN 内容的原样副本、全部文件和显式偏移。完整读取时用前向扫描交叉核对：代头、本地头、检查点的位置（按头部的 N 重算）与尾部不一致就拒绝。
- **追加**：`append 旧包 新目录 输出 [--plan 计划]`。不给计划就是做法 A（沿用上一代的 Seed、组键表和字典）；给计划就是做法 B（新代用自己的 Seed，分组和字典只看新文件）。旧包仍是新包的前缀。固实的 `regroup` 生成只有一代的新包，**所有组都重压**（v3 只重压收到新文件的组），代价会偏高，比较时要注明。做法 C（热启动重搜）由运行脚本完成：搜索得到计划后重新 `pack`，格式上不需要额外支持。
- **恢复**：`partial 包 输入目录` 在 5 %、10 % … 95 %、少 1 字节、完整处截断，输出每处能恢复的文件数和字节数。来源有两个：前缀里最新的完整尾部（也可能是作废的旧尾部），以及所有有效的记录。每个文件都要过 CRC；同一路径两份内容不同就整体报错；恢复出的路径要过生产的清单检查（ADR-0005）。工具还会核对恢复出的每个文件都与输入逐字节相同。
- **推荐规则 rec-r0（临时值，未经测量）**：关档包小于 4 MiB 时推荐“关”；否则逐文件开销不超过 1 % 就推荐“逐文件”，检查点开销不超过 1 % 就推荐“检查点”，再不满足就推荐“关”。`pack` 的最后一个参数可以指定 `off / checkpoint / file`，覆盖推荐；不指定就用推荐档。输出写明三档的大小、实际用的档，以及是“推荐”还是“用户指定”。数据只编码一次，再按三档各排一次版。
- **研究适配器**：新增 `decompress_solid_prefix`，按流式解码截断的固实帧，返回解出的前导字节数，不会写出界；`codec.dictionary_research` 加了测试。
- **测试** `research.append4_study`（`check_append4.cmake`）覆盖：三种模式 × 三档 × 做法 A / B；打包是确定的；旧包是前缀；校验、单文件解压；截断恢复（有冗余时只缺结尾也能全部恢复；“关”档靠作废的旧尾部恢复第 0 代）；三档的数据字节相同、“关”最小；拒绝重复追加、覆盖、非规范计划、未知档位和过小的检查点；“自动”档在小树上选“关”。`selftest`：1242 个损坏样本全部被拒，48 个作废尾部的翻转不影响解压，252 次恢复检查。
- **构建**：MSVC Release、GCC UCRT64、Linux GCC Release、Linux Clang ASan+UBSan 都是 0 警告；Linux 两套 43/43，无 sanitizer 报告；Windows MSVC 42/42。MSVC ASan、CLion 检查尚未做。
- **冒烟观察**（`core/` + `tests/`，70 个文件，只用于确认工具能用，**不是实验结果**）：逐文件档比“关”多约 2.2 %，检查点（64 KiB）约 0.8 %；只缺结尾时两档都能恢复全部文件，“关”只能恢复第 0 代（62.7 % 字节）。另外，字典放在每代最前面，截断点落在字典之内时，这一代什么都解不出来，H-partial 的曲线要把这一点算进去。

### 7.6 分卷（用户 2026-11-15 提出，设计记录，未实现）

> 用户：然后还有就是分卷压缩支持，当然，我们的设计可以很轻易的分卷压缩。

**为什么容易**：v4 的每条记录都写着自己在“逻辑字节流”里的偏移，每一代又自带代头。分卷就是把这条逻辑流按固定大小切开，每卷前面加一个卷头，记录里的偏移照旧按逻辑流计算，不用改。

- **卷头**（每卷开头，自带 CRC32C）：魔数、格式版本、档案标识、卷号、本卷数据在逻辑流里的起点和长度、上一卷内容的 CRC32C（卷链，用来发现拿错了卷或卷的顺序不对）。
  - 档案标识要能区分不同的包，又要保持确定性（同样的输入得到同样的分卷）。候选：第 0 卷头部之后前若干字节的哈希。具体算法待定。
- **读取**：卷齐全时按卷号拼回逻辑流，与单文件完全一样。缺卷时，缺的那段当作空洞，扫描器照常跳过；其他卷里完整的文件照样恢复（记录只在自己声称的偏移上有效，跨过空洞也不会错位）。
- **追加**：新的一代**从新卷开始写**，已有的卷文件一个字节都不改；旧的最后一卷可以不满。这和“旧包是新包的前缀”是同一个性质，只是落到了文件层面：下载过旧卷的人只需再下载新卷。
- **要注意的依赖**（不是完全没有代价）：
  - **跨卷的文件**：一个文件的数据跨过卷边界时，两卷都在才能解出来。
  - **字典只在一代的开头**：一代跨多卷时，后面各卷里用字典编码的文件，都依赖这一代第一卷里的代头和字典；那一卷丢了，后面这一代的字典块全都解不出来。缓解办法：每卷开头复写一份代头（几十字节，便宜）；字典是否也每卷复写（每卷多 16–112 KiB）做成选项，开销要实测。
  - **尾部只在最后一卷**：与单文件的问题相同，靠代头和第二层的记录解决。
  - **固实模式**：一个帧跨卷时，缺了前面的卷，后面就解不出来，比分块模式吃亏得多。
- **安全**：读取一组卷时要限制卷数和总大小，卷号不能重复或越界，卷文件名只按约定的模式在同一目录里找，不跟随用户给出的其他路径。生产格式的分卷要写进那份生产 ADR（C 级）。
- **研究上要量的**：H-partial 加一种情形“缺中间某一卷”；比较每卷复写代头 / 复写字典的开销与恢复率。

#### 7.6.1 实现（2026-11-15，用户要求立即实现）

- 在 `seedarc_append4_study` 里实现，卷文件名为 `vol-NNNNN.sadv`：
  - `split 包 卷大小 新目录 [none|gen|dicts]`：切分已有的 v4 包，目录必须不存在；
  - `vappend 卷目录 新文件目录 [--plan 计划]`：要求卷齐全，拼回后追加，**只写新卷**，已有卷文件不以写方式打开；
  - `vverify 卷目录 输入目录`：拼回后完整核对；
  - `vpartial 卷目录 输入目录`：依次假设每一卷缺失，报告能恢复的文件数，以及数据落在缺失卷里的文件数。
- **卷头**：60 字节固定部分（魔数、版本、卷号、档案标识、逻辑起点、数据长度、标称卷大小、上一卷整个文件的 CRC32C、复写模式、复写区长度），加复写区和覆盖两者的 CRC32C。
- **档案标识**：对包头、第 0 代的代头和字典做 FNV-1a 64。这几段追加永远不会改动，所以追加出的新卷标识与旧卷相同。它用来区分不同的包，不是安全手段。
- **复写**（`carry`），按逻辑偏移复写卷开头之前的字节段：
  - `none`：不复写；
  - `gen`（默认）：包头，加上当时生效那一代的代头；
  - `dicts`：再加上那一代用到的全部字典。
  拼接时，复写段与已有数据重叠的部分必须完全相同，否则报错。
- **缺卷**：缺失的部分用零填充，同时记下哪些字节真实存在。扫描和恢复只解码完全落在真实字节里的块和帧；固实帧解码到第一个空洞为止。
- **检查**：
  - 同一组卷必须档案标识、标称大小、复写模式都相同；
  - 相邻两卷都在时，要求逻辑范围首尾相接、卷链 CRC 一致；
  - 卷号必须与文件名一致；
  - 拼回要求卷齐全，拼出的包要通过完整解析，档案标识也要对得上。
- **测试**（`check_append4.cmake`）：三种模式 × 三种复写，覆盖切分、核对、追加（旧卷哈希不变）、再核对、缺卷恢复。复写 `dicts` 的分块模式下，每缺一卷，损失的文件不超过“数据在该卷里的文件数 + 1”。另有拒绝情形：目录已存在、卷太小、缺卷时核对、缺卷时追加、混入别的包的卷。`selftest` 新增 433 个卷头 / 复写区损坏样本和一个卷数据损坏样本，全部被拒（总计 1675/1675）。
- **构建**：MSVC、GCC UCRT64、Linux GCC、Linux Clang ASan+UBSan 都是 0 警告，Linux 43/43，无 sanitizer 报告。
- **冒烟观察**（`core/` + `tests/`，32 KiB 一卷，**不是实验结果**）：
  - 不复写：前三卷（包头和字典所在）缺任何一卷，什么都恢复不了；第二代的代头所在卷缺了，第二代的文件也丢（43/55）。
  - 复写代头：第二代那种情况恢复到 55/55，开销只多几百字节。
  - 复写字典：每缺一卷，凡是数据不在这一卷里的文件都能恢复，但卷这么小时复写的字典（约 62 万字节）比包本身还大。这个选项只适合大卷，开销要在 dev 上按真实卷大小量。
