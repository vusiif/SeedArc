# Seed 的追加优势：接近固实的压缩率，追加时免于重新搜索（r1 计划）

状态：**计划，尚未实现、尚未运行**。日期：2026-11-15。任务：DEV-017。前序：[seed-g5-r1](seed-g5-r1.md)（Seed 在小空间里没有搜索优势，H2 不成立）、[shared-dictionary-r1](shared-dictionary-r1.md)（固实压缩列为后续）。

## 1. 用户的定位（2026-11-15，原话要点）

> seed 方案就是可以减少追加文件的重复搜索时间，而分组压缩本质就是为了更小的压缩率，固实压缩用于最小的压缩率（一般情况下），seed 方案就可以在压缩率接近固实压缩的基础上，加快追加压缩文件的速度。

此前用户还指出：Seed 的优势区间在大文件、无法完全遍历的场景，小文件没有优势；另一个优势是可复现性。

用户进一步说明（2026-11-15）：

> 可复现性包含两方面，一方面是同一份文件再次压缩（其实也就是我刚才说的追加文件），另一方面是解压，因为如果没有 seed，解压会变得比较困难。

### 1.1 两种可复现性的落地方式

- **再次压缩 / 追加（编码端）**：同一个工具版本、同一个 Seed、同样的输入，得到逐字节相同的产物，不需要重新搜索；追加时，新文件按 Seed 的规则直接确定位置和参数。这对应第 5 节的 H-append 和 H-generalize。
- **解压（解码端）**：Seed 是**解码计划的紧凑描述**。解码端用版本化的、确定性的规则，从 Seed 加上索引里的路径和大小，就能算出每个文件属于哪个组、用哪个字典，不必为每个文件显式存一张表。G5 的容器 v2 已经实现了“从 Seed 重算分组，并与组表核对”。
- **必须守住的边界**（AGENTS.md 第 6 节）：解码所需的信息必须能从归档里读到，或者从归档里的元数据确定性地重建。所以说“没有 Seed 解压会变得困难”，准确的意思是：Seed 就是这部分解码元数据，它**必须存进归档**；不用 Seed 的方案，则必须把等价的显式表存进去。Seed 不是密钥，不能从 Seed 恢复文件内容。不能出现“归档里只有数据，Seed 由外部提供才能解压”的设计。
- **代价与风险**：
  - 解码端要重新执行分组规则，这需要计时；
  - 规则的实现一旦改变，旧 Seed 必须仍能按旧修订解释，所以解释器要带修订号，不能静默改变语义；
  - Seed 和显式表要么二选一存储，要么同时存储用作校验，两者的元数据大小都要计入。

### 1.2 新增假设（与第 5 节一起在 dev 上确定门槛后冻结）

- **H-meta**：用 Seed 加组键映射代替逐文件组表，元数据至少减少 X %（文件越多越明显），而解码端重算分组的额外时间不超过 Y 毫秒，或不超过解压时间的 Y %。
- **H-decode-repro**：同一个 Seed 和归档，在两个平台（Windows / Linux）、两种编译器上重算出的分组完全相同，跨平台确定性已经有测试。

## 2. 要回答的问题

不是“Seed 能不能搜得更好”（G5 已回答：在小空间里不能），而是：

- **Q-A（追加）**：已有压缩包追加新文件时，基于 Seed 规则的追加，能否在**接近固实的压缩率**下，比固实追加和全量重建快得多？
- **Q-G（推广）**：Seed 产出的是一条**规则**，能把没见过的新文件放进合适的组；直接搜索产出的是一张**逐文件分配表**，新文件没有现成的位置。这种推广能力是否带来可测的收益？

## 3. 对照组（暂定）

| 组 | 首次压缩 | 追加一个或一批新文件 |
| --- | --- | --- |
| R 全量重建 | 任意方法 | 对旧文件和新文件一起重新压缩（压缩率最好的参照之一，最慢） |
| S 固实 | 每组一个连续流 | 二选一，都要测：重新压缩整组的流（压缩率保持，代价大）；或者追加一个新的固实段（快，但压缩率下降） |
| D 直接搜索 + 分配表 | G5-coord 的结果 | 新文件没有规则可依：(a) 为新文件单独重新搜索；(b) 用最近似的组（启发式） |
| Seed | G5-seed 的结果 | Seed 规则直接决定新文件属于哪个组；用该组已有的字典编码，旧数据块原样保留；可选：以旧 Seed 为起点，做小预算的热启动再优化 |
| LZMA2-6 | 生产 CLI | 全量重建 |

## 4. 指标

- **压缩率**：每次追加后的完整大小，以及与固实（整组重压）的差距百分比；连续追加 N 次后的漂移（字典逐渐过时）。
- **追加耗时**：只计追加操作本身（读入、编码、写出、索引），与全量重建、固实整组重压比较；同时记 CPU 时间和墙钟时间。
- **单文件解压延迟与峰值内存**：固实会牺牲随机访问，这是分组和 Seed 方案的对价。
- **正确性**：每次追加后逐字节往返；“按历史可复现”是否成立，即同一个旧包、同一个新文件、同一个工具版本，得到的新包逐字节相同。

## 5. 可证伪的假设（数值门槛在 dev 上确定后、看留出集之前冻结）

- **H-ratio**：Seed 方案首次压缩的大小，与固实（同分组、整组一个流）的差距不超过 X %。
- **H-append**：单次追加的耗时不超过固实整组重压的 Y %，也不超过全量重建的 Y %；而追加后的大小，与“全量重建得到的 Seed 包”的差距不超过 Z %。
- **H-drift**：连续追加 N 次后，Seed 方案相对全量重建的大小漂移不超过 W %；超过时，热启动再优化能把差距收回到 Z % 以内，且耗时远小于从头搜索。
- **H-generalize**：在追加的新文件上，“Seed 规则分配”的大小不劣于“D(b) 最近似组启发式”，并且不需要 D(a) 的重新搜索时间。
- **H0**：所有产物逐字节往返；“按历史可复现”成立。

## 6. 必须先解决的设计问题

1. **分组规则必须对插入保持稳定**。G5 的规则是“按总字节数排名，前 k−1 名各自成组”，加一个大文件就可能改变排名，从 Seed 重算出来的分组会和已存的组表对不上，G5 容器 v2 的“Seed 与组表一致”校验也会失败。r1 的候选做法：把“组键到组号”的映射存进包里，新的键按 Seed 规则落进固定的组或“其他”组，不再每次重新排名。
2. **两种“可复现”分开承诺**：“按历史可复现”可以做到；“追加结果等价于全量重建”一般做不到，因为字典是按当时的文件训练的。格式契约里必须写明承诺的是哪一种。
3. **追加的安全性**：按项目底线，不就地修改旧包；写出新文件（旧数据块原样流式拷贝，不重新压缩），再原子发布；中途失败时旧包保持不变。
4. **对生产格式的影响**：如果字典或固实要进生产，“支持增量追加”应写进那份 ADR 的需求，避免格式定型后返工。

## 7.1 语料设计：append-r1（2026-11-15，构建前确定）

四个池，每个池都按整组划分成 dev 和 holdout，内容 SHA256 不相交；每个划分再切成“初始集”加 3 批追加。

| 池 | 来源 | 分组单位 | 每个划分的上限 |
| --- | --- | --- | --- |
| linux-src（公开） | Linux 6.12 源码 | 前两级目录（如 `drivers/net`） | 48 MiB |
| native-bin（本机） | MSVC `lib/x64` 的 `.lib`；MSYS2 UCRT64 `bin` 的 `.dll` / `.exe` 和 `lib` 的 `.a`；每个文件 64 KiB – 32 MiB | 文件名中第一个 `-` / `_` / `.` / 数字之前的前缀（近似软件包） | 64 MiB |
| silesia（公开） | Silesia 的 12 个文件 | 每个文件一组 | 无（约一半进 dev，一半进 holdout） |
| wiki-text（公开） | enwik8 按顺序切成 100 段，每段 1,000,000 字节 | 段 | 前 50 段为 dev，后 50 段为 holdout |

- **路径**：每条路径都用 `seedarc_path_check` 检查（ADR-0005）；每个划分的完整清单还要用 `--manifest` 模式过一遍生产的大小写冲突检查。Python 先用 `casefold()` 把可能冲突的一对都排除，这比简单大小写折叠更严，宁可多排除，被排除的逐个列出。
- **追加顺序**：wiki-text 按段的自然顺序（模拟日志按时间追加）；其他池按 `sha256("append-r1:<路径>")` 排序。按字节累计：前 70 % 是初始集，其后三个 10 % 各成一批。
- **enwik8 切段是人为构造**，用来模拟“新数据不断追加”的场景，记录里会注明。
- 原始文件和切出来的段只放在被忽略的 `research/local/append-r1/` 下，仓库里只存清单。

## 7.2 研究容器 v3 与工具设计（2026-11-15，实现前确定）

- **新工具 `research/tools/append_study.cpp`**。`g5_study` 随冻结配置 g5-r1 定型，**不再修改**，以保证 G5 的结果可复现。新工具复用 `study_common.hpp`，计划的字段（规则、k、每组 D / T）与 G5 相同。
- **对插入稳定的分组**：首次压缩时，按字节数排名，前 k−1 个组键各自成组；把这 k−1 个“组键到组号”的映射写进包里的**组键表**；其余的键，以及以后追加时出现的新键，都落到最后一个“其他”组。追加时不重新排名，旧文件的分组永远不变。
- **两种元数据模式**（用来检验 H-meta）：
  - **显式**：每个文件 1 字节组号，加组表；
  - **Seed**：只存 4 字节 Seed 加组键表，解码端按规则从路径和大小重算每个文件的组。

  两种模式下，数据与字典完全相同，只有元数据不同。
- **追加操作** `append OLD NEW_DIR OUT`：旧字典和旧数据块按字节原样拷贝，不重新压缩；新文件用所属组的现有字典编码；重写组号表 / 组键表和索引；写成新文件（目标已存在就拒绝），再在内存里把全部文件逐字节核对。新文件归哪一组：
  - Seed 模式：用 Seed 的规则加组键表决定；
  - 显式模式的 **D(b)**：不用规则，按启发式归入“已有文件里与它路径公共前缀最长的那个文件所在的组”。
- **固实对照**：每组的文件按顺序拼接成一个 Zstd-9 帧，窗口取 `min(27, ⌈log₂ 组字节数⌉)`，并记录每个文件在流中的偏移。追加有两种：
  - 整组重压：压缩率保持，代价是整组；
  - 追加新的固实段：快，但不能利用旧段的内容。

  单文件解压必须从帧头开始解码，延迟会单独测量。Zstd 的参数化帧编码只在 `core/codec/dictionary.cpp` 的研究适配器里调用（ADR-0003：zstd 头文件不出 codec 边界）。
- **全量重建参照**：在“初始集 + 已追加的各批”上，从头搜索再打包。

### 7.3 Seed 放在哪里（用户 2026-11-15 决定）

- **明文放在文件尾部的索引区**，带修订号、长度（有上限）和值，由尾部的 CRC32C 一起保护。头部只放格式版本和“含 Seed”的标志。
- **追加只追加**：新包 = 旧包的全部字节 + 新数据 + 新尾部。旧包是新包的逐字节前缀，旧尾部作废但留在原处（它的字节也计入大小）。新尾部带上历次的 Seed 记录（第几代、Seed、覆盖到第几个文件），支撑“按历史可复现”。
- 计划的来源：在初始集上用冻结的 `g5_study` 搜索得到计划（它的按字节排名分组，与 v3 首次压缩时的排名一致），再由 `append_study pack` 按该计划生成 v3 包。

### 7.3.1 实现（2026-11-15）

- **`research/tools/append_study.cpp`**（`seedarc_append_study`），研究容器 v3（`SADXR003`，结尾魔数 `SADXEND3`）：
  - 头部 32 字节（格式版本、块大小、等级、模式标志）；
  - 第 0 代的字典和数据，之后各代追加的数据；
  - 尾部：组表（字典偏移 / 大小 / CRC32C）、组键表、Seed 记录（修订号 1、长度 4、值）或逐文件组号、历代记录、带显式数据偏移的索引；固实模式另有帧表；
  - 24 字节结尾：尾部偏移、尾部大小、尾部 CRC32C、魔数。
- **命令**：`pack seed|explicit|solid PLAN 输入 输出`、`append 旧包 新文件目录 输出 [segment|regroup]`、`verify`、`peek`（冷启动单文件解压）、`selftest`。
- **追加**：
  - Seed 模式按规则加组键表定组；显式模式和固实模式按“路径公共前缀最长”的启发式；
  - 旧包始终是新包的逐字节前缀（solid 的 `regroup` 除外：它重写受影响的组，生成一个全新的包）；
  - 路径已存在就拒绝；目标已存在就拒绝。
- **固实编解码**：在研究适配器 `core/codec/dictionary.{hpp,cpp}` 中新增 `compress_solid` / `decompress_solid`：单个 zstd 帧，窗口不超过 2²⁷，内容大小写进帧头，拒绝多帧、尾随字节和用了字典的帧。`codec.dictionary_research` 加了相应的测试。
- **作废尾部**：追加后，旧尾部成为不再被读取的字节，校验不覆盖它。自检确认在那里翻转字节不影响解压；其他所有区域的损坏都必须被拒绝。
- **测试**：
  - `research.append_study`（`check_append.cmake`）：三种模式下打包都是确定性的；追加后旧包是前缀，有两代记录；单文件解压正确；拒绝重复追加、覆盖和非规范计划；校验时缺文件会报错；Seed 模式的元数据小于显式模式，而数据字节完全相同；`regroup` 生成全新的包。
  - `selftest` 在 r2 dev config 上：208 个损坏样本全部被拒，18 个作废尾部的翻转确认不影响解压。
- **构建**：MSVC Release、GCC UCRT64、Linux GCC Release、Linux Clang ASan+UBSan 都是 0 警告；Linux 两套配置都是 42/42，无 sanitizer 报告；Windows 主测试 39/39。
- **路径检查工具**：`seedarc_path_check --manifest` 会补上隐含的父目录，再调用生产的清单检查。

  - Seed 只有约 29 位，可以穷举；
  - Seed 只决定分组和字典分配，字典和压缩数据仍在包里，攻击者可以对每个块逐个试字典，绕过 Seed 恢复内容；
  - 所以“去掉 Seed”只是增加了麻烦，不是加密。而且 AGENTS.md 第 6 节写明“Seed 不是密钥”。
- **可行的方向**：由用户密码经 KDF（如 Argon2id）派生密钥，用认证加密（如 XChaCha20-Poly1305）加密整个索引和数据，Seed 在被加密的索引里。保护来自加密本身，而不是 Seed。这属于 C 级协议决定，要单独写 ADR，并做威胁模型和依赖审查。

## 8. 实现边界

研究工具与研究容器（从 G5 的容器 v2 演进为 v3，加入组键映射和追加），不改生产归档格式，也不冻结任何格式。固实对照组需要新的研究编码路径（同组文件连续压成一个 zstd 流，记录每个文件在流中的偏移）。
