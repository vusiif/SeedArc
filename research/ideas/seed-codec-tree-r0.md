## 1. 用户的想法

用户 2026-11-27 在聊天中提出：

这是对 [结构化种子设计草案](../../docs/users_idea/SeedArc_结构化种子设计草案.md) §2 的细化。草案里的 Codec 和 Params 段是定宽的，§11 也写明 16 / 16 / 32 / 32 / 32 的位宽划分不冻结。原稿未改。

"哈夫曼"在这里指的是**前缀码标签**：给算法分配标签时，依据的是它需要多少参数，而不是它出现的频率。参数越多的算法，标签越短，留给参数的位越多。

## 2. 现在的布局（配方映射修订 3）

研究工具用的是 32 位 Seed，见 [solid_plan.hpp](../tools/solid_plan.hpp)。

| 位 | 字段 | 合法值 |
| --- | --- | --- |
| 0–4 | 分组规则 rule（2 位）+ k−1（3 位） | k = 1 时只有 rule 0；k = 2–8 时 rule 0–3，共 29 / 32 |
| 5–7 | 帧上限档位 | 0–5，共 6 / 8 |
| 8–9 | 算法 | 0 Zstd、1 LZMA2，2 / 4 |
| 10–14 | 级别 | Zstd 1–19，LZMA2 0–9 |
| 15 | extreme | 只对 LZMA2 有效 |
| 16 | dedup | 0 / 1 |
| 17–31 | 保留 | 必须为 0 |

**数一数**（直接按上面的合法范围计算）：

- 算法这一段（bit 8–15，共 8 位，256 个值）里只有 39 个合法组合：Zstd 19 个，LZMA2 10 × 2 = 20 个。其中 Zstd 的 extreme 位永远是浪费的。
- 已用的 17 位共 131 072 个值，合法的配方只有 29 × 6 × 39 × 2 = **13 572 个（10.4%）**；其余 15 位整段保留。
- 每加一个开关，就要再占一个高位，所有算法共用这一位，不管它对某个算法有没有意义。ADR-0007 加 extreme、ADR-0008 加 dedup 都是这样做的，保留位的测试也跟着从 bit 17 挪到 bit 18。
- 如果要放 Zstd 的 windowLog、strategy、LDM，或者 LZMA2 的 dict、lc/lp/pb，按现在的做法，每个字段都会在所有算法下占位，这 15 位很快就会用完。

## 3. 候选布局：公共前缀 + 前缀码标签 + 算法专用段

位从低到高读取，总长仍是 W = 32 位。

```
bit 0                     8 9                                                      31
| 公共前缀（9 位，定宽）   | 标签（1–3 位，前缀码） | 算法专用参数（20–22 位，按算法布局） |
```

### 3.1 公共前缀（位置固定，不随算法变化）

| 位 | 字段 | 说明 |
| --- | --- | --- |
| 0–4 | rule + k−1 | 同修订 3 |
| 5–7 | 帧上限档位 | 同修订 3 |
| 8 | dedup | 同修订 3 的 bit 16 |

公共字段放在最前面，不用先认出是哪个算法，就能读出分组、帧和去重。

### 3.2 算法标签

| 标签（按读取顺序） | 算法 | 剩下给参数的位数 |
| --- | --- | ---: |
| `0` | Zstd | 22 |
| `10` | LZMA2 | 21 |
| `110` | Store | 20 |
| `111` | 保留给以后的算法（Brotli 等），可以再往下分 | 20 |

Kraft 和：1/2 + 1/4 + 1/8 + 1/8 = 1，前缀码是完整的，任何比特串都能解出唯一一个标签，不会有歧义。每个算法拥有的码位不重叠，总长也不会超过 W。

### 3.3 算法专用段（字段只是示意，取值范围另需 ADR 决定）

约定：每个可选参数都用 **0 表示"取级别 / 预设的默认值"**。这样，只要把专用参数全部取 0，得到的就是和修订 3 完全相同的配方，现有配方都能一一映射过来。

**Zstd（22 位）**

| 字段 | 位 | 取值 |
| --- | ---: | --- |
| level | 5 | 1–19（现有的允许集合）；20–22 是否开放另议 |
| windowLog | 4 | 0 = 默认，n = 9 + n（10–24），上限受资源限额约束 |
| strategy | 4 | 0 = 默认，1–9 |
| LDM | 1 | 0 / 1 |
| 保留 | 8 | 必须为 0 |

**LZMA2（21 位）**

| 字段 | 位 | 取值 |
| --- | ---: | --- |
| preset | 4 | 0–9 |
| extreme | 1 | 0 / 1 |
| dict | 5 | 0 = 预设默认，n = 2^(n+11)（最大值受资源限额约束） |
| lc / lp / pb | 3 + 3 + 3 | 0 = 默认，n = n−1（0–4）；要求 lc + lp ≤ 4 |
| 保留 | 2 | 必须为 0 |

**Store（20 位）**：全部保留，必须为 0。

保留位统一放在各段的末尾。某个算法以后要加参数，只用它自己的保留位，不影响别的算法。

## 4. 好处与代价

**好处**

- 各个算法有多少参数就占多少位。extreme 这类只属于 LZMA2 的位，不会再挤占 Zstd 的空间。
- 只有专用段里的组合可能无效，而且规则局限在一个算法之内，容易测。
- 新算法从 `111` 分支长出来，已有码的含义一位都不变。符合 AGENTS.md 第 6 节的要求：语义变化开新修订，不悄悄重新解释旧 Seed。
- 128 位版本（用户草案）也能这样做：Chunk、Group 作为公共前缀，Codec 加 Params 作为按算法变长的一段，Variation 保持不变。

**代价与风险**

- 字段位置不再固定，不能再用一个掩码直接取出级别，需要按算法查表的解码器。解码器很小，但是每个算法一张字段表。
- 草案 §5.2 的分段局部搜索：只要变异碰到标签，后面整段参数的含义就会全部改变。搜索要把"换算法"和"改参数"当成两种变异，分开处理，不能把整个 Seed 当成均匀的比特串随意翻位。这和草案 §3.6 说的"确定性不等于局部性"是同一个问题。
- 专用段里加入原始参数（windowLog、dict 等），搜索空间和内存需求都会变大。每个字段都要有上限，ADR-0009 的 `solid_encoder_memory` 也要能覆盖这些参数，否则 `--jobs auto` 会估错。
- 专用段内部仍然有无效值，比如 Zstd 的 level 0、LZMA2 的 lc + lp > 4。如果要做到每个值都合法，可以对专用段用混合进制编码，但这样就看不出字段边界了，不推荐。现在倾向于保留位段，加明确的拒绝检查。

## 5. 大种子与小种子（用户 2026-11-27 聊天补充）

### 5.1 用户的想法

1. **问题**：要复现，就得能用种子复现同一个压缩出来的文件。那么追加过的归档，该怎么用种子表示？
2. **方案**：分成大小两层种子。
   - 大种子：记录能复现整个包的全局参数，由一个专门的工具算出来。
   - 小种子：记录每一代的参数，直接写在包里。
3. **大种子会变**：追加一段以后，整个包的压缩方式其实已经变了，所以表述整个包的大种子自然也要跟着变。

主 Agent 原先建议把大种子固定为第 0 代的配方，这样追加时它不会变。用户否定了这个建议，以上面第 3 条为准。

### 5.2 前提：种子代替不了输入

追加包的字节取决于三样东西：每一代的配方，每一代加进去的文件批次，以及编码器的版本。

文件批次是输入，长度没有上界，任何定长的种子都装不下。所以这里说的"复现"是指：大种子、包里的小种子链、原来的各批文件、相同版本的编码器，四样凑齐，就能重放出逐字节相同的包。种子不能用来恢复文件内容（AGENTS.md §6.1）。

用户仍然希望大种子能完整复现追加包，§5.6 给出的变长历史种子可以做到。按 §5.6 的做法，复现时不再需要当初的各批文件，有最终的文件集合就够了。

### 5.3 定长大种子：只能认出和检验，不能复现

| | 小种子（每代） | 大种子（整个包） |
| --- | --- | --- |
| 位置 | 每代的 GEN 记录。现在每代已经存了一个 32 位 Seed，这次不新增位置 | 不写进包里，由工具从包里算出来 |
| 内容 | 这一代的配方，用 §3 的定长变段布局。是否改成"相对上一代的差异"，见 §5.5 | ① 全局参数：容器修订、映射修订、编码器版本编号、全局策略（去重范围、trailer 形式）<br>② 代数 n<br>③ 链摘要：对小种子链和每代文件清单哈希的确定性摘要 |
| 追加以后 | 新一代多一个小种子，旧的不变 | ②、③ 必然变；如果新一代换了全局策略或编码器版本，① 也会变 |

- 大种子是定长的，而代数没有上界，所以它不可能无损装下整条小种子链。③ 用摘要代替。
  - 摘要的作用是**认出**和**检验**：看手上的包和批次是不是同一份历史。小种子本身仍然从包里读取。
  - 摘要截短到定长以后会有碰撞的可能。长度至少 64 位，它只用来标识，不用来做安全承诺。
- 大种子由同一个包算出来，所以同一个包永远得到同一个大种子。一个包的大种子只在追加或合并以后改变，这正是用户说的"跟着变"。
- 合并成一代以后：n = 1，链里只有一个小种子，大种子退化成"全局参数加一个配方"。

### 5.4 配套工具（候选，未实现）

- `seed-summary ARCHIVE`：校验每一代，然后输出大种子、每代的小种子和链摘要。用户说的"专门用一个工具算出来"指的就是它。
- `replay-check`：给定大种子、原来的各批文件，按小种子链依次执行 pack 和 append，最后比对：
  - 整包的 SHA 必须相同；
  - 重放出来的包，大种子也必须相同。
- 使用 §5.6 的历史种子时，`replay-check` 不需要原来的各批文件。它只要最终的文件集合，先按代号序列把文件拆回各代，再重放。

### 5.6 变长历史种子：从最终文件集合完整复现（用户 2026-11-27 要求，主 Agent 提出做法）

**为什么定长做不到**：同一批最终文件，分成几代、每个文件落在哪一代，可能的分法种数没有上限，而每种分法压出的字节都不同。定长 W 位最多只能区分 2^W 种。按抽屉原理，分法一多，必然有两种历史共用同一个种子。所以，要完整复现，大种子只能是变长的。

**缺的只是"代号"**：最终的文件集合解包就能得到。要从它复现整个包，只缺下面几样：

1. 每一代的配方：小种子链，每个小种子存完整配方；
2. 每个文件属于哪一代；
3. 全局参数和编码器版本。

每一代内部的文件顺序可以按路径确定性地排出来，不需要另外存。所以"历史"就等于给每个文件标一个代号。

**组成**：

```
大种子 = 全局段（定长） | 代数 n | n 个小种子（各自定长） | 代号序列（熵编码）
```

- 代号序列：按路径排序后依次列出每个文件的代号，再做熵编码。大多数文件通常在第 0 代，给它最短的码，这正是用户最早说的"哈夫曼"。
- 粗估：16 000 个文件分成三代，比例 90% / 5% / 5%，每个文件约 0.57 位，合计约 1.2 KB。只有一代时，代号序列为 0 字节。
- **按目录记代号**（未测）：新追加的文件通常集中在少数几个目录里。如果一个目录下的文件都属于同一代，就只记一次这个目录的代号，不必每个文件记一次。这可能比改进熵编码省得多。要在 dev 树上，用真实的追加历史测出实际长度。
- 上界：代号序列最多 文件数 × ⌈log₂ n⌉ 位，再加 n 个小种子的长度。超出上限一律拒绝。
- 代号序列可以从包里推出：trailer 本来就记录着每个文件属于哪一代。所以 `seed-summary` 能直接把它算出来。

**复现条件**：大种子、最终的文件集合、相同版本的编码器，三样齐全，就能逐字节重放出原包。当初的各批输入不再需要。

**限制**：
- 追加只增不改（见 §5.5 第 5 条）。如果允许覆盖，旧版本的内容不在最终集合里，就复现不出来。
- 编码器版本必须相同。跨版本只承诺能解码，不承诺字节相同。
- 定长的折中办法：用规则定义每一代，例如按修改时间分段，那么种子里只需记 n 个时间切点。前提是每一批文件确实能按时间切开，所以只适合一部分用法。

### 5.7 文本形式（用户 2026-11-27：变长以后不应只用字母数字，要考虑别的符号，免得种子太长）

**加符号能省的有限**：字符集越大，每个字符能装的位数只按对数增长。以 9 600 位（约 1.2 KB）为例：

| 表示法 | 每字符位数 | 字符数 |
| --- | ---: | ---: |
| 十六进制 | 4 | 2 400 |
| Base32 | 5 | 1 920 |
| Base58 | 5.86 | 1 640 |
| Base64url | 6 | 1 600 |
| Base85 | 6.41 | 1 498 |
| Base91 | 6.51 | 1 475 |
| Base32768（Unicode） | 15 | 640（UTF-8 下约 1 920 字节） |

- 从十六进制换到 Base64，字符数少三分之一。再往上换，只能多省 5–8%。
- Base85 和 Base91 会用到 `"`、`'`、`\`、`$`、`` ` ``。放在命令行、URL、文件名里都要转义，复制粘贴也容易出错。
- Unicode 方案按字符数算短，按字节数算并不比 Base64 小，还有字体、规范化和形近字的问题。

**候选写法**：

```
sa4.<全局段>.<小种子链>.<代号序列>.<校验>
```

- **全局段和小种子**：用人能读懂的写法，例如 `solid/lzma2-9e/g1-r0/frame-32MiB`，或者紧凑的十六进制。用户说过"看种子就知道在用什么压缩"，这层可读性要保留。
- **代号序列**：熵编码之后，用 Base64url 写出（RFC 4648 §5，不加填充）。它只用 `A–Z a–z 0–9 - _` 这些字符，在命令行、URL 和文件名里都不用转义。
- **校验**：末尾加几个字符的校验码，可以参照 Bech32 的思路。抄错一个字符能检测出来，不会被当成另一个合法种子。
- **超长时改存文件**：代号序列超过一个阈值（例如 256 字符）时，文本里只放它的摘要，完整内容写进 `.seed` 文件。上千个字符的种子，换哪种字符集都没法手抄。
- 真正决定长短的是内容：一代的包没有代号序列；多代的包能不能按目录记代号，比选哪种字符集影响大得多。
