# DEV-017：大规模追加主实验 r2（设计与实现差距）

日期：2026-11-23。作者：协调 Agent；这是依据用户最新方向提出的实施方案，**不是新的用户原话、冻结配置或实验结果**。

## 1. 当前目标与证据顺序

优先依据用户 2026-11-23 在本轮结果之后明确的定位（见第 9 节），再参考 [追加 r1](seed-append-r1.md) 中 2026-11-15–16 的测试后讨论（§1、§7.5.1、§7.5.4、§7.6），其次使用 [G5 留出记录](../experiments/20261115-g5-holdout-main-001/record.md) 的适用边界，再回看最早的结构化种子草案。G5 的小空间负面结果已记录，不以重复同类样本作为新的主目标。

主问题：在不能充分搜索的大规模场景中，保存、沿用或局部更新 Seed 描述的策略，能否以接近固实的完整大小，降低后续追加的总成本，并保留可复现解码、分代与分卷的工程价值？这是待证伪的假设，不能先宣称成立。

印度已中止的两个约 50 MB dev 池只验证了固定环境与部分流程，[记录](../experiments/20261123-append-india-dev-main-001/record.md) 保留，不作主实验。以下条件满足前，不启动主实验或使用留出集。

## 3. A / B / C 的独立历史与对照

| 路径 | 第 i 批起点 | 行为与比较 |
| --- | --- | --- |
| A 沿用 | A 自己的上一包 | 不搜索，沿用上一代 Seed / 组键表 / 字典；旧包逐字节为新包前缀 |
| B-new 新代 | **B 自己的上一包、上一代计划** | 仅对新批次从上一计划 local 搜索，append --plan；现有 v4 只能训练本代新字典，明确命名 B-new，不冒充可逐组选择旧字典的 B-mix |
| B-mix（待实现） | B 自己的上一包及字典集合 | 每组可选引用旧字典或训练新字典；成本含选择、训练和记录。先设计评估器与契约，再决定是否纳入首个冻结主实验 |
| C 合并优化 | C 自己的上一计划 | 在累计输入上 local 搜索，再完整 pack 新包；旧数据重新读入 / 编码 / 写出都计时；不是“只搜少量就免除重压” |
| D 显式表 / 启发式 | D 自己的上一包 | 与 A 同初始计划，新文件按实际最近组启发式；元数据与解码成本完整计入 |
| S-segment 固实新段 | 自己上一包 | 快追加但不能利用旧帧内容，保持独立历史 |
| S-regroup 固实重压 | 自己上一包 | 现有工具重压所有组（偏高），不能称“只重压受影响组”；另列实际整组范围 |
| R 冷启动重建 | 每批 default + 累计输入 | 与 C 使用相同搜索算子和预算；分别记搜索与完整重建，不把固定计划 pack 当作冷搜索 |
| C-coord / R-coord | 各自上一计划 / default | 相同候选空间的直接坐标搜索对照；当前工具搜索的是分组参数，不是任意逐文件分配的 Oracle |

“同一计划不比起点差”仅指**当前输入、当前重新训练字典的评估目标**，不意味着完整 C 包一定比 A 的历史包更小。所有结果按完整产物比较。

## 5. 实施顺序与验收关口

1. **历史正确性（当前）**：运行器必须延续各自的 A / B / C / D / solid 历史；检查 B 的搜索起点确实是自己的上一计划、C / coord 亦然。每批独立 verify，A / B / S-segment / D 的前缀与代数正确，C / R 重建一代；同输入、同历史、同种子复跑字节一致。小夹具只用于这些行为验收。
2. **资源模型与数据准备**：从已获授权的公开源中建立新版本 dev / holdout 清单，内容哈希去重、按来源组划分；不读取 holdout 作调参。首次只建立 / 检查清单，不立刻启动长测。旧的本机专有二进制不上传。大规模流式改动需另列范围与独立回归；不为了跑起来降低安全检查。
3. **候选复杂度**：先对当前可分离空间做参考诊断，量出接近精确解的实际成本与有限预算下覆盖。大输入下即使有限次整份编码也可能不可承受，因此不强制先扩字段或改变格式。仅在现有空间无法代表目标场景时，再选一个确有用途的耦合维度（例如分组与组内顺序共同影响训练选择）；它尚未选择 / 实现，须保留直接表示对照与新修订，不自动冻结格式，不通过扩大 k 偷换问题。
4. **印度 dev**：在固定 Release 工具链上串行、固定 CPU / 线程运行，按方案轮换顺序；固定预算梯度，报告质量—预算—时间曲线和 min / median / max。以冷启动达到的若干质量点为参照，求暖启动达到相同质量的实际成本；仅比较相同预算的终点不足以检验 H-warm。
5. **冻结与留出**：根据 dev 的测量精度和应用取舍提出 X / Y / Z / W，明确接受理由后形成可追溯配置；不能看过 holdout 再补标准。正式留出仅运行一次，失败和无收益同样保存。
6. **恢复 / 分卷单独验证**：分别测 off / checkpoint / file、卷大小与字典复写，统计恢复字节与额外大小；不把缺卷恢复或冗余头成本混进纯追加速度实验。小文件推荐规则仍允许用户覆盖。

- 完整包 / 全部卷字节、旧包 / 新包 SHA256、元数据 / 字典 / stale 尾部 / 数据构成；独立逐文件往返。

- 实际搜索预算与缓存命中、计划 / 组评估数、起点 / 结果计划及候选修订；相同输入历史可复现、Windows / Linux 解码一致。

### 大目录 dev 的后续决定

[首轮完整观测](../experiments/20261123-append-large-dev-main-001/preview.md) 显示固实分段是强简单基线；C 整体重建的体积减少主要是移除旧索引尾部，不能当作 Seed 数据压缩收益。C 与同算子冷启动的最终归档 / 实际预算相同；本轮未观察到 H-warm 的预算优势。单遍、人工分批与跨监控版本的限制见记录，不冻结阈值或推广至其他空间。

因此下一步优先固定策略直接重建 / 结构整理的对照，核对人工公共路径前缀对候选键的影响；再依据真实压缩用途评估布局、分组和顺序的候选修订。保留现有 r4 解码语义，不直接加位宽 / 增预算来制造所谓大空间，也不急于运行留出。统一修复后的监控、预算梯度、重复和漂移仍为后续关口。

## 9. 用户最新定位：在成熟策略上使用 Seed，重点测大规模

来源：用户在本轮结果之后于 2026-11-23 明确表示，小 / 简单文件上的 Seed 预期与简单固实接近，无需专门为此优化；“完全可以只是在现有的策略上面简单套用我们的seed，然后在大规模上面尝试优化测试”。这是最新的研究优先级；小输入近似等价仍是用户的判断 / 工作假设，不改写成已被本轮全面证明的事实。用户两份 users_idea 原稿哈希未变，此处记录新消息，不修改原稿或历史实验数据。

### 采纳与当前实现差距

- 保留现有成熟编解码器和有效的固实 / 固实分段策略，Seed 放在策略表示、生成、保存与复用这一层。无搜索路径可以映射到既定强策略，小 / 简单输入无需为了证明 Seed 有效而强行搜索或追求额外压缩率；仍须保证正确性、安全、确定性和 Unicode 路径支持。
- 当前 v4 的 header_for 把 seed 与 solid 设为互斥模式；seed 路径走分块 encode_blocks，solid 路径走 compress_solid。先前两条路径的体积差混入了底层布局差异，不能把 seed 模式弱于固实直接解读为“在同一固实策略上附加 Seed”的代价或 Seed 表示本身无效。
- 下一最小实现应让 Seed 能表达 / 重建所选强策略的具体计划，再由现有编码管线执行；同一计划和配置下，Seed 表示与显式表示应使用相同的数据编码路径。Seed 元数据、完整归档大小、解码重建成本分别核算，不承诺只加 Seed 就会自动改善压缩率。
- 该接入的最小实现与零搜索验证已在 DEV-018 落地（详见末尾实施入口），不静默重解释旧种子或使旧 r4 包不可解码；候选映射采用可追溯的新修订。延续计划解释与 codec / I/O 解耦，不预建插件或泛化调度框架。

### 下一轮顺序（优先于第 8 节原先的后续排序）

1. **强策略上的最小 Seed 接入**：从已有固实 / 固实分段计划开始，保留固定策略和显式计划对照；零搜索时检查同一底层编码的数据载荷一致性、往返和确定性，完整大小允许有已核算的 Seed 元数据差异。小夹具用于验收接口，不再单独展开小文件压缩调参。
2. **直接进入已验收的大规模 dev 范围**：在印度固定环境中比较相同底层策略的固定计划、Seed 无搜索、Seed 预算搜索、旧 Seed 复用 / 热启动及直接表示的同算子搜索；记录完整大小、追加与重建成本、实际预算、RSS 和分批漂移。当前 512 MiB 是已验收范围，更高规模按资源路径验证推进，不仅因独占授权就放宽 1 GiB 输入界限。
3. **根据实测选择优化维度**：先利用现有有效策略，复杂度作为实测指标；无需先人为制造耦合或扩大位宽才能开始大规模测试。只有分组、帧布局、顺序等确有用途时才扩展候选，并保留相同策略空间 / 算子 / 预算的直接表示对照。

固定策略重建、根路径检查和旧索引开销仍是避免归因错误的必要对照，但不要求先开发一套独立的索引整理优化器或继续精调旧分块 D/T 路径。既有负面结果保留，用于界定旧实现；它们不代替上述同底层策略的新实验。独立留出仍在配置 / 评价规则确定后使用。

### 最小接入实施入口

DEV-018 选择 [solid-plan-r1](solid-seed-r1.md)：新实验头部修订5、种子映射2，旧v4不变；seed-solid / explicit-solid 使用同一Zstd-9固实编码，默认0单组，首版off冗余、明确拒绝未验收恢复 / 分卷。当前本机验收与印度512MiB零搜索结果见 [执行记录](../experiments/20261123-solid-seed-main-001/record.md)。搜索尚未接入此固实目标，不复用旧分块搜索结果冒充大规模优化。

DEV-018验证补充：Windows Release43/43、Linux Release / ASan+UBSan各44/44，32份固定小包跨平台SHA相同。真实512MiB零搜索三表示的完整帧载荷一致，四代新Seed / 显式包相对旧固实只多56 B元数据。具体证据与IDE待补范围见执行记录；本轮不宣称搜索收益，后续对照直接消费同一固实目标。

## 10. 用户最新校正：速度与恢复性优先（2026-11-24）

用户明确主目标是：接近固实压缩率时提高速度和安全性，或在较快速度下优于同压缩时间的其他算法；不能只拿各对手单项极值作判据。DEV-019/020体积搜索仅保留为机制基线，不继续围绕29分组候选抠少量字节。下一阶段按[速度 / 体积 / 损坏恢复联合计划](speed-resilience-r1.md)，先建立可比基线和有界分段 / 局部重压范围，再让Seed描述 / 选择 / 复用有实测价值的计划。安全主指标包括损坏隔离和可核验恢复，既有内存 / 路径 / 资源底线不放宽。完整归档、实际时间、规划成本及恢复开销均计入；阈值待dev测量后明确，不预设已有优势。
