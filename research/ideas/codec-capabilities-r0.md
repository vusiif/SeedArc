# 现有编解码器里没用上的能力（codec-capabilities r0）

2026-11-26，主Agent（Claude）。状态：探针已运行（DEV-033，结果见[记录](../experiments/20261126-codec-capabilities-main-001/record.md)）；**不改格式、不改配方允许集**。来源：用户问过要不要增加算法，当时的回答是先挖现有算法没用上的能力；用户 2026-11-26 同意按这个方向开始。

## 1. 要回答的问题

固实帧现在只用了两样东西：Zstd 的单线程 `ZSTD_compress2`（级别 1–19，窗口 ≤ 2^27），和 LZMA2 的原始流（预设 0–9）。下面这些能力都没用上：

| 能力 | 可能带来的好处 | 主要代价 / 风险 |
| --- | --- | --- |
| Zstd 长距离匹配（LDM） | 大帧里相隔很远的重复，例如多份相同的头文件、重复的数据块 | 编码稍慢；DEV-028 里时好时坏 |
| Zstd 20–22（ultra） | 更小 | 编码很慢、内存大；窗口仍限 2^27 |
| Zstd 多线程（nbWorkers） | 编码更快 | 多线程模式切分任务，输出和单线程不同；要确认**输出与线程数无关**，否则会破坏 DEV-031 证明的确定性 |
| LZMA2 extreme（`9e`） | 再小一点 | 编码约慢一倍 |
| LZMA2 + BCJ x86 滤镜 | x86 可执行文件明显更小 | 对非可执行文件可能更差；解码时必须知道用了哪个滤镜 |
| 按文件类别选算法 | 每类用最合适的算法 | 不同类别之间不能再互相引用 |

LZMA2 原始流不支持多线程（liblzma 的多线程只在 `.xz` 容器里按块切分），这次不测。

## 2. 探针：`codec-probe`（只做研究）

研究工具新增两条命令：
- `codec-probe DIR VARIANTS`：把 DIR 里的文件按路径顺序拼成一个整帧，按每个变体压缩；
- `codec-probe-classes DIR VARIANTS`：先把文件分成三类，每类各压一帧，同样跑每个变体。

每个结果都解码回来逐字节比对，并报告：
- 压缩后字节；
- 帧的 CRC32C，用来比较不同线程数的输出是否相同；
- 编码 / 解码耗时；
- 峰值内存。

变体写成 `zstd-19-ldm`、`zstd-9-mt4`、`lzma2-9e-bcj` 这样的名字。

文件类别：
- 可执行：开头是 `MZ`、ELF 或 Mach-O 魔数；
- 文本：前 64 KiB 没有 NUL，且可打印字节（含 UTF-8 高位字节和常见空白）占 95% 以上；
- 其他二进制：其余所有文件。

## 3. 数据与环境

| 类别 | 数据 | 环境 | 测什么 |
| --- | --- | --- | --- |
| 源码 | DEV-023 源码树（268 MB） | 印度，单 CPU 钉核 | 体积 + 时间 |
| 文本 | DEV-023 文本树 | 印度，单 CPU 钉核 | 体积 + 时间 |
| 多线程 | 同上两棵树 | 印度，不钉核（4 核） | 时间，以及输出与线程数是否无关 |
| 可执行 / 库 | append-r1 dev 的 native-bin（64 MB，MSVC / MSYS2 二进制） | **只在本机** | 体积（本机耗时仅作参考） |

native-bin 的规则是"只在本机评估、不再分发"（[append-r1](../datasets/append-r1.md)），所以不上传到任何服务器。所有数据都是 dev，不碰 holdout。

## 4. 怎样算值得进入配方

- 体积：完整归档字节数明显变小，在同类数据上有一致的收益，不能只靠一个文件。
- 时间：按 DEV-026 的预算口径，在相同或更少的编码时间内更小，才算支配旧点。
- 确定性：输出必须与线程数、CPU、构建无关；多线程如果做不到，只能作为"同一线程数下可复现"的单独承诺，而且需要用户确认。
- 解码：所需参数必须能从配方读出，例如 BCJ 要写进配方；解码内存要有上限。

这些条件满足了，才会提出扩展 ADR-0006 允许集的方案，并请用户确认。

## 5. 结果与下一步（DEV-033，2026-11-26）

整帧实测，详见[记录](../experiments/20261126-codec-capabilities-main-001/record.md)：

| 能力 | 结论 |
| --- | --- |
| LZMA2 extreme（`9e`） | **唯一明确的收益**：比 LZMA2-9 再小 2.7%（源码）/ 2.1%（文本）/ 1.6%（native-bin），编码慢 1.3–1.9×，解码不变，现有解码器即可解 |
| Zstd LDM | 强开无效。`ZSTD_c_enableLongDistanceMatching = 0` 是"自动"：level ≥ 16 且窗口 2^27 时 zstd 已自动开启；窗口 2^26 的 native-bin 上强开只省 0.04% |
| Zstd 20–22 | 被 LZMA2-9 支配：更大、更慢、内存多 450–560 MiB；只有解码快这一点，目前无需求 |
| Zstd 多线程 | 输出与线程数无关（mt1 = mt2 = mt4），但与单线程 API 不同，+0.01–0.07%；提速取决于能切成几个任务：源码 Zstd-19 4 核 2.97×，文本 1.18×，Zstd-9 无提速 |
| LZMA2 + BCJ | 不采纳：固实帧里 +4.3%，BCJ 按位置改写地址，破坏了相同副本之间的匹配 |
| 按类分帧 | 不采纳：native-bin 上 +0.4%；源码、文本树全部是一类 |

32 MiB 分帧完整归档复测（同日，第二轮）：LZMA2-9e 比 LZMA2-9 小 2.72%（源码）/ 2.08%（文本），编码慢 1.69× / 1.43×，解码与内存不变；LZMA2-6e 同样有效（−2.8% / −1.9%），源码上比 LZMA2-9 还小 1.4%。分帧下窗口只有 2^25，LDM 自动规则不触发，强开只省 0.26% / 0.15%。

下一步（待用户决定）：
1. 是否把 extreme 作为"任意 LZMA2 预设可加 `e`"加入 ADR-0006 允许集。这需要在配方 / Seed 里表示它（C 级）；解码器不用改。
2. Zstd 多线程如果要用，只能作为"同一 zstd 版本下与线程数无关"的单独承诺，同样要用户确认；在 32 MiB 分帧下价值更小，因为分帧本身就可以并行压缩。
