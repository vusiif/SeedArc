## 1. 用户的想法（2026-11-27，聊天）

1. **增量重压**：有时文件夹里只改了几个文件，却要把整个文件夹重新压一遍。种子可以在这里派上用场：先推出改了哪几个文件，再只针对这几个文件做压缩搜索。
2. **本地不一定有旧包**，所以同时支持两种种子：
   - **不定长种子**：记录每个文件的校验值，最终存成一个文件；
   - **定长种子**：不必支持太多追加，更适合日常使用。
3. **定长种子记录的是压缩思想**，而不是跟具体文件强绑定的压缩算法。
4. **只需要较优解**：人们不需要最优解，只需要一个较优解。这句话是用户对下面第 6 节"通用策略不一定最优"的回答。

原稿没有改动。主 Agent 曾说过"种子本身推不出改了哪些文件"，用户据此补充了第 2 条：把校验值放进不定长种子。

## 2. 三层分工

| 层 | 内容 | 是否与文件绑定 | 放在哪里 |
| --- | --- | --- | --- |
| **策略种子**（定长） | 压缩思想：文件怎么分类、每类用哪套配方、怎么分组、帧怎么切、是否去重 | 不绑定，可以用在别的目录上 | 用户手里；也可以抄一份到包里 |
| **计划**（从策略推出） | 策略套到这批文件上的具体结果：每个文件属于哪一类、放在哪一帧、用什么参数 | 绑定 | 包里（解码依据），以及 `.seed` |
| **种子文件**（不定长，`.seed`） | 计划，加上每个文件的强哈希、所属代、小种子链，以及每帧压缩后的哈希 | 绑定 | 包旁边的一个文件 |

- 套用是确定的：同一个策略种子、同一批文件、同一版本的工具，得到同一份计划和同一个包。
- 编码时可以根据内容做选择，但解码需要的信息必须全部写在包里（AGENTS.md §6.1）。计划写进包里，读包时不需要策略种子。
- 这和用户在 user-vision §4 说的定位一致：Seed 是一种表示，让人知道自己在用哪种压缩方式，并能把这种方式固定下来、反复使用。

## 3. 策略种子（定长）

### 3.1 候选布局（128 位，只是示意）

| 段 | 位宽 | 内容 |
| --- | ---: | --- |
| 全局 | 16 | 映射修订、策略族 |
| 分类器 | 8 | 按扩展名、文件头魔数、抽样熵……分类器要带版本号，结果必须是确定的 |
| 分组 / 帧 / 去重 | 24 | 类似现在的 rule、k、帧档、dedup，但作为规则来解释 |
| 每类配方槽 | 3 × 24 | 例如"文本"、"已压缩"、"其他"，每个槽用 codec-tree 的定长变段布局编码 |
| 保留 | 8 | 必须为 0 |

- 32 位放不下几个槽，所以策略种子用 128 位，和用户草案的长度一致。codec-tree 那篇稿子里的 32 位布局，就是这里"一个配方槽"的编码方式。
- 分类器如果要看文件内容（比如抽样），必须满足四条：有版本号；结果确定；读取的字节量有上限；分类结果写进计划。否则，同一个种子在不同机器上可能会分出不同的类。

### 3.2 追加

定长种子不必支持很多次追加（用户第 2 条）。

- **单代包**：策略种子加上文件集合，就能逐字节复现。
- **多代包**：定长种子只能说明"这个包是怎么压的"，并用摘要认出这个包，不保证能重放。要完整复现，就用 `.seed`（见 codec-tree §5.6 和本稿第 4 节）。

## 4. 种子文件 `.seed`（不定长）

**内容**：
- 全局段、小种子链（每个小种子都存完整配方，这是用户 2026-11-27 的决定）；
- 每个文件一条记录：路径（前缀压缩）、大小、强哈希、所属代；
- 帧布局（每帧包含哪些文件），以及每帧压缩后的哈希。

**要求**：
- **强哈希**，至少 128 位，例如 SHA-256。CRC32C 只能用来发现意外损坏。如果拿它判断"文件没改"，碰上 CRC 恰好不变的修改，就会静默出错。
- **写包时同时生成**。现在的 trailer 里只有 CRC，没有强哈希，所以不能事后从包里推出 `.seed`。由 pack 在写包时一起输出，归档格式不用改。
- **体积粗估**：每个文件 40–50 B，主要是哈希。16 000 个文件大约 700 KB。没有实测。
- **有上限**：记录条数、路径长度和总大小都有上限，读取时先检查，再分配内存。
- **隐私**：`.seed` 里有完整的文件清单和指纹，分享出去就暴露了目录结构，别人还能用它核对某个文件在不在包里。分享时只给策略种子；`.seed` 默认当作私人文件。

## 5. 增量重压

**步骤**：
1. **找改动**：用 `.seed` 里的路径和强哈希与当前文件夹比对，分出新增、删除、修改、未变四类。不需要旧包。
2. **找受影响的帧**：固实压缩时，一个文件和别的文件共用一帧。所以"只压这几个文件"，实际做的是只处理含有改动文件的帧。
3. **未变的帧**：
   - 本地有旧包：直接把旧包里这些帧的压缩字节拷过来。拷之前要逐字节比对（或核对强哈希），确认来源就是那一帧。
   - 本地没有旧包：按旧配方重新压这些帧。压缩是确定的，压出的结果应当和 `.seed` 里记的帧哈希一致。对不上，说明编码器版本或环境变了，必须报出来，不能静默接受。
4. **受影响的帧**：先按策略种子重新套用，再在这几帧上做有预算的针对性搜索。搜索结果写进新包的计划和新的 `.seed`。

**省在哪里**：
- 没有旧包时，省的是**搜索**（未变的帧不搜，只重压），重压本身省不掉。
- 有旧包时，未变的帧连重压也省了。

**待解决：帧边界会连锁移动**：
- 现在的帧是按大小贪心切的。一个文件的大小一变，它后面所有帧的边界都可能跟着动，未变的帧也就复用不了。
- 而且 ADR-0006 规定，读包时要按配方重算帧边界，算出的结果和包里不一致就拒绝。
- 要让旧帧保持不动，可以按内容定边界（DEV-037 研究过，当时没有采纳任何规则），或者在包里显式记录帧的成员。这两种都要改帧边界的规则，属于 C 级。

**和追加的关系**：
- 如果用追加来表示"修改"，就要把新版本写成新的一代，旧内容留在包里成为死数据，包会越来越大。
- 增量重压是重建一个新包，只复用未变的帧，包的大小接近整包重压。
- 所以"修改文件"更适合走增量重压，追加只用来新增文件。这和 codec-tree §5.6 "追加只增不改"的前提一致。

## 6. 验收口径：较优解，不求最优

用户的判断：人们不需要最优解，只需要较优解（第 1 节第 4 条）。

据此，策略种子的验收**不以"接近逐文件夹搜索出的最优计划"为门槛**，改为"较优"。

**用户 2026-11-27 已决定这条线：不输强默认即可。**也就是说，在同一批数据上，策略种子压出的完整归档字节数不大于强默认配方压出的。

- 强默认暂定为 DEV-038 的 `solid/lzma2-9e/g1-r0/frame-32MiB/dedup`。正式写 ADR 时再确认，如果那时有更强的默认配方，就换成它。
- 对比在完整归档字节上进行，trailer 和元数据都算在内。用同一版本的工具，在 dev 数据上调参；留出集只评估一次。
- 时间不在这条线里，但要如实记录。如果策略种子比强默认慢很多，就在记录里写明，不能隐去。

**用户同日补充：什么算"较优"，由使用的人决定。**想要更快，包可以大一点；想要更小，时间可以长一些。甚至可以专门设计一个"彩蛋种子"，用来找最优解。据此把上面那条线细化为：

- **按偏好分档比较**：每个偏好档都有自己的强默认，在本档内比较，不输即可。
  - 例：
    - "快"档的强默认是一个快速配方，比如 Zstd 的某个级别；
    - "小"档的强默认是 DEV-038 的 LZMA2-9e 去重配方。
  - 比较规则：先在本档的另一个维度上保证预算相当，然后看偏好的那个维度不输；或者用 Pareto 前沿比较，不被本档强默认支配即可。
  - 每档的强默认和预算在 ADR 里写定。
- **偏好放进策略种子**：在全局段里留一个"偏好档"字段，让种子本身说明它是按什么取舍压的。这和 STATUS 2026-11-24 用户说的"取舍由用户选择"（速度、体积、损坏恢复、单文件提取、补加新文件）是同一条线；联合计划见 [speed-resilience-r1](speed-resilience-r1.md)。
- **彩蛋种子**：用户随后说明，它完全独立于策略种子系统，见第 7 节。它不占偏好档里的取值。

原先列出的候选口径保留在下面，作为参考：

- 不比强默认差：完整归档的大小不比固定的强默认配方大，例如 LZMA2-9e 去重配方，或者 DEV-040 外部基线里同等耗时的 tar.xz / 7z；
- 时间在预算内：套用策略加上有限搜索的耗时，不超过约定的倍数；
- 增量收益：改动只占少数时，增量重压的耗时明显少于整包重压，而包的大小与整包重压相差不超过约定的百分比。

和最优计划之间差多少，仍然要量出来写进记录。但它只作为参考数字，不作为通过的门槛。

**已有证据，供参考**：DEV-012 在分块路径上测过按内容抽样选算法（adaptive-file-r1）。无界档 −7.45%，固定 LZMA2-6 是 −7.95%，选择器在大小和速度上都输给了固定配方；Oracle 也只比 LZMA2-6 再小 0.025%。当时测的是分块路径，现在是固实路径加分组，条件不同，不能直接套用。但这说明分类加配方分配的收益不能凭直觉断定。

## 7. 彩蛋种子（用户 2026-11-27）

### 7.1 用户的想法

- 彩蛋种子要"看着有字面意思"：它是一个字符串，有自然语言的含义。
- 它**完全脱离整个策略种子系统**，专门用来做一些独特的算法。比如用户先前提到的"找最优解"。

- 用户进一步说明：**彩蛋相当于官方给出的一些建议，或者一些好玩的压缩方法，必须跟用户说清楚。**

据此，彩蛋不是隐藏功能，而是官方整理、公开说明的一组命名压缩方法。它有两类：
- **建议类**：官方推荐的做法，例如"日常备份就这样压"；
- **趣味类**：独特、好玩的压法。

所有彩蛋都要能列出来，比如提供 `egg --list`，逐条显示名字、字面含义、实际做什么、速度和体积的取舍、资源上限、版本。用某个彩蛋压缩之前，也要先把这些告诉用户。

**用户 2026-11-27 已决定：建议类彩蛋可以复用策略种子系统。**建议类彩蛋就是给一个官方策略种子起的好记的名字，展开后按策略种子执行。注册表里要写明它展开成哪个策略种子，`egg --list` 也要显示出来。只有趣味类彩蛋才需要自己的算法，独立于策略种子系统。

### 7.2 设计约束（主 Agent 提出，用户 2026-11-27 已全部接受）

1. **有注册表，不做哈希**：
   - 每个彩蛋是注册表里的一条：名字 → 一个算法和它的版本，例如 `egg/<名字>@1`。
   - 不能把任意字符串哈希成种子。否则拼错一个字，就会静默变成另一个种子。
   - 名字不在注册表里，一律明确报错，不回退到别的含义。
2. **和普通种子不能混淆**：文本形式用固定的前缀，比如 `egg/`，和 `sa4.`、`solid/`、十六进制等形式区分开。
   - 名字的字符集要先定下来。如果只用 ASCII，就规定为小写、可以带连字符。
   - 如果允许中文，就要规定一种 Unicode 规范化形式（例如 NFC），并拒绝形近字和不可见字符。
3. **解码不依赖彩蛋**：
   - 彩蛋只改变编码这一侧怎么做选择，结果依然是普通容器里的普通计划，现有的读取器就能解开。
   - 包里可以记下彩蛋的名字和版本，作为出处说明，但解码时不读它（AGENTS.md §6.1）。
   - 如果某个彩蛋需要新的解码变换或新的算法，那它就成了格式特性，不再算彩蛋。那要走 ADR，算法接入是 B 级，格式变更是 C 级。
4. **照样确定，照样有界**：
   - 彩蛋算法必须是确定的，每个都有版本号和文档，没有隐藏行为。
   - 可以跑得很慢，但内存和磁盘要有上限，能中断，能报告进度（AGENTS.md §2）。
   - 搜索类的彩蛋把搜到的计划写进包和 `.seed`，以后复现时直接用这份计划，不用再搜一遍。
5. **"找最优"类彩蛋只说在自己的空间里最优**，不承诺全局最优。
6. **最小复杂度**：先把策略种子的主体做完、验收过，再加彩蛋。每个彩蛋一个小函数，用显式分派，不建插件系统。每个彩蛋都要有往返测试和确定性测试。
