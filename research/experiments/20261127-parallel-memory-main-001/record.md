# 并行编码的内存预算（DEV-039）

2026-11-27，主 Agent（Claude），无委派。状态：执行者报告，**未经独立审计**。只测量和起草规则，不改格式，也不改任何默认值。

## 问题

正式 CLI 是否默认并行编码（DEV-035 的 `--jobs`）？要回答这个问题，需要一条确定 worker 数的内存规则：
1. 每多一个 worker，峰值内存增加多少？
2. 能否不靠实测常数，直接从压缩库自己的数据算出来？

## 方法

- **估算**：新增 `solid_encoder_memory(codec, level, size, extreme)`（`core/codec/dictionary.{hpp,cpp}`），表示一次 `compress_solid_codec` 在输入之外要分配的内存，即编码器状态加输出缓冲区。输出缓冲区会先清零，所以全部常驻。
  - **LZMA2**：`lzma_raw_encoder_memusage`，滤镜参数与实际编码相同（同一预设、同样把字典封顶到输入大小）。
  - **Zstd**：按 `compress_solid` 的参数（级别、窗口、不加校验、不开多线程，用稳定缓冲区）建一个真的编码上下文，用 pledged size 加一次 `ZSTD_e_flush` 强制初始化，再读 `ZSTD_sizeof_CCtx`。
    - 没有用 `ZSTD_estimateCCtxSize_usingCCtxParams`：它不会解析 zstd 自动开启的长距离匹配（btopt 及以上、窗口 2^27 时自动开启）；显式开启时，又会用未补默认值的 LDM 参数做除法。zstd 1.5.7 上 `zstd-19 / 128MiB` 因此整数除零崩溃，已复现。
  - **研究命令**：`memory-estimate RECIPE` 输出每个 worker 的内存，即"帧大小 + 编码器 + 输出缓冲区"。
- **实测**：`recipe-pack` 打包 [dup-local-dev-r1](../../datasets/dup-local-dev-r1.md) 的"全部"树（544 740 699 B，16 258 个文件），读出 Windows 的 PeakWorkingSetSize。
  - 32 MiB 分帧（18 帧）：6 个配方 × `--jobs` 1 / 2 / 4 / 8；
  - 128 MiB 分帧（5 帧）：2 个配方 × `--jobs` 1 / 2 / 4；
  - 每组只跑一次，期间机器上没有别的测量任务。
- **环境**：
  - 构建：MSVC Release，工具 SHA 见 [local/commands.txt](local/commands.txt)；
  - 机器：Windows 10，16 个逻辑核，31 GB 内存；zstd 1.5.7（vcpkg 静态库）。
- **原始数据**：[local/](local/)。归档用完即删，SHA 记在 commands.txt 里。

## 测试与构建

- **`research.codec_probe`**：
  - 估算大于帧大小，并随帧大小和级别增大；
  - `zstd-19 / 128MiB` 不崩溃，并包含长距离匹配；
  - 非法配方返回 2。
- **构建**：MSVC 50/50；WSL GCC 51/51；Clang ASan+UBSan 22/22。都是 0 警告，没有 Sanitizer 报告。
- **Linux 上的估算**：LZMA2 与 Windows 完全相同；Zstd 多 8 B（`ZSTD_sizeof_CCtx` 随平台变化）。估算只用于规划，不进入任何格式。

## 结果

斜率是对峰值内存与 worker 数做最小二乘拟合，表示每多一个 worker 增加的内存：

| 配方 | 帧 | 峰值内存（MiB）j1 / j2 / j4 / j8 | 斜率（MiB / worker） | 估算（MiB / worker） | 估算 ÷ 斜率 | 加速 j8（128 MiB 为 j4） |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| Zstd-3 / 32 MiB | 18 | 1223 / 1222 / 1222 / 1278 | 8 | 65 | 7.93 | 1.18× |
| Zstd-9 / 32 MiB | 18 | 1191 / 1191 / 1212 / 1374 | 27 | 75 | 2.74 | 1.50× |
| Zstd-19 / 32 MiB | 18 | 1168 / 1273 / 1498 / 1941 | 111 | 145 | 1.31 | 4.47× |
| LZMA2-6 / 32 MiB | 18 | 1172 / 1295 / 1513 / 2018 | 121 | 157 | 1.30 | 4.22× |
| LZMA2-9 / 32 MiB | 18 | 1410 / 1713 / 2282 / 3329 | 273 | 433 | 1.59 | 4.28× |
| LZMA2-9e / 32 MiB | 18 | 1410 / 1699 / 2358 / 3342 | 276 | 433 | 1.57 | 5.22× |
| Zstd-19 / 128 MiB | 5 | 1305 / 1571 / 2117 / — | 271 | 402 | 1.48 | 2.53× |
| LZMA2-9 / 128 MiB | 5 | 1831 / 2625 / 4227 / — | 799 | 929 | 1.16 | 2.94× |

- **字节不受线程数影响**：每个配方在各个线程数下的归档 SHA 都相同，8 个配方都核对过。
- **估算从不偏低**：8 个配方的估算都不低于实测斜率，比值 1.16–1.59。快速 Zstd（3 / 9）的比值大，是因为它们的峰值不在编码阶段。
- **基础占用约 1.1–1.8 GiB，与线程数无关**。来源有：
  - 研究工具先把整棵树读进内存（约 520 MiB）；
  - 归档本身；
  - 打包后的逐字节校验；
  - 单线程时的那一个编码器。
  
  正式 CLI 应流式读入，这一块会小得多，所以规则把它和每个 worker 的占用分开算。
- **加速**：
  - 慢配方用 8 线程是 4.2–5.2 倍；
  - 快速 Zstd 只有 1.2–1.5 倍，瓶颈不在编码；
  - 128 MiB 分帧只有 5 帧，4 线程时就受帧数限制。

## 规则（用户 2026-11-27 选择"auto, 50% RAM"，见 [ADR-0009](../../../docs/decisions/0009-solid-encode-worker-budget.md)）

```text
W = memory-estimate(配方)          每个 worker：帧 + 编码器 + 输出缓冲区（库给出的估算）
B = 内存预算 − 基础占用              基础占用：读入缓冲区、归档、索引等，与 worker 数无关
jobs = clamp(floor(B / W), 1, min(16, 逻辑核数, 帧数))
```

- 估算只会偏大（实测 1.16–1.6 倍），所以 B 不必再打折扣。
- 1 个 worker 都放不下时仍用 1 个，同时明确报告超出预算，不悄悄降低配方。
- 归档字节与 jobs 无关，所以这条规则只影响速度和内存，不影响确定性，也不需要写进配方或 Seed。

**用户决定**：
- 正式 CLI 默认 `auto`，预算为物理内存的 50%；
- 快速 Zstd 也按同一条规则。

研究工具已实现 `--jobs auto [--memory-budget BYTES]`，自己的默认值仍为 1。`research.solid_recipe` 新增的用例：auto 的字节与固定 worker 数相同；1 B 预算报告 `memory_over_budget`，用 1 个 worker；12 位数的最大预算受帧数或核数限制；非法写法被拒绝。实现之后复测：MSVC 50/50（第一次运行时 solid_recipe 失败，原因是测试里写了 13 位的预算，超过参数解析的 12 位上限；修正测试后通过），WSL GCC 51/51、ASan+UBSan 22/22，均 0 警告。实测示例：cargo 树、LZMA2-9、32 MiB 分帧，预算 16.8 GB，选了 9 个 worker，受帧数限制。

## 限制

- **只测了 Windows**：用的是 PeakWorkingSetSize，没有测 commit charge，也没有测 Linux 的 `ru_maxrss`。估算基于库的分配量，与平台无关，但"估算 ≥ 实测"这个结论只在 Windows 上验证过。
- **只有一棵树**、每组只跑一次；峰值内存受分配器和数据影响，不同数据上的斜率可能不同。
- **Zstd 的估算**会真的建一个编码上下文并初始化（一次约 20–60 ms）。只用于规划，不在每帧调用。
- 基础占用的组成是推断，没有逐项测量。
- CLion 诊断未运行（MCP 连接失败）。
