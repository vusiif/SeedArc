## 问题

用户的标准是"体积、速度、资源三项中两项强"。DEV-044 之后最小的配方 `lzma2-9e-dict256MiB/整体/去重` 体积已胜过 7-Zip 26 与 xz，但它只有一帧，不能并行。本实验回答：

1. 帧切成 32 / 64 / 128 / 256 MiB 时，体积比整体帧大多少，`--jobs auto` 换来多少提速？
2. 在印度 4 vCPU / 5.8 GiB 的机器上，ADR-0009 的 50% 内存预算让大字典配方开几个线程？预算放到 75% 能多开几个？
3. 纯解码时间（不含读源树）和单文件提取随帧大小怎么变？
4. 同字典大小下，7-Zip（-md=256m，单线程 / 默认线程）和 xz（256 MiB 字典单线程；64 MiB 块多线程）处在什么位置？

供下一步"定偏好档"（快档 / 小档的强默认）使用；本实验本身不定默认。

其余三棵树见 [preview.md](preview.md)，趋势相同；要点：

- **小档（单线程、最小）**：SeedArc 整体 dict256 在四棵树上都是最小或并列最小。比同库同字典的 xz 小 0.06–0.38%，xz 用时是它的 0.97–1.16 倍；比 7z 26 档（23.01 + `-md=256m`）小 1.8–4.9%，但 7z 单线程快 1.17–1.38×。
- **快档（4 线程）**：32 MiB 帧拿到 3.3–4.9× 提速，体积代价随树差别很大：append-r1 dev +1.5%，cargo +13%，rustup +16%，全部 +15%。和 xz 的 64 MiB 块多线程同一档（体积互有胜负，−3.4%…+2.4%；SeedArc 用时是它的 0.75–1.10 倍），提取最快（0.04–0.20 s）。
- **中间段是空档**：7z 默认线程用 +1.9–5.1% 的体积换 1.66–2.36× 提速，SeedArc 没有格子同时比它小又比它快。最接近的是 128 MiB 帧 dict128 加 75% 预算（"全部"上 +7.1% / 2.46×；cargo +0.8% / 1.77×；rustup +8.5% / 2.07×）。7z 的多线程几乎不增体积（-mmt1 与默认线程只差 0.03%），说明它的提速不来自切块；liblzma 只有切块式多线程（同 xz -T0），这一长处用现有库吸收不了，属于待查的猜想（可能是匹配查找线程）。
- **内存是这台机器上的瓶颈**：50% 预算下 64 MiB 帧只开 2–3 个线程，128 MiB 以上只开 1 个；放到 75% 后 64 MiB 帧开满 4 个（"全部" 173→112 s），128 MiB 帧开 2 个（343→186 s），实测峰值最高 3 276 MiB，都在预算内。研究工具把输入整份读进内存，预算公式里的"常驻 + 预留"约为输入的两倍（"全部"上约 1.1 GB），流式读入后能直接腾出线程。
- **帧大小不单调**："全部"上 64 MiB 帧比 32 MiB 帧还大 2.0%（另三棵树 64 MiB 小 1.2–2.1%）。DEV-037 已见过只移动帧边界就能差 ±3–5% 的噪声，这里同类；64 MiB 帧不是一个稳定的中间档。体积的大跳变来自字典与帧同时放大到 128 / 256 MiB（rustup：64 MiB 帧 +13.1% → 128 MiB +8.5% → 256 MiB +1.3%）。
- **dict128 与 dict256**（整体帧）：cargo 上 dict128 反而小 0.06%；append-r1 dev / rustup / 全部 dict256 小 0.04% / 1.3% / 0.97%；峰值内存多 763–1 345 MiB，时间多 1–5%。
- **解码偏慢（新发现）**：SeedArc 纯解码（`decode_wall_ms`，不含读源树）"全部"8.0–9.6 s，同一 liblzma 的 xz -dc 3.5 s、7z t 5.2 s；其他树也是 xz 的 2–3 倍。帧大小对解码时间几乎没有影响，所以不是 LZMA 本身，嫌疑在研究工具的解码路径（整包读入、可能的重复解析或 CRC / 比较开销），需要单独剖析。注意 `decode_wall_ms` 含与内存中源树的逐字节比较，但这只是一次 memcmp。
- **单文件提取**：随帧线性：32 MiB 帧 0.04–0.20 s，128 MiB 0.38–1.18 s，256 MiB / 整体 0.39–2.55 s（与 xz、7z 整体固实同档）。

### 结论与限制

- 现在 SeedArc 在"小档"上体积最强、速度与 xz 同档、资源偏高；在"快档"上速度最强（32 MiB 帧 4 线程），体积代价因数据而异（1.5–16%）。中间段被 7z 默认线程占据。
- 对偏好档的启示（不是决定）：小档候选 `lzma2-9e-dict256MiB/整体/去重`；快档候选 `lzma2-9e/32MiB/去重` + auto；中档要么接受 128 MiB 帧 dict128 + 放宽预算，要么先做流式读入降低常驻内存，再复测。
- 限制：每格一次，时间未重复；只有 dev 数据；只在一台 4 vCPU / 6 GB 机器上测，核数更多、内存更大的机器上结论可能不同；SeedArc 的打包时间是进程墙钟（含读树），与外部工具口径一致；7-Zip 是 23.01 + `-md=256m`（DEV-042 证明与 26.00 同字节，未在印度用 26.x 复核）。
