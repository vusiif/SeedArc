# 追加漂移探针：新一代能从旧数据里借回多少

2026-11-26，DEV-028，主Agent（Claude），无委派。状态：执行者报告通过，**未经独立审计**；**只做测量，未改任何格式**。设计与候选见 [append-drift-r0](../../ideas/append-drift-r0.md)，问题来自 DEV-027：Zstd-9 源码类追加 4 次后比重建大约 15%。

## 方法

研究工具新增 `drift-probe OLD_DIR NEW_DIR ZSTD_LEVEL`。它对同一批新文件压缩多种变体，每种都解码回来逐字节比对，并报告以下几项：
- 压缩后字节；
- 需要额外存的字节（字典）；
- 解码一帧时依赖的旧原文字节，以及全部依赖字节；
- 编码时间。

"理想"指旧 + 新一起全量重建的大小，减去只压旧文件的大小，也就是新文件在重建里的边际成本。"差距"是"不参考"超出理想的部分。

各变体：

| 变体 | 做法 |
| --- | --- |
| none | 新文件单独成帧，即现状 |
| dict-112KiB / dict-1024KiB | 用旧文件训练字典，字典大小计入总字节 |
| tail-8 / 32MiB | 以旧数据（按路径拼接）的最后 8 / 32 MiB 作参考前缀 |
| related-8 / 32MiB | 选与新文件共享最深目录的旧文件作参考前缀 |
| *-ldm | 同上，另开 Zstd 长距离匹配 |
| per-group-dN-* | 按前 N 层目录把新文件分组，每组单独成帧，只引用同组旧文件（上限 8 / 32 MiB）；"-none"为不引用的对照，用来单独量分组本身的代价 |

数据用 DEV-023 的两棵树，批次划分同 DEV-027（与压缩结果无关的路径哈希顺序）：
- first-batch：旧 = 第 0 批（约 40%），新 = 第 1 批；
- last-batch：旧 = 第 0–3 批（约 85%），新 = 第 4 批。

级别取 Zstd-3 和 Zstd-9，单 CPU，热缓存。

先在本机用 append-r1 的 dev Linux 小样（旧 20 MB、新 7.6 MB）试跑、调好探针，结果存在 [local-dev-sample-probe.json](local-dev-sample-probe.json)。分组深度和上限的扫描属于探索，不是预登记的取值。

## 结果

源码类（268 MB，新批约 40 MB）：

| 情形 | 差距（none 比理想大） | 最好变体 | 缩小差距 | 新批字节变化 | 单帧最大依赖 |
| --- | ---: | --- | ---: | ---: | ---: |
| first-batch zstd-9 | 14.9% | per-group-d3-32MiB | 52.1% | −6.76% | 31 MiB |
|  |  | per-group-d3-8MiB | 30.5% | −3.95% | 7 MiB |
| last-batch zstd-9 | 18.2% | per-group-d3-32MiB | 45.5% | −7.01% | 31 MiB |
|  |  | per-group-d3-8MiB | 36.9% | −5.68% | 7 MiB |
| first-batch zstd-3 | 12.1% | related-32MiB-ldm | 42.0% | −4.54% | 32 MiB |
|  |  | per-group-d3-32MiB | 6.2% | −0.67% | 31 MiB |
| last-batch zstd-3 | 13.0% | per-group-d3-8MiB | 12.0% | −1.39% | 7 MiB |

文本类的差距本来就小（0.4–5.0%）。Zstd-9 下用相关旧数据作参考能缩小 73–84%，但绝对量只有新批的 1.6–3.8%。Zstd-3 下几乎没有收益。

**观察**：
1. **训练字典全都更差**：源码类新批大 3–21%，文本类最多大 1 倍以上。帧是几十 MB 的大固实帧，字典提供不了多少新信息，还要加上字典本身的体积。A 方案排除。
2. **按目录分组 + 同组旧文件参考，在 Zstd-9 上最有效**：源码类缩小差距 30–52%。单独分组反而让新批大 5.2–5.6%（深度 3），所以收益来自"相关的旧内容就在附近"。深度 3 在两种情形里都最好，深度 2 和 4 都差一些。
3. **Zstd-3 几乎用不上参考**：快档的匹配查找太浅。
4. **长距离匹配不稳定**：有时帮忙，有时更差，不能当固定做法。
5. **本机小样高估了收益**：小样上缩小 64%，全尺寸只有 30–52%。不能拿小样数字直接外推。
6. **编码时间**：新批 Zstd-9 从约 0.9 s 增加到 1.4–1.9 s，主要是复制参考的开销，仍远低于全量重建的约 11 s。

## 解读与限制

**能借回多少**：这种参考结构在 Zstd-9 上，最多能把追加漂移收回约一半。每次追加省下新批约 4–7% 的字节；按 DEV-027 的四次追加推算，最终包比重建大的那 15%，大约能收回一半。

**代价**：提取一个新文件时，要先解码它引用的旧文件。最多 8 或 32 MiB 原文，而且可能分散在多个旧帧里；"单帧最大依赖"只是原文字节数，没有计入要解哪些帧。提取速度、损坏与分卷时的依赖处理都会受影响。这些都还没测，也不能凭这次的数字下结论。

**对照的整理办法**：定期全量重建能把漂移完全清零，源码类约 11 s 一次，而且不增加任何依赖。

**这次只做了测量**：
- 不是 holdout；
- 单 CPU、两类数据、单轮；
- 没有改格式，也没有决定采用哪种做法。

**另需说明一件事**：DEV-026 在本机剖析索引开销时，为了凑够文件数，用了 append-r1 的 dev + holdout Linux 小树（共 8.4k 文件）。那次只测了路径检查耗时，没有根据它调任何压缩参数，但 holdout 数据确实被读过、压过一次，在此如实记录。
