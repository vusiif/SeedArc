# DEV-013：跨文件共享 zstd 字典可行性——test 划分正式评估（唯一一次）

日期：2026-11-13（America/Los_Angeles）。主 Agent 执行（由 B2 协调会话委派）。登记在先：[shared-dictionary-r1](../../ideas/shared-dictionary-r1.md)。参数来自 dev 调参 run [20261113-dict-dev-main-002](../20261113-dict-dev-main-002/record.md) 的 `selection.json`。语料：[b2r5-corpus-r2 修订 2](../../datasets/b2r5-corpus-r2.md)，test 与 dev 的内容哈希交集为 0，运行前自动检查过。**这是 test 划分的唯一一次测量，期间没有重跑。**

## 结论

**带字典的 Zstd-9 在这份 test 划分上有收益**，满足预登记的 H2(a)：三类数据上都比 Fixed LZMA2-6 小，而且压缩墙钟只有它的 0.54–0.60 倍。H1 没有通过，原因是训练时间：字典总能让容器变小，但总耗时超出了无字典的 1.5 倍上限。

| 判定（预登记） | Zstd-3 + 字典 | Zstd-9 + 字典 |
| --- | --- | --- |
| H1：三类都比同级无字典小，且耗时 ≤ 1.5 倍 | 三类都更小（−14.4 % / −21.4 % / −4.2 %），但耗时为 2.48 / 1.45 / 3.30 倍，**不成立** | 三类都更小（−18.2 % / −24.8 % / −7.8 %），但耗时为 2.21 / 1.72 / 2.63 倍，**不成立** |
| H2(a)：耗时 ≤ 1.25 × LZMA2-6，且三类都更小 | source 比 LZMA2-6 大 7.8 %，**不成立** | −17.7 % / −29.4 % / −4.7 %，耗时 0.54 / 0.60 / 0.57 倍，**成立** |
| H2(b)：体积在 ±2 % 内，且耗时 ≤ 0.5 倍 | 不成立 | 不适用（体积明显更小） |

（三个数值依次对应 config-cmake-pkg、many-small-docs、source-python。）

**必须一并说明的混杂因素：** 研究容器的索引比生产格式的索引紧凑（三类合计 174,337 B 对 310,535 B）。把容器索引换成生产索引的大小之后：
- Zstd-9 + 字典 3,134,091 B，仍比 LZMA2-6 小 **12.1 %**；
- Zstd-3 + 字典 3,477,537 B，只小 2.4 %。

时间口径也不完全相同：生产路径包含每块自校验和安全提交，研究容器不包含。好在 Zstd-3 上两者的耗时接近（无字典容器 103 / 323 / 146 ms，对生产 99 / 321 / 183 ms），而 LZMA2-6 的耗时主要花在编码上。所以“比 LZMA2-6 快”这一结论不靠口径差异撑着，但具体倍数只能看作近似值。

## 结果（完整产物字节；时间为 5 次的中位数）

| 方案 | config-cmake-pkg | many-small-docs | source-python | 合计 | 合计压缩墙钟 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| P-zstd3（生产） | 705,404 | 1,337,457 | 1,875,320 | 3,918,181 | 604 |
| P-lzma6（生产） | 639,089 | 1,276,811 | 1,648,080 | 3,563,980 | 2,605 |
| C-nodict-3 | 685,195 | 1,245,302 | 1,853,588 | 3,784,085 | 572 |
| C-dict-3（D=64 KiB，训练用全部输入） | 586,407 | 978,730 | 1,776,202 | 3,341,339 | 1,204 |
| C-nodict-9 | 642,612 | 1,198,465 | 1,702,927 | 3,544,004 | 702 |
| C-dict-9（D=64 KiB，训练用全部输入） | 525,792 | 901,798 | 1,570,303 | **2,997,893** | 1,499 |

- **大小构成**：研究容器 = 头部 32 + 字典 65,536 + 分组表（每个文件 1 B）+ 索引 + 数据，**字典和分组表都计入**，没有当作零。
- **时间构成**：带字典的容器压缩耗时 = 读入 + 训练 + 编码。以 source-python 为例：训练 317 / 407 ms（Zstd-3 / Zstd-9），编码 89 / 221 ms。
- **解压**：研究容器解码到内存约 25–74 ms；生产路径要写出文件，403–1,861 ms，两者不能直接比较。
- **单文件提取**（每个数据集 30 个文件，每次都冷启动：重新读整个文件、解析索引、加载字典，然后解码、比对）：研究容器的中位数 0.58–1.33 ms；生产归档 1.9–7.9 ms，其中读取整个归档就占了大部分。
- **峰值内存**（PeakWorkingSetSize，含工具本身）：带字典压缩 20.8–28.6 MiB，无字典 9.8–16.1 MiB，生产 8.3–10.0 MiB。研究工具会把整个输入读进内存，所以压缩内存**不能**代表流式实现的水平。

## 限制

- 只有一台 Windows 机器、热缓存、5 次重复。test 划分只有三类数据，共 11.6 MB / 2,294 个文件，都是文本类，不能外推到二进制或已压缩数据。
- many-small-docs 的 dev 划分很小（0.78 MB），而 test 有 2.9 MB，选参依据有限。dev 调参中，训练预算选“全部输入”本身就占优；1 MiB 与 4 MiB 两档在这些数据池上差别很小。
- 研究容器不是归档格式：没有流式写出、没有原子提交、没有目录项，校验只解码到内存。生产格式没有任何改动，也不冻结字典格式。
- 训练用的是本次输入本身，字典随产物一起保存。所以“压缩一次、解压多次”的场景最划算；对“一次性小归档”，训练时间占比更高。
- 没有运行：GCC / Clang 下的实验（只做了编译和测试，见 STATUS）、Fuzz、UBSan、非 Windows 平台；固实压缩没有做（列为后续）。
