## 结果

### 体积（字节，单线程；粗体为每棵树最小）

| 配方 / 工具 | append-r1 dev | cargo | rustup | 全部 |
| --- | ---: | ---: | ---: | ---: |
| 输入 | 241 788 546 | 268 434 309 | 257 342 222 | 544 740 699 |
| SeedArc zstd-19 / 32 MiB 帧 | 39 803 077 | 24 086 211 | 57 730 667 | 83 689 536 |
| SeedArc lzma2-9e / 32 MiB 帧 | 37 503 831 | 23 171 178 | 51 240 508 | 76 235 571 |
| SeedArc lzma2-9e / 32 MiB 帧 / 去重 | 36 101 964 | 21 852 175 | 51 181 600 | 74 854 271 |
| SeedArc lzma2-9e / 整体 / 去重 | 35 612 206 | 20 168 897 | **48 727 168** | 70 687 543 |
| tar \| xz -9e | **35 445 856** | **19 539 944** | 48 782 200 | **69 937 464** |
| tar \| zstd -19 | 38 472 228 | 23 578 520 | 60 482 898 | 85 762 990 |
| tar \| zstd -19 --long=27 | 37 764 004 | 19 685 642 | 53 274 352 | 74 747 276 |
| 7z -mx9 | 36 080 089 | 19 789 676 | 50 486 046 | 71 903 675 |
| 7z -mx9 -ms=32m | 37 773 150 | 22 632 829 | 52 404 607 | 76 312 628 |

**两种可以直接比较的情形**：

- **固实块大小相同时（32 MiB）**：SeedArc 的去重配方比 7z `-ms=32m` 小。四棵树依次是 −4.4%、−3.4%、−2.3%、−1.9%。这时 trailer 还没有压缩。
- **整体固实时**：SeedArc 在 rustup 上已经最小。其余三棵树比 tar|xz 大，依次为 +0.47%、+3.2%、+1.07%。

**扣掉 trailer 以后**：用 [DEV-041](../20261128-trailer-probe-main-001/record.md) 估算 trailer 压缩能省下的字节，从整体去重的结果里减去：

| 树 | 整体去重，减去估算 | 对比 tar \| xz -9e |
| --- | ---: | ---: |
| append-r1 dev | 35 407 545 | −0.11% |
| cargo | 19 296 030 | −1.25% |
| rustup | 48 702 542 | −0.16% |
| 全部 | 69 635 615 | −0.43% |

所以，这三棵树上和 tar|xz 的差距**全部来自 trailer 没有压缩**。不过这是估算：DEV-041 量的是 32 MiB 帧的 trailer，整体帧的帧表只少几项，差别可以忽略。ADR-0010 实现之后要实测确认。

### 时间（秒，进程墙钟；tar 流的时间含 Python 写 tar 的时间）

| 配方 / 工具 | append-r1 dev | cargo | rustup | 全部 |
| --- | ---: | ---: | ---: | ---: |
| SeedArc lzma2-9e / 32 MiB / 去重，单线程 | 187.6 | 144.5 | 135.5 | 286.3 |
| 同上，`--jobs auto`（选了 4 个线程） | 65.8 | 47.6 | 43.0 | 90.3 |
| SeedArc lzma2-9e / 整体 / 去重 | 205.5 | 159.6 | 173.5 | 347.7 |
| tar \| xz -9e -T1 | 215.4 | 199.7 | 169.6 | 380.0 |
| tar \| xz -9e -T0 | 204.7 | 175.5 | 166.1 | 363.4 |
| tar \| zstd -19 --long=27 -T1 | 193.0 | 136.4 | 137.2 | 287.7 |
| 7z -mx9 -mmt1 | 166.2 | 134.4 | 141.5 | 298.2 |
| 7z -mx9（默认线程） | 115.9 | 91.8 | 73.5 | 105.9 |

- 单线程时，SeedArc 和 xz、7z 处在同一档。
- 多线程时，SeedArc 的 `--jobs auto` 最快，"全部"树上用了 90 s，7z 用了 106 s。xz -9e 的 `-T0` 几乎不加速：它的块大小是字典的 3 倍，这么大的数据也只切得出几块。
- 但 SeedArc 的多线程结果是 32 MiB 帧的体积，比整体固实大 5.9%。

### 内存（峰值常驻，MiB）

| | append-r1 dev | cargo | rustup | 全部 |
| --- | ---: | ---: | ---: | ---: |
| SeedArc 32 MiB / 去重，单线程 | 846 | 824 | 852 | 1 373 |
| SeedArc 整体 / 去重 | 1 320 | 1 383 | 1 382 | 2 139 |
| SeedArc auto（4 个线程） | 1 576 | 1 673 | 1 791 | 2 214 |
| xz -9e -T1 | 675 | 675 | 675 | 675 |
| 7z -mx9 -mmt1 | 682 | 694 | 679 | 695 |

- SeedArc 的内存明显偏高。原因是研究工具会把整批输入读进内存，这是已知的限制。
- **Linux 上的 `--jobs auto` 内存核对**（ADR-0009 遗留的验证项）：4 棵树都受核数限制，选了 4 个线程。每个线程的估算约 454 MB，实测峰值都在"常驻 + 预留 + 4 × 每线程估算"之内。以"全部"树为例，实测 2 214 MiB，上界约 2 730 MiB。

| 配方 / 工具 | 完整解码，全部 | 提取第 90% 位置的文件：append / cargo / rustup / 全部 |
| --- | ---: | --- |
| SeedArc lzma2-9e / 32 MiB / 去重 | 9.63* | 0.14 / 0.18 / 0.04 / 0.22 |
| SeedArc lzma2-9e / 整体 / 去重 | 10.04* | 0.38 / 1.30 / 2.61 / 1.33 |
| tar \| xz -9e | 3.30 | 0.34 / 1.34 / 2.46 / 1.30 |
| tar \| zstd -19 | 0.74 | 0.17 / 0.80 / 0.64 / 0.83 |
| 7z -mx9 | 5.18 | 0.50 / 2.13 / 3.00 / 1.71 |
| 7z -mx9 -ms=32m | 5.61 | 0.18 / 0.21 / 0.13 / 0.25 |

\* SeedArc 的"完整解码"用的是 `verify`，它还会读入源树逐字节比较，所以时间偏高（规则里已注明），不是纯解码时间。

- 单文件提取时，32 MiB 帧的 SeedArc 和 7z `-ms=32m` 在同一档，都比整体固实快 6–60 倍。
- 整体固实的 SeedArc 和 tar|xz 差不多。

## 差距拆解：其他工具的哪些长处可以吸收

| 来源 | 证据 | 结论 | 可以吸收成什么 |
| --- | --- | --- | --- |
| trailer 未压缩 | 扣掉估算后，整体去重在四棵树上都比 tar\|xz 小 | **这是落后 xz 的主要原因** | [ADR-0010](../../../docs/decisions/0010-compressed-trailer.md)（提议中，待用户决定） |
| 长距离匹配 / 窗口 | cargo 上，zstd-19 加 `--long=27` 从 23.58 MB 降到 19.69 MB（−16.5%）；SeedArc 的 zstd-19 配方是 24.09 MB | Zstd 的窗口大小影响很大 | codec-tree 的 Zstd 槽加 windowLog 和 LDM 两个字段，先在 dev 上测 |
| 固实块大小 | 32 MiB 帧比整体固实大 5.9%（全部）；7z `-ms=32m` 比它的默认设置大 6.1% | 在两个工具上的代价一样，SeedArc 换来的是单文件提取和多线程 | 由偏好档决定：快档或单文件提取档用小帧，小档用整体帧 |
| 可执行文件过滤器（BCJ） | 7z 23.01 在 rustup（二进制多）上为 50.49 MB，比 SeedArc 整体去重（48.73 MB）大；但 26.03 是 46.55 MB，比它小 | 23.01 看不出优势，26.03 有，要和下一行一起查清 | 先查清版本差的原因，再决定 LZMA2 槽是否加过滤器字段；另在 native-bin 树上单独测（本次没有那棵树） |
| 7-Zip 的版本差 | 本机 7-Zip 26.03 比印度的 23.01 小：cargo −4.3%，rustup −7.8%，全部 −6.8%。在 rustup 和全部上，26.03 比 SeedArc 整体去重还小 4.5% / 5.2%（[DEV-040b](../20261128-external-rar-main-001/record.md)） | **本轮最值得追的一项**，原因不明：可能是新版本的编码或过滤器，也可能是平台或元数据的差异。rustup 的差距最大，说明可能和二进制过滤器有关 | 在同一台机器上，用两个版本压同一棵树，再用 `7z l -slt` 对比两边的方法和过滤器 |
| 内存 | SeedArc 1.3–2.2 GB，xz 和 7z 约 0.7 GB | 研究工具整批载入数据 | 流式读入或有界的帧缓冲，这是研究工具已知的限制 |
| 去重 | cargo 上去重使 32 MiB 帧再小 5.7% | 这是 SeedArc 的长处，外部工具都没有 | 保持开启 |

## 结论与限制

- SeedArc 在固实块大小相同时比 7z 23.01 小；在多线程下最快；单文件提取和 7z 的小块模式在同一档。把 trailer 压缩以后，整体固实的配方估计在四棵树上都比 tar|xz 小，最多小 1.25%。
- 但是本机的 7-Zip 26.03 在 rustup 和全部这两棵树上，比 SeedArc 整体去重小约 5%，扣掉 trailer 的估算以后仍然更小。所以"超过 xz"不等于"超过最好的外部工具"，下一步先查清 7-Zip 新版本的长处从哪里来。
- 体积和单文件提取能同时最好，是因为 SeedArc 可以按偏好选择帧的大小。这一点必须由用户按偏好档来取舍，单个配方做不到两样都赢。
- **限制**：
  - 每格只跑了一次，时间没有重复测量。
  - 这只是 dev 数据，不是独立评估，结论不能推广到其他数据。
  - trailer 压缩后的体积是估算。
  - SeedArc 的解码时间包含与源树的比较，偏高。
  - 7-Zip 只测了 23.01 一个版本。
  - 没有 native-bin 树。

**后续（2026-11-28）**：7-Zip 26 比 23.01 小的原因已由 [DEV-042](../20261128-7zip-version-main-001/record.md) 查明。`-mx9` 的默认字典从 64 MiB 改成了 256 MiB；过滤器和平台都不是原因。
