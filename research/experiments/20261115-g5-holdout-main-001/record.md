## 判定（按预先登记的规则，由脚本机械判定）

| 假设 | 结果 | 依据 |
| --- | --- | --- |
| **H0** 往返与确定性 | **成立** | 540 个搜索产物和 9 个起点产物，在工具内重建核对和独立 `verify` 中都逐字节一致；9 个 LZMA2-6 参照都逐字节往返。另外抽 18 格（三个池的合计输入 × 三种方法 × 4× / 16× × 种子 3）重跑，产物逐字节相同。 |
| **H1** 4× 时 coord 中位数比起点小 1 % 以上，至少两个池 | **不成立** | 4× 时三个池都是 0 %，coord 一步也没离开起点。到 8× 时：docs 0 %、source-python −0.25 %、config −1.54 %，也只有一个池达到 1 %。 |
| **H2** Seed 的独立价值，至少两个池 | **不成立** | 三个池、四档预算中，seed 中位数都**不小于** coord（收敛时只多 4 字节 Seed）；达到 coord 最好结果所需的预算也都相同（docs 2×、source-python 8×、config 8×）。 |

**结论**：在 g5-r1 的候选空间（分组规则 × k × 每组 D / T）和预算范围内，**没有发现 Seed 表示加局部变异相对直接坐标搜索的独立价值**；分组与多字典搜索本身相对单个全局字典的收益也很小（合计输入上 0 到 −1.5 %）。这是一个负面结果，照实记录。

## 合计输入的结果（中位数）

| 池（输入字节） | LZMA2-6 | 起点 G-dict-r1 | 起点相对 LZMA2-6：直接 / 折算 | coord 最好中位数（预算） | 相对起点 |

| source-python（5,872,095） | 1,620,668 | 1,436,310 | −11.4 % / −8.4 % | 1,432,662（8×） | −0.25 % |

“折算”的做法：用生产 CLI 的 `--codec store` 对同一份输入打包，取（归档字节 − 输入字节）作为生产格式的头部加索引，用它替换研究容器自己的头部、组表和索引。这是近似值：两种格式的块描述大小不同，生产索引的实际大小也随 codec 有细微差别。

## 两半的观察（不参与判定）

4× 时 seed 中位数比 coord 小的情况：

| 输入 | coord 4× | seed 4× |
| --- | --- | --- |
| docs / local | 0 % | −0.29 % |
| source-python / local | 0 % | −0.57 % |
| source-python / public | −0.12 % | −0.43 % |
| config / public | −0.79 % | −3.65 % |
| docs / public、config / local | 与 coord 相同或更差 | |

8× 起两者基本相同。在较小的输入上（每一半约 1–3 MB），同样的倍数预算能评估的计划更少，随机单字段变异有时比按字段系统尝试更早碰到有改进的分组。但这只是在**不参与判定**的子集上、每格 5 个种子的观察，不构成 Seed 有价值的证据。要检验，必须作为新的假设、换新的留出集重新登记。

## 局限

- 候选空间很小：4 种规则、k ≤ 8、每组 4 种 D、2 种 T，加上按组缓存，使中等预算下几乎能穷举。Seed 的潜在优势在更大、更耦合的空间里才可能显现，本轮无法检验。
- 只有 Zstd 等级 9，块大小 64 KiB，单线程，一台机器；没有比较时间开销（原始计时在 `raw.json`）。
- 起点相对 LZMA2-6 的优势来自共享字典（DEV-013 的结论在新数据上复现了），**不是** G5 搜索带来的。两者用的是不同容器格式，折算值只是近似。
- 本机那一半的数据只在本机评估，不能逐字节复现；公开那一半（Django 6.1.3、vcpkg `fe8e78fa`）可以复现。
- g5-holdout-r1 现在已经用过一次，以后不能再用来调参。
