# 7-Zip 26 比 23.01 小的原因（DEV-042）

2026-11-28，主 Agent（Claude），无委派。状态：执行者报告，**未经独立审计**。只做测量。

## 问题

DEV-040b 发现，本机的 7-Zip 26.03 比印度的 23.01 小 4.3–7.8%。在 rustup 和"全部"两棵树上，它还比 SeedArc 的整体去重配方小约 5%。原因可能有三种：版本里的算法或过滤器、平台差异、默认参数。本实验要分辨是哪一种，并判断 SeedArc 能吸收什么。

## 方法

- **数据**：DEV-040 的 rustup 和 cargo 两棵树。本机这两棵树已经和上传清单逐个文件核对过，见 DEV-040b。未碰留出集。
- **工具**，都在同一台机器上运行：
  - 7-Zip 26.03 x64，Windows 版 `7za`；
  - 7-Zip 26.00，WSL 里的 Ubuntu 26.04 软件包；
  - 7-Zip 23.01：用户 2026-11-27 同意后，从 Ubuntu 官方仓库下载 `7zip_23.01+dfsg-11_amd64.deb`（1 846 156 B）。
    - 包的 SHA256 `0f79450d…` 和印度那份相同；
    - 解出的 `7z` 的 SHA256 `b2a12fa6…` 也和印度相同，所以是同一个二进制。
    - 只解到临时目录里运行，没有安装，用完已删除。
  - xz 5.8.3，WSL 自带。它的 `-9e` 输出和印度 xz 5.8.4 逐字节同大小：rustup 48 782 200 B，cargo 19 539 944 B。
- **格子**：
  - 都用 `-mx9 -mmt1`；
  - 默认设置之外，分别改三项：过滤器（`-mf=off`）、按类型排序（`-mqs=on/off`）、字典（`-md=256m`）；
  - 每个包都用 `7z l -slt` 读出各块实际用的方法；
  - tar 用 external_baseline.py 的 `write_tar` 写出，规则和 DEV-040 相同。
- **脚本**：
  - 仓库外的临时脚本 `z7ablate.py` 和 `z7round2.py`，内容已经抄进本目录的 `commands.md`；
  - 原始数据在 `local/ablate.jsonl` 和 `local/round2.jsonl`。

## 结果（字节）

| 设置 | rustup | cargo | 各块方法 |
| --- | ---: | ---: | --- |
| 7-Zip 23.01 -mx9（印度同款） | 50 486 815 | 19 826 727 | `LZMA2:26`（64 MiB），rustup 有 18 块用了 BCJ2 |
| 23.01 -mx9 -md=256m | **46 553 195** | **18 918 543** | `LZMA2:28`（256 MiB） |
| 7-Zip 26.00 -mx9（WSL） | **46 553 195** | **18 918 543** | `LZMA2:28` |
| 7-Zip 26.03 -mx9（Windows） | 46 553 189 | 18 931 714 | `LZMA2:28` |
| 26.03 -mx9 -mf=off | 44 371 005 | 18 931 714 | 没有 BCJ2 |
| 23.01 -mx9 -md=256m -mf=off | 44 371 010 | 18 918 543 | 没有 BCJ2 |
| 26.03 -mx9 -mqs=on | 46 439 446 | 19 132 166 | |
| tar \| xz -9e（64 MiB 字典） | 48 782 200 | 19 539 944 | |
| tar \| xz preset=9e,dict=256MiB | **44 312 736** | **18 619 240** | |
| SeedArc lzma2-9e / 整体 / 去重（DEV-040） | 48 727 168 | 20 168 897 | 64 MiB 字典 |

1. **版本差距完全来自默认字典。**
   - 23.01 加上 `-md=256m` 以后，和 26.00 **逐字节一样大**。所以 `-mx9` 的默认字典从 64 MiB 变成了 256 MiB，就是全部原因。
   - 压缩算法本身没有变化。平台差异也很小：同一个大版本里，Windows 和 Linux 只差 6 B 和 0.07%。
2. **BCJ2 在 rustup 上反而有害**：关掉过滤器后小了 4.7%。
3. **按类型排序没有用**：rustup 小 0.2%，cargo 大 1.1%。
4. **同一个 liblzma，换成 256 MiB 字典**：xz 在 rustup 上小 9.2%，在 cargo 上小 4.7%，都比 7-Zip 26 的默认结果还小。

## 对 SeedArc 的意义

- SeedArc 的 `lzma2-9e` 用的是预设 9 的 64 MiB 字典，和 xz `-9e` 一样。SeedArc 整体去重的大小本来就和 tar|xz `-9e` 相当。所以只要把字典放大到 256 MiB，按同比例估算，rustup 约为 44.3 MB，cargo 约为 18.6 MB 再减去去重的收益。这样就会比 7-Zip 26 小。
  - **这是估算，没有实测。**SeedArc 现在的配方里不能设字典大小。
- **只对大帧有用**：帧只有 32 MiB 时，比帧还大的字典没有意义。字典要和"整体"帧，或者 ≥ 256 MiB 的帧档配合使用。
- **代价是内存**：LZMA 编码器的内存大约是字典的 10 倍。xz 手册里写着 `-9` 用 64 MiB 字典时约需 674 MiB，按这个比例，256 MiB 字典约需 2.6 GiB。这是推算，要用 `solid_encoder_memory` 实测。这样一来，印度那台 6 GB 的机器上，`--jobs auto` 只能开 1–2 个线程。解码时也要 256 MiB 以上的字典内存。
- **可以吸收**：给 LZMA2 加一个字典字段。它正好对应 codec-tree 想法稿 §3.3 里 LZMA2 槽的 `dict` 字段。改配方的允许集合属于 C 级，按 ADR-0006 要先由用户决定。
- **不用吸收**：BCJ 过滤器和按类型排序，在这批数据上都没有收益。

## 限制

- 每个格子只跑一次；时间来自本机，没有固定 CPU，不作结论。
- 只测了 rustup 和 cargo 两棵树。
- 关于 SeedArc 的数字都是用 xz 推算的，没有实测。
- 7-Zip 是什么时候、为什么改默认字典的，没有查发布说明，本实验只凭测量结果下结论。
