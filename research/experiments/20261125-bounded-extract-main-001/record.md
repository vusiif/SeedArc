## 问题与预登记

DEV-022 / 023 的读取倍率来自 access-profile：每个样本把整包读进内存、解码整帧、校验，不写文件。本轮回答：换成真实的索引式提取，即定位读取、只解到目标文件、安全写盘，原来的优势还剩多少；实际从包里读了多少字节。

配置在测量前保存：[bounded-extract-dev-r0.json](../../configs/bounded-extract-dev-r0.json)，参考 SHA 见 [bounded-extract-reference-r0.json](../../configs/bounded-extract-reference-r0.json)。

- **输入**：DEV-023 的最终树：source 268.4 MB / 11,285 文件，text 81.6 MB / 49 文件。
- **归档**：每类每档 bounded-pack 一次并 verify。SHA 和大小必须与 DEV-023 的全量重建产物完全一致，实际全部一致，说明写入端没有变化。
- **轮次**：4 轮，帧档循环移位，各占一次第 1–4 位；每档两种 profile 都跑，先后顺序逐轮交替。每个 profile 前先读一遍归档，属于热缓存。每类 40 条命令，共 80 条。
- **样本**：两种 profile 都是 12 个均匀路径加最大文件，样本集合相同。
- **检查**：
  - 每次 byte_exact；
  - 每个样本解码量 ≤ 帧上限且 ≥ 请求量；
  - 读取量 ≤ 包大小；
  - 每次 profile 后输出目录为空；
  - 归档在 profile 前后不变。

## 解读与限制

1. **源码类的真实提取收益比诊断更大**：32 MiB 快 3.9–4.4 倍（access 诊断为 3.0 倍），64 MiB 3.0–3.2 倍，128 MiB 约 2.7 倍。每次只读包的 23–61%。原因是不再读整包，帧也只解到目标文件为止；整段档平均要解约 187 MB，32 MiB 档只要约 16 MB。
2. **小帧时索引成了大头**：source 每次提取有约 79 ms 固定花在读取并解析 752 KB 的 trailer（含 11,285 条路径的清单检查），在 32 MiB 档占 121 ms 的约 65%。这是下一步最直接的优化点：索引缓存、分代 / 分帧局部索引，或者不必每次都做的全量清单检查。目前没有实现，也没有测过。
3. **更正 DEV-023 的判断**：DEV-023 中"文本 64 MiB 对整段是支配点"只对内存诊断成立。真实提取时，整段档也只解到目标文件为止，两档的解码量中位都是 24.5 MB，所以 64 MiB 只有 0.93–1.10 倍，落在噪声带内。文本 32 MiB 仍快约 2 倍。text 128 MiB 与整段同 SHA，0.91–1.01 倍就是本机噪声。
4. **整段档的提取也比诊断略快**：source 整段 487 ms 对 491 ms，text 131 对 202。所以"分帧 vs 整段"要拿同一种提取方式比，不能拿真实提取的数字去和 access 诊断比。
5. **写出成本**：text 每次写出 + commit 约 18.6 ms，包含大文件和 SafeOutputDirectory 的大小 / CRC 复读；source 约 2 ms。没有 fsync，不代表断电持久化。
6. **内存**：提取进程的峰值 RSS 包含 extract-profile 为逐字节比对而载入的参考树（source 268 MB），不代表生产提取的内存。解码缓冲最大为"帧内偏移 + 文件大小"。
7. **适用范围**：
   - 只有热缓存，测的是每样本重新打开文件、读索引的延迟，不是冷磁盘延迟；
   - 帧的压缩数据整段读入，没有流式读前缀；
   - 一台机器、四轮、dev 数据，不作 holdout 或统计显著性结论；
   - Seed 与显式表示的载荷相同，收益来自布局和读取方式，不归因于 Seed；
   - 不设默认，不改研究选项表。
