# SeedArc 内存安全、并发与安全解压

> 本文是所有阶段的安全底线。MVP 可以**拒绝未支持的输入 / 文件类型**，但不能在支持的路径上留下已知内存错误、目录逃逸或无界解压。

## 1. 威胁模型与信任边界

- **压缩输入**：普通本地文件和目录；仍须处理读取失败、文件在扫描 / 读取期间变化、符号链接 / junction、巨型文件以及权限变化。
- **归档输入**：一律视为**完全不可信字节流**，包括头部、索引、种子、压缩块、文件名、哈希及扩展字段。
- **第三方库**：成熟压缩库也可能存在漏洞或未定义输入限制；适配层必须校验长度、上下文所有权和返回状态，并持续审计版本。
- **输出目录**：用户原有数据必须受到保护；攻击者可能预建符号链接、junction 或重解析点，也可能并发更改路径。

## 2. C++23 所有权与错误模型

1. C API 仅在 `core/codec/` 调用；第三方上下文由 `std::unique_ptr` + deleter 或专用 RAII 类管理，异常不能越过 C ABI 边界。
2. 优先 `std::vector<std::byte>`、`std::unique_ptr`、`std::span`、固定宽度整数；所有非拥有视图有清晰生命周期。不得持久化指向临时缓冲的 `span`、`string_view`、裸指针。
3. 使用 `std::expected<T, Error>` 等清晰的可恢复错误通道。错误需说明阶段、文件 / 块索引及上游错误（脱敏），不得用裸布尔成功值、吞错或“不可能失败”断言替代处理。
4. 对 `uint64_t` / `size_t` 转换、长度加法、长度乘法、偏移加长度、数组索引、缓冲区扩大执行 checked arithmetic；**先核验，后分配 / 读写**。
5. 不根据不可信头部一次性分配声称的解压长度。使用有界分块 / 流式接口，校验单块输出、整体输出、文件数量、路径长度、索引数量、内存与必要的运行预算。
6. 完整性校验失败时必须报错，不能将部分解压数据作为完整文件输出；普通哈希 / checksum 不等同于认证加密。
7. 一切新压缩 / 解压路径必须测试空输入、极短输入、超大长度、截断、错误字典、已压缩随机数据与编码器失败。

建议边界形态（**概念接口，不是被冻结的 API**）：

```cpp
struct CodecError {
    int code{};
    std::string message;
};

// 使用 span 限定无所有权输入、使用明确的资源限额；
// 大数据最终应支持有界流式 API。
std::expected<std::vector<std::byte>, CodecError>
compress(std::span<const std::byte> input, const CodecOptions& options);
```

接口公开前应先看 `archive-format.md` 的最大块大小与预算，再确定缓冲策略；不因抽象“通用性”被迫全量复制数据。

## 3. Windows 安全解压

默认仅支持**普通文件与目录**，禁止未经明确定义的链接、设备和重解析点恢复。尤其应检查：

| 攻击面 | 基本策略 |
| --- | --- |
| `..` / 绝对路径 / 盘符相对路径 / UNC / `\\?\` | 只允许已验证的归档相对路径；拒绝任何可能逃逸的表示；不能靠字符串前缀测试路径是否安全 |
| ADS（如 `file:stream`）与设备名 | 拒绝冒号 / ADS、保留设备名、NUL、非法格式、尾随空格 / 点等 Windows 歧义路径 |
| 大小写 / Unicode 冲突 | 处理大小写不敏感目标上的重复条目、规范化碰撞及同一文件不同名称；冲突默认拒绝 |
| symlink / junction / reparse point | 不跟随未经授权的重解析点；不能只检查归档名而忽视磁盘上已存在的目录链接 |
| TOCTOU（检查和创建间竞态） | 需要时使用 Windows 句柄级 / 不跟随策略及安全的创建流程；不能认为 `weakly_canonical` 检查就解决竞态 |
| 覆盖已有用户文件 | 默认拒绝覆盖；明确冲突处理与失败回滚，不破坏既有有效数据 |
| 压缩炸弹与索引攻击 | 输出 / 块 / 文件数 / 路径 / 内存 / 字典上限与可取消性；拒绝异常膨胀 |

细节实现必须根据实际 Windows API 能力设计与测试。若现有库 / API 无法满足当前安全要求，**首先提出补齐工具、SDK 或改用经验证安全流程的方案**，不能隐式放松检查。如果首版不支持重解析点 / 链接，必须**安全拒绝**，而不是尝试复制其目标内容。

### 输入与输出的约束差异

压缩阶段读取目录也需要限制链接追踪和枚举变化，避免把意外目录打入归档；但解压阶段处理**恶意构造归档**，必须对每个内部路径及输出写入保持独立安全校验。不要将“压缩器只读可信文件”的假设传播给解压器。

## 4. 写入、取消与故障恢复

- 归档或解压文件写入优先临时文件 + 校验 + 安全提交；考虑 Windows 文件锁、同卷原子替换约束、磁盘已满和中断。
- 失败 / 取消时清理临时文件，不留“成功命名”但缺块或校验失败的产物。清理不得意外删除用户已存在文件。
- 已存在文件默认不覆盖；后续显式覆盖功能必须设计备份、权限、原子性和回滚规则，并按高风险权限确认。

## 5. 多线程和共享状态

- 不共享未经验证为线程安全的编码器上下文；并行任务持有独立上下文、明确其生命周期。
- 任务取消和错误传播需覆盖各工作线程，提交顺序必须独立于执行完成顺序，以满足确定性。
- 搜索结果缓存的键必须包含输入内容 / 身份、编码器及版本、参数、字典、分块规则与其他影响输出的条件；互斥 / 原子提交要有测试。
- 内存预算基于**并行任务累计消耗**，而不是仅按单个块估算。

## 6. 证明要求

- 工具链支持时运行 AddressSanitizer 与合适的动态分析；静态分析、编译警告和审查不能替代运行测试。
- 至少构建路径穿越、ADS、保留名、重复文件、junction / symlink、畸形索引、溢出及解压炸弹的负面案例。
- Fuzz 的覆盖边界和阶段验收见 `testing.md`；未运行就不能宣称完成模糊测试或通过不可信输入安全审计。

**默认处置策略**：未实现的特性 → **明确报错并拒绝**；未知或无法安全处理的归档 → **不写出文件并报错**；安全要求必需的工具缺失 → **报告安装方案并阻塞该功能验收**。
