# ADR-0006：Seed 配方 r1（固实路径）

状态：**用户已确认（2026-11-25）；研究工具中已实现并通过 MSVC 47/47、Linux GCC 48/48、Clang ASan+UBSan 相关 6/6，均 0 警告；未经独立审计，未进入正式格式**。日期：2026-11-25。起草：主Agent（Claude）。决定人：用户，§6 三项均选推荐方案（原话"按照推荐来吧"）。格式仍为 experimental、未冻结；本 ADR 只授权在研究工具中实现映射修订 3，不改正式归档格式。

输入：
- 用户 2026-11-25 对 Seed 的定位（[user-vision §4](../user-vision.md#4-seed-应承担什么作用)）：Seed 是表示工具，让人知道自己在用什么压缩，并固定这种压缩方式；它是重要特征，不是全部。
- 现有实现：[solid_plan.hpp](../../research/tools/solid_plan.hpp)（solid-plan-r1，映射修订 2）、[有界固实](../../research/ideas/bounded-solid-r0.md)、DEV-021–024 实验。
- 约束：[设计探索 §8](../../research/ideas/seed-design-study.md#8-为后续修改保留的实现边界)：表示、语义与映射分开；改语义要用新修订；旧种子不重新解释。

## 1. 问题：现在的 Seed 说不全实际配方

修订 5 固实包的 GEN 记录里，每代存一个 32 位值。按现行映射修订 2，这个值只编码：

- 分组规则（2 bit）；
- 组数 k−1（3 bit）。

实际决定压缩结果的另外几项都不在 Seed 里：

| 配方项 | 现在在哪里 | 用户能否从 Seed 看出 |
| --- | --- | --- |
| 分组规则、组数 | Seed | 能 |
| 压缩算法 / 级别 | 代码写死 Zstd-9；头部 `level` 字段固定 | 不能（隐含） |
| 帧上限（整段 / 32 / 64 / 128 MiB） | 写入命令的单独参数，包里没有记录 | 不能 |
| 冗余级别 | 头部；修订 5 只允许 off | 不在 Seed |

所以同一个 Seed `0x0`，既可能是整段固实，也可能是 32 MiB 分帧。按用户的定位，这个标签不完整。

## 2. 决定（候选）：配方修订 r1

### 2.1 Seed 描述什么

一个**配方**（Recipe）是一组写入策略，Seed 是它的紧凑表示：

| 字段 | 取值（r1 允许集） | 说明 |
| --- | --- | --- |
| 布局 | 固实 | 本 ADR 只覆盖固实路径；块模式沿用旧映射 |
| 分组规则 / 组数 | 与修订 2 相同：rule 0–3，k 1–8 | 不改语义 |
| 帧上限 | 整段（≤ 1 GiB）、16、32、64、128、256 MiB | 3 bit 编码，见 §2.3 |
| 压缩算法 | Zstd（码 0）、LZMA2（码 1） | 2 bit；码 2–3 保留并拒绝 |
| 级别 | Zstd 1–19；LZMA2 预设 0–9 | 5 bit；范围外拒绝 |

**允许集扩大（2026-11-25）**：最初 r1 只接受 Zstd-9。用户同日指示"你先做234吧"，即先做多算法 / 级别对照，没有逐档指定。Agent 按 codec 层已支持的完整范围扩大允许集：Zstd 1–19、LZMA2 预设 0–9（raw LZMA2，字典不超过输入大小，必须有结束标记）。扩大只是把原先非法的值变成合法，已合法的 Seed 含义不变，修订号仍为 3。可读文本写作 `zstd-<级别>` / `lzma2-<预设>`。

Seed **不**描述：文件清单、实际帧边界（由配方和文件顺序确定性推出）、索引、校验、冗余、字典内容。解码仍以包内显式记录为准，Seed 不替代任何解码所需信息（AGENTS.md §6.1）。

### 2.2 两种表示，同一个配方

- **Seed 值**：32 位整数，GEN 记录里以映射修订 3（"solid-recipe-r1"）存放。
- **可读文本**：规范写法 `solid/zstd-9/g<k>-r<rule>/frame-<上限>`，例如 `solid/zstd-9/g1-r0/frame-32MiB`。CLI 两种都接受，输出两种都打印。

显式表示（explicit）保留，作为同算子对照，与 Seed 映射到同一个 Recipe 结构，载荷必须逐字节相同（沿用 payload-compare）。

### 2.3 位布局（候选）

```text
bit  0–1   分组规则 rule
bit  2–4   组数 k−1
bit  5–7   帧上限码：0 = 整段，1 = 16 MiB，2 = 32 MiB，3 = 64 MiB，4 = 128 MiB，5 = 256 MiB，6–7 保留
bit  8–9   算法码：0 = Zstd，1 = LZMA2，2–3 保留
bit 10–14  级别：Zstd 1–19，LZMA2 预设 0–9
bit 15–31  必须为 0
```

这样设计的原因：
- 低 5 bit 与修订 2 完全相同，整段、Zstd-9 时数值也相同（`0x0`、`0x4`…），便于对照；但它们属于不同修订，不能互换解读；
- 新增值只把原来非法的取值变成合法，不改变任何已合法 Seed 的含义；
- 帧上限只给几档，而不是任意字节数。研究里实际用到的就是这几档，任意值既不可读，也会让配方空间失去意义。

### 2.4 标签必须真实

读包时要核对包的实际内容与配方相符，不符则拒绝（fail closed）。这样"让人知道自己在用什么压缩"才靠得住：

- **帧边界**：按配方的分组与帧上限，从文件顺序用写入端的同一贪心规则重算帧划分，必须与帧表完全一致。
- **算法**：帧必须是对应算法的有效帧。
- **级别**：从 Zstd 输出无法验证级别，只能靠重新压缩比对，代价高。r1 把级别标为"声明值"：`describe` 明确写出"级别未从数据验证"，不冒充已核实。

### 2.5 分代

- 每代有自己的配方（沿用"分代是队列"的思路）。追加的新一代可以沿用旧配方，也可以换帧上限。
- 旧代按自己的修订解释，新修订不重新解释旧代。
- 修订 2 的旧代和修订 3 的新代可以出现在同一个包里。

### 2.6 `describe` 命令

新增 `describe ARCHIVE`，按代输出：
- Seed 值、可读文本、映射修订；
- 帧数、最大帧原文字节；
- 核对结果：帧边界已核对，级别为声明值。

旧修订 2 的代按其真实含义描述为"Zstd-9，帧上限未记录"，不猜测当时用了哪档。

## 3. 不做 / 留待后续

- 不改块模式（v4 非固实）的旧映射。
- 不把冗余、分卷、恢复记录放进 r1 配方；等它们在修订 5+ 路径上实现后再定。
- 只支持 Zstd 和 LZMA2；Brotli、LZ4 等以后再说，用保留的算法码 2–3。
- 不做任意长度的 Seed 或 TLV 框架（设计探索 §8）。
- 不冻结长期格式。

## 4. 兼容与风险

- **旧包**：修订 2 的包照旧可读、照旧描述；新工具不改写旧包。
- **旧工具**：遇到映射修订 3 会拒绝（现在的 `parse_gen_body` 只接受修订 2），属于预期的明确拒绝，不会误读。
- **位布局一旦有正式数据就难改**：所以先以研究工具实现，用 DEV 数据验证后再考虑进入正式路径。
- **帧边界核对**：要求写入端贪心规则固定、可复现。规则改变就是新修订。

## 5. 验收（实现时）

- 每个允许集取值往返：Seed ↔ 可读文本 ↔ Recipe；保留位或非法取值全部拒绝。
- 修订 3 包与对应显式表示载荷逐字节相同；整段配方的载荷与修订 2 相同。
- 篡改帧表或帧上限使其与配方不符时，读包拒绝。
- 修订 2 / 3 混合分代可读；`describe` 对两种修订输出正确。
- MSVC、Linux GCC、ASan+UBSan 全部通过，0 警告；跨平台固定小包 SHA 一致。

## 5.1 实现（2026-11-25，研究工具）

- **编码**：[solid_plan.hpp](../../research/tools/solid_plan.hpp) 定义 `SolidRecipe` / `RecipeFields`，包括：
  - Seed 值编解码（§2.3 位布局）；
  - 显式两字描述符（布局 ID 2；一字放 rule / k / level，一字放帧档 / 算法）；
  - 规范文本 `recipe_text`，以及 `parse_recipe`（文本或 `0x` Seed）。
- **GEN 记录**：Seed 表示用修订号 3、长度 4；显式表示用修订号 0、长度 8。修订 2 和长度 4 的旧显式记录照旧解读。
- **读取核对**：`parse_index()` 对每个配方代调用 `check_recipe_frames()`，用写入端同一贪心规则重算帧划分，帧表或文件位置不符即拒绝。全量解析、索引式提取、describe 都经过这一步。
- **命令**：
  - `recipe-pack seed|explicit RECIPE IN OUT`；
  - `recipe-append OLD NEW OUT [RECIPE]`：不给 RECIPE 时沿用最后一代的配方；给了就新建一代，用新的分组和配方；
  - `describe ARCHIVE`。
- **旧命令**：`bounded-pack` / `bounded-append` 仍写修订 2，字节不变。在配方代后面用 `bounded-append` 时，帧上限必须等于最后一代的配方，否则拒绝。
- **测试**：`research.solid_recipe` 覆盖：
  - 6 档 × 2 种分组 × 2 种表示往返，Seed / 显式载荷相同；
  - Seed 值与文本等价；整段配方载荷等于修订 2；
  - 21 MiB 输入被 16 MiB 档切成 2 帧；把整段包和 16 MiB 包互换标签、修好 CRC 后，verify / describe / extract 都以"不符合配方"拒绝；
  - 沿用 / 更换配方、修订 2 / 3 混合分代、显式包追加；
  - 非法级别、帧档、组数、保留位、算法码一律拒绝，被拒绝的命令不留输出。

## 6. 用户的选择（2026-11-25 已确认）

1. 帧上限只允许几档：整段 / 16 / 32 / 64 / 128 / 256 MiB，不用任意字节数。
2. 算法 / 级别字段现在就放进 Seed；r1 只允许 Zstd-9。
3. 读包时严格核对帧边界与配方一致，不符即拒绝。
