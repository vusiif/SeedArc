状态：**已接受（用户 2026-11-27 选择"Accept, implement"，全部按推荐：别名条目、同代同组、保持原帧、Seed bit 16，整帧配方也允许 dedup）**；实现见 §7。日期：2026-11-27。起草：主 Agent（Claude）。决定人：用户。

本 ADR 修订 [ADR-0006](0006-seed-solid-recipe.md) 的允许集、位布局和帧核对规则（§2.1、§2.3、§2.4），在 [ADR-0007](0007-recipe-lzma2-extreme.md) 之上再加 1 位；ADR-0006 的其他内容不变。格式仍为 experimental、未冻结，只在研究工具中实现，不改正式归档格式。按 AGENTS.md 第 3 节，改配方允许集属于 C 级，需要用户明确接受。

## 输入

- **DEV-036**（[记录](../../research/experiments/20261127-dup-probe-main-001/record.md)）：
  - 整文件重复在包缓存和工具链目录里很常见：字节占比 cargo 11%、npm 10%、rustup 3%、MinGW 工具链 39%；
  - 32 MiB 分帧、保持原帧边界、只删副本时，帧字节在每棵树上都只减不增：cargo −5.8–6.0%，append-r1 dev −3.8–4.0%，三池合计 −1.7–1.8%，native-bin −23%，无重复的树 0；
  - 去重后按剩余文件重新切帧，合计树反而 +1.2–1.7%。原因是帧边界整体移动了，不是去重本身。
- **DEV-037**（[记录](../../research/experiments/20261127-frame-cut-main-001/record.md)）：只平移帧边界，体积就会变化 −3.5%…+5.5%。简单的切点规则都不稳定，没有采用。
- 用户 2026-11-27 的选择："Do dedup first"。

## 1. 问题

有界固实把文件按路径顺序装进最多 L 字节的帧，每帧独立压缩。同一内容的第二份副本如果落在另一帧，编码器看不见原件，只能再存一遍。即使在同一帧里，副本也占帧容量。

## 2. 决定（候选）

### 2.1 怎样表示副本：别名条目（推荐，不加新字段）

研究容器修订 5 的固实条目本来就有 `(frame, frame_offset, size, file_crc)`。副本条目直接指向原件所在的帧和偏移，四个字段与原件相同，自己不占帧字节。

- **零额外元数据**：条目长度不变，trailer 不加新记录。
- **提取不变**：读帧、按偏移截取、核对 CRC。指向别处的条目，现有的读取和边界检查已经能处理。
- **单文件提取的代价**：副本的代价等于原件的代价，需要解原件所在的帧。

备选是新增"引用第 i 个条目"的字段，不推荐：要改条目格式，而且提取还要多一层间接。

### 2.2 去重范围

| 选项 | 做法 | 推荐 |
| --- | --- | --- |
| **同代、同组** | 只在同一代、同一分组内找原件 | **推荐** |
| 跨代 | 追加的新一代可以指向旧代的帧 | 暂不做 |
| 跨组 | 不同分组之间也去重 | 不做 |

推荐只在同代同组内去重，原因：
- **跨代**：读取器现在要求条目所在帧属于同一代（`solid entry outside its frame`）。放开以后，新代会依赖旧代的数据，分代恢复和"只读新一代"都要重新设计；合并时也要重新安排。这部分收益（重复追加同样的文件）还没有测过。
- **跨组**：读取器要求条目的分组等于它所在帧的分组，而且分组由路径规则决定（`g<k>`）。跨组的副本必须放宽这条核对，收益只在 k > 1 时才有，而且很小。

### 2.3 判定规则（确定性）

- 在一代内按条目顺序（即路径顺序）处理。一个非空文件，如果在它之前有同组文件与它**逐字节相同**，它就是副本，指向第一次出现的那一份。
- 先按（大小，CRC32C）分桶，再逐字节比较。只比哈希不算相同。
- 空文件不去重，照旧处理。

### 2.4 帧边界：保持原帧（推荐）

| 选项 | 做法 | 实测（32 MiB，三池合计） |
| --- | --- | --- |
| **A. 保持原帧** | greedy 照常对全部文件累计大小，副本也计入预算，但不写入帧字节 | Zstd-19 −1.72%，LZMA2-9e −1.84%；每棵树都只减不增 |
| B. 重新切帧 | greedy 只对非副本文件累计 | Zstd-19 +1.65%，LZMA2-9e +1.22%；其他树上比 A 稍好或相近 |

推荐 A：
- 实测中每棵树都没有变大；
- 每个帧的内容是不去重时该帧内容的子序列，帧数不变，与同一配方不去重时的结果直接可比；
- B 的问题出在切点对边界敏感（DEV-037），不是去重本身。

A 的代价是帧可能装不满，例如 native-bin 上本来可以少一帧。

`check_recipe_frames` 相应修改：
- 对全部条目累计"预算字节"，帧边界仍按 greedy 判定；
- 只有非副本条目累计"实际字节"，并且必须顺序排列，与帧的 `raw` 一致；
- 副本条目必须指向本代、本组中更早的一个非副本条目，并且 `(frame, frame_offset, size, file_crc)` 完全相同。

### 2.5 Seed 与可读文本（沿用 ADR-0007 的做法）

```text
Seed bit  0–15  与 ADR-0007 相同
Seed bit  16    dedup：1 = 同代同组整文件去重（§2.3），帧边界按 §2.4 A
Seed bit  17–31 必须为 0
```

- **显式两字描述符**：第二字的 bit 17 作为 dedup 标志，bit 18–31 必须为 0。
- **可读文本**：在末尾加 `/dedup`，例如 `solid/lzma2-9e/g1-r0/frame-32MiB/dedup`。只有这一种拼写。
- **映射修订仍为 3**：只是把原先非法的值变成合法，已有的合法 Seed 含义不变；旧工具会按非法值拒绝 bit 16 = 1，属于明确拒绝。
- **整帧配方**：`frame-whole` 也允许 dedup，但实测几乎没有收益（0.02–0.84%）。是否允许请用户定，推荐允许，保持各字段正交。
- **`describe`**：可以从元数据直接验证别名是否符合 §2.4 的结构，所以列为"已核对的结构"。至于"是否去掉了全部副本"，要解码比较内容才能确认，列为声明值。

### 2.6 不是配方的固实代

不是配方生成的固实代（修订 2 的 Zstd 9）不去重。现有读取器对这些代只检查边界，不检查顺序排列，所以理论上已经能读别名。这一点保持不变，不放宽也不收紧，实现时补一个测试把行为固定下来。

## 3. 不做

- 跨代、跨组去重；近似重复和块级去重；
- 按内容选切点（DEV-037 没有通过）；
- 正式归档格式的改动；
- 修订 5 的分卷和恢复（这两项本来就没有实现）。

## 4. 兼容与风险

- **兼容**：不带 dedup 位的配方，归档字节与现在完全相同。带 dedup 位的归档，旧工具会明确拒绝，不会误读。
- **损坏影响**：跨帧的副本原来有自己的一份数据，现在依赖原件所在的帧。那一帧坏了，原件和全部副本都读不出来。修订 5 本来就没有恢复功能，这里只记为已知代价。以后如果做恢复，要报告受影响的副本。
- **资源**：判重需要比较内容。研究工具现在是整树读进内存，比较不另外增加内存；以后改成流式时，需要为"待比较的原件"定读回上限。
- **合并（consolidate）**：合并会把全部文件重新写成一代，按 §2.3 重新判定副本。原来分在不同代里的重复，合并后可以被去掉。

## 5. 验收（实现时）

- **答案已知的测试**：同帧副本、跨帧副本、空文件、不同组的相同内容（不去重）、副本链（第三份指向第一份）。
- **往返**：pack、append、consolidate、单文件提取、describe，都要逐字节一致。
- **拒绝用例**：
  - 别名指向后面的条目、别的代或别的组；
  - 别名与目标的四个字段不一致；
  - 没有 dedup 位却出现别名（配方代）；
  - 有 dedup 位，但非副本条目不是顺序排列；
  - Seed bit 17–31、显式第二字 bit 18–31 非 0。
- **确定性**：
  - 固定的小包，MSVC 与 GCC 的 SHA256 相同；
  - 不同 `--jobs` 产生相同的字节；
  - 帧字节总数必须等于 DEV-036 的 `dedup_same_cut`（同树、同配方）。
- **工具**：Fuzz 语料加入 dedup 样例，ASan + UBSan 回放；MSVC / GCC 0 警告。
