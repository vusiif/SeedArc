# ADR-0010：研究容器的 trailer 压缩存放

状态：**已接受**（用户 2026-11-28："接受 ADR-0010，开始实现"，即方案 A：zstd-19，用标志位标记，新归档默认压缩；方案 D 前缀编码不做），已在研究工具中实现，见 [DEV-044](../../research/experiments/20261128-zstd-trailer-main-001/record.md)。日期：2026-11-28。起草：主 Agent（Claude）。决定人：用户。

本 ADR 改的是研究容器（修订 5）的存储方式：trailer 改为压缩存放。它不改配方、Seed 或帧数据，只在研究工具中实现，正式归档格式不变。改容器的读写契约，按 AGENTS.md 第 3 节属于 C 级，需要用户明确接受。

## 输入

- **DEV-040 冒烟测试**（npm 树，1 087 个文件）：
  - SeedArc 的帧数据为 1 636 430 B，比整个 `tar | xz -9e`（1 659 804 B）还小；
  - 但 trailer 原样存放，有 77 111 B，结果整包大了 3.2%。
- **DEV-041**（[记录](../../research/experiments/20261128-trailer-probe-main-001/record.md)）：
  - trailer 平均每个文件 71–109 B，可以压缩到原来的 1/4.4–1/5.4；
  - 以 DEV-038 的 LZMA2-9e 去重归档为基准，整包可再小：cargo −4.0%，npm −3.5%，全部 −1.4%，append-r1 dev −0.6%，rustup −0.05%。

## 1. 问题

trailer 是整个归档的索引，内容依次是：头部 CRC、每代的记录、（显式分组时的）组号、每个文件的路径和定长字段、帧表。

现在它不经压缩直接写在文件末尾。路径占了大部分，而相邻路径大多有相同的前缀，冗余很大。tar.xz 和 7z 的文件头则会和内容一起被压缩。所以文件越多越碎，SeedArc 在元数据上吃的亏就越大。

## 2. 决定（候选）

### 2.1 怎样压缩（推荐 A）

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 整个 trailer 用 zstd-19 压缩** | footer 仍指向 trailer，存的是压缩后的字节；另记原始长度 | **推荐**：比 LZMA 只大 2–4%，解码快得多。打开归档必须先读 trailer，解码速度直接影响单文件提取的延迟 |
| B. 用 LZMA-9e | 同上 | 最小，但每次打开都要多花一些解码时间 |
| C. 只对路径做前缀编码，不用通用算法 | 每条路径只存与上一条不同的后缀 | 不依赖压缩库，但收益只有 A 的一部分，而且要自己写编解码，容易出错 |
| D. 前缀编码之后再用 zstd | C + A | 可能再小一点，但更复杂；先做 A，测过后再考虑 |

### 2.2 怎样标记

- 头部新增一个标志位 `flag_compressed_trailer`（bit 2）。
  - 现有读取器只接受 bit 0–1，遇到 bit 2 会报 `bad header`，属于明确拒绝，不会把压缩数据当成原始 trailer 来读。
  - 容器修订号仍为 5，这样不用改动现有代码里大量 `revision == 5` 的分支。
- 标志位置 1 时，trailer 区域为 `原始长度（8 字节） | zstd 帧`。
  - footer 的 CRC 覆盖整个存储区域（即压缩后的字节）；
  - 解码之后再按现有的规则解析，条目和帧表的检查全都不变。

### 2.3 安全与资源

- **先查长度再分配**：原始长度必须 ≤ 一个固定上限，例如 `max_files ×（最长路径 + 定长字段）`再加每代记录的上限，超过就拒绝。必须先检查，再分配内存。
- **解码要求精确**：只接受恰好一个 zstd 帧，不允许带字典；帧头里的内容大小必须等于记录的原始长度；窗口有上限；后面不能有多余字节。做法和 `decompress_solid` 一样。
- **确定性**：zstd-19，不加校验和，记录内容大小。同一版本的 zstd 在各个平台上输出相同；跨 zstd 版本的字节一致，和帧数据一样不做承诺。

### 2.4 追加与合并

- 追加时，新一代照常写一份新的完整 trailer，也是压缩的。旧 trailer 留作 `stale_trailers`，大小因此同样变小。
- 追加和合并时，压缩方式沿用原归档：原归档压缩了，新写的也压缩；原归档没有压缩，就保持不压缩。这样不会一个归档里混用两种形式。另外提供一个显式的选项，用来把老归档转换成压缩形式。

### 2.5 写入时默认开启

新写的修订 5 归档默认压缩 trailer。现有的固定小包、fuzz 语料和测试里使用未压缩 trailer 的部分保留不动，继续作为回归用例。

## 3. 不做

- 不压缩各代的记录（GEN 记录本身很小）；
- 不把 trailer 拆分成可以随机访问的块，以后文件数大到解码 trailer 本身变慢时再考虑；
- 不改正式归档格式。

## 4. 兼容与风险

- **旧归档**：未压缩的 trailer 照常能读。新写的归档，旧工具会明确拒绝。
- **打开代价**：每次打开都要解压 trailer，"全部"树约 1.3 MB，用 zstd 只需几毫秒，对单文件提取影响很小。实现时要实测确认。
- **损坏影响**：trailer 压缩以后，坏一个字节就可能导致整个索引都解不出来。原来坏一个字节也会让 CRC 失败、整个 trailer 被拒绝，所以影响范围其实一样。修订 5 本来就没有恢复功能。

## 5. 验收（实现时）

- 往返：pack、append、consolidate、extract、describe 都逐字节一致；新写的归档带 bit 2。
- 大小：在 DEV-041 的 5 棵树上，整包缩小量与估算一致（误差在记录头那几十字节以内）。
- 拒绝：
  - 原始长度超上限、帧头里的内容大小与原始长度不符、多帧、带字典、帧后有多余字节；
  - bit 3 及以上的标志位。
- 兼容：现有的未压缩小包和 fuzz 语料全部照常通过；固定小包 GCC 与 MSVC 的 SHA 相同。
- Fuzz：加入压缩 trailer 的样本，跑 ASan + UBSan。

## 6. 需要用户决定

1. 是否接受：方案 A（zstd-19），用标志位标记，新归档默认压缩。
2. 是否同时做前缀编码（方案 D）。推荐先不做，等方案 A 测完再定。

## 7. 实现记录（2026-11-28，DEV-044）

- 按 §2 实现。补充下面几项细节：
  - **原始长度的上限是 256 MiB**，和只读索引时原有的 trailer 上限相同；fuzz 构建里降到 16 MiB。
  - **转换命令用 `trailer-recode`，只接受单代归档**：多代归档里旧的 trailer 保持当初写入时的形式，如果只改最后一个，同一个归档里就会混用两种形式。多代归档要换形式，用 `consolidate --trailer`。
  - **最前面的选项 `--trailer raw|zstd`**：只决定新写的修订 5 归档用哪种形式；追加时如果给出和原归档相反的形式，拒绝执行。
- **验收**：
  - 整包节省和 DEV-041 的估算一致，误差不超过 38 B；
  - 打开索引没有变慢；
  - 9 种存储故障都被拒绝；
  - 带字典 ID 的帧没有单独做故障用例，由共用的 `decompress_solid` 检查拒绝。
- **对既有测试的影响**：retag / realias 夹具要直接改 trailer 里的字节，所以它们的源包改为用 `--trailer raw` 打包；solid_search 里比较 Seed 和显式表示大小的那一项，也改用 raw 形式。
