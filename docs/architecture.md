# SeedArc 架构与阶段路线

> 状态：**设计指导，尚非实现快照**。本文由项目 v0.2 构想和后续命名 / Agent 治理要求整理；具体参数与公开格式必须以已确认 ADR 为准。

## 1. 项目定位

**SeedArc — Seed-Driven Adaptive Compression**：面向文件与文件夹的实验性混合压缩系统。以 C++23 集成可靠的现有 C / C++ 压缩库，通过**可版本化的种子驱动策略生成器**决定分块、编码器及参数，在相同预算下实验搜索是否改善最终完整归档体积。

- 衡量的是**完整归档字节数**：文件索引、种子、元数据、字典、块头和校验均计入。
- 种子是压缩策略的紧凑表达，不是文件数据、口令或加密密钥。
- 先实现稳定的压缩 → 解压 → 验证闭环，再研究搜索与高级压缩策略。**不得预设种子搜索一定优于单算法或逐块择优。**
- 可复现仅在已规定的输入规范化、算法 / 工具版本及构建条件下主张；跨编码器版本的归档不必字节相同，但受支持格式需保持可解码。

## 2. 建议模块与依赖方向

```text
SeedArc/
├── AGENTS.md
├── CMakeLists.txt                 # 工程创建后
├── CMakePresets.json             # 配置完成后
├── vcpkg.json                    # 采用 manifest 时
├── docs/

│   ├── development.md
│   ├── memory-safety.md
│   ├── archive-format.md
│   ├── reproducibility.md
│   ├── testing.md
│   └── agent-workflow.md
├── core/
│   ├── archive/                  # 版本化归档、索引、校验
│   ├── filesystem/               # 输入枚举、文件 / 路径安全
│   ├── chunk/                    # 固定分块；后续内容感知分块
│   ├── seed/                     # PRNG、策略映射与版本
│   ├── codec/                    # 第三方库封装唯一边界
│   │   ├── zstd/
│   │   └── lzma2/
│   ├── search/                   # 搜索、预算与候选缓存；后续
│   └── benchmark/                # 统计 / 基线；后续
├── cli/                          # 优先开发
├── gui/                          # Qt 6；后置
├── tests/
├── fuzz/                         # 测试基础设施成熟时
└── third_party/                  # 外部源码；来源与维护约定已建立
```

仅为**逻辑布局**。Agent 要检查仓库实际结构；不得为了符合示例随意迁移用户代码或凭空创建未来模块。

依赖方向：`cli` / `gui` / `tests` / `benchmark` → 公开 `core` 接口 → 内部模块 → `codec` → 第三方库。`core` 不依赖 Qt；策略、索引、UI 模块不直接调用第三方压缩 C API、持有其上下文或泄漏第三方错误码。

## 3. 首批编码器与扩展节奏

| 阶段 | 编码器 / 结构 | 要求 |
| --- | --- | --- |
| MVP | **Store、Zstandard / libzstd、LZMA2 / 成熟库** | 真实编解码、可恢复错误、资源限额、往返、归档完整性 |
| 扩充 | Brotli、zlib / DEFLATE、LZ4 | 同一适配层；依赖版本与许可证；算法对照基准 |
| 研究 | 内容定义分块、文件聚类、固实压缩、共享字典、跨块关联、局部搜索 | 证明净收益；记录字典 / 元数据开销和资源预算 |
| 产品化 | Qt GUI、更多压缩库、插件接口、可选认证加密 | 不阻塞核心；以实际需求与维护成本证明合理性 |

LZMA2 是编码方式，不等于 `.xz` 容器；编码流形式必须记录解码所需的字典 / 参数。多层重复压缩往往无益，仅作为可禁用、有基线的实验，不得以其存在宣称安全性或压缩优势。

## 4. 数据路径与职责

压缩：输入文件列表标准化 → 分块 / 分组 → 通过种子确定策略 → 独立编码上下文压缩 → 生成索引 / 必需策略字段 → 完整性校验 → 安全提交归档。

解压：校验魔数 / 版本 / 上限 → 安全解析索引与种子 / 必需字段 → 分派解码器 → 校验恢复字节 → 将文件写入限定输出根目录；任何失败不得伪造成功或覆盖合法数据。

关键边界：**编码时以原始内容作出的判断，解码器不能凭种子和归档外不可得信息重做**。这些判断的必要信息必须写入归档。详见 `archive-format.md` 与 `reproducibility.md`。

## 5. 分阶段实施与范围控制

- **阶段 0**：CMake / CTest / CLI / core 最小骨架、统一错误模型、编码器接口、可测试的 PRNG 约定与 Git 跟踪。安全与 ABI 问题不得靠关闭检查“解决”。
- **阶段 1（MVP）**：文件 / 目录、固定分块、Store / Zstd / LZMA2、指定种子、基本归档、验证与安全解压；往返和确定性测试通过。
- **阶段 2**：Brotli / DEFLATE / LZ4，有限预算的种子搜索、单算法 / 逐块择优基线；保留最优且已验证的候选。
- **阶段 3**：聚类、字典、结构化策略与跨块依赖；严谨测量压缩 / 解压 / 搜索时间和峰值内存。
- **UI 安排**：按用户人工交互测试需要启动轻量 Qt GUI，不绑定 M4 完成时间；先用 CLI / JSON / 报告比较种子计划，必要时提供交互界面，搜索相关界面随核心实际能力补齐。GUI 复用核心逻辑，作为可选构建，不阻塞 CLI。详见[开发计划](development-plan.md)。
- **阶段 4–5**：新算法、生态 / 插件、GUI 产品化、可选认证加密、发布与跨平台兼容。加密应采用成熟认证加密和 KDF：先压缩再加密；解密后再解压。

CLI 规划名称：`seedarc compress`、`seedarc extract`、`seedarc verify`，之后 `seedarc search`、`seedarc benchmark`。这些命令是**计划接口，未证明已经存在**。

## 6. 最小必要复杂度

- 内部模块只抽象**当前已有的两种及以上真实用法**，或者有明确可测试的安全 / 解耦需要；不单凭“将来可能”设计通用框架。
- 优先标准库容器、RAII、小型稳定适配器；不在未 profile 时引入自定义 allocator、复杂线程池或手写 SIMD。
- 扩展接口需兼顾简单调用与真正的流式处理；避免要求调用者一次性持有完整大文件。
- 优化必须包含 Release 性能基准及回归测试，且不影响归档可读性或数据正确性。

## 7. 待明确的工程决定

PRNG 与种子编码、压缩参数映射、归档字节布局、Windows 元数据约定、分块大小、资源限额、线程 / 缓存政策、LZMA2 底层流形式、跨工具链确定性保证范围。未冻结前可以研究、实现局部原型并测试；**对外冻结与改变已冻结协议**必须按 `AGENTS.md` 的权限模型办理。
