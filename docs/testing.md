# SeedArc 测试、性能实验与分阶段验收

> 本文区分**必须立即满足的安全 / 正确性底线**与**随阶段增加的测试深度**。未执行的检查不得标成通过；缺少必需工具时应告知如何安装并标注验收阻塞。

## 1. 任何阶段都不得豁免的底线

- 所有声称成功的归档必须能完整解压并逐字节还原受支持输入；不能只看命令退出码。
- 不允许已知越界、整数溢出、悬空引用、无限内存分配、路径穿越、目录逃逸或未授权覆盖用户文件。
- 完全不支持的特性必须**显式拒绝**，不能边报错边继续写入，或假装安全处理。
- 出错、取消、磁盘已满、解码器失败或校验失败后不得产生伪装成功的文件 / 归档。
- 第三方库 / ABI / 依赖缺失时不通过降低安全限制、关闭警告 / 检查来制造“通过”。

## 2. 按阶段验收矩阵

| 验收项目 | 阶段 0 / MVP | 研究阶段 | 正式发布 |
| --- | --- | --- | --- |
| C++23 构建与 CTest | 必须；所选构建链路 | 必须；多链路回归 | 必须；发布目标矩阵 |
| 单测、编解码往返、错误报告 | 必须 | 必须回归 | 必须回归 / 发布检查 |
| 资源上限、路径与文件安全 | **必须**，未支持的特殊类型安全拒绝 | 扩展恶意输入矩阵 | 完整威胁模型与公开不可信输入审查 |
| 种子策略 / 同环境确定性 | 必须（已实现功能） | 并发及已支持跨工具链验证 | 发布承诺范围内的完整兼容验证 |
| Sanitizer / 静态分析 | 与改动风险相关的可用检测必须执行；不可用如实上报 | 多配置动态分析及回归 | 发布范围内形成可审计记录 |
| Fuzzing | 明确解析 / 解压入口与负面测试；安全关键变更按风险执行适用 Fuzz | 持续 Fuzz、崩溃回归、语料管理 | 必须有针对不可信归档的 Fuzz 证据及缺陷处置 |
| 公平压缩率 / 时间 / 内存基准 | 首批算法基本基线，禁止未证收益宣称 | **必须**有完整归档和公平预算比较 | 性能回归及可复现实验报告 |
| 已发布旧包 golden fixtures | 尚无正式格式时不适用；冻结后建立 | 版本演进时必须 | **必须**覆盖承诺的旧格式 |
| 依赖漏洞 / 许可 / 分发 | 引入依赖时审核 | 更新与检查 | 完整发布审查 |

MVP 的“阶段较早”仅意味着可以减少支持范围；不能“先让路径穿越工作，发布前再补”。对不能安全处理的重解析点、链接等拒绝解压，并为拒绝行为写测试。

## 3. 单元、集成与负面测试目录

### 3.1 单元测试

- PRNG 固定输出及 seed→strategy 测试向量、映射边界和版本字段。
- 编码器配置检查、未知算法 / 不支持等级、第三方错误映射、上下文 RAII 销毁。
- 索引序列化 / 解析、checked arithmetic、缓存键完整性、错误码和限额计算。

### 3.2 往返测试

- 空文件 / 空目录、单字节、长路径 / 非 ASCII 名称、嵌套目录、大量小文件、大文件、已压缩数据、高熵数据。
- Store、Zstd、LZMA2 每种支持编码器；未来算法接入时自动套用相同测试。
- 同样输入 + 种子 + 受控环境重复打包，确认**归档字节完全相同**（按已声明的保证范围）。
- 模拟部分读写、权限错误、取消、磁盘空间不足、临时文件清理、输出文件冲突。

### 3.3 负面 / 恶意归档测试

- 错误头 / 未知格式、截断头 / 流、伪造长度、负数等非法字段、越界及交叠索引、坏字典、错误校验。
- 声明超大解压长度、解压炸弹、过多文件 / 块 / 目录、无界元数据、算术溢出。
- Windows `..`、绝对 / UNC / 盘符相对路径、ADS、保留设备名、大小写冲突、尾随点 / 空格，以及符号链接 / junction / reparse point 和竞态。
- 任何负测失败都应返回清晰错误、无越界、无越权写入；不得仅靠进程不崩溃判定安全。

## 4. Sanitizer、静态分析与 Fuzz

- 首选已安装 clang-tidy、编译器警告和实际可运行的 Sanitizer 组合；**不要假设 Windows 下 MSVC、MSYS2 Clang 与 GCC 的动态检测完全相同**。
- 归档解析、长度计算、第三方 ABI 边界相关改动，需要更严格的动态检查与恶意输入测试；安全相关 Fuzz 无法运行时需报告原因、建议工具 / 版本及可继续完成的独立工作。
- Fuzz 入口优先：`parse_archive_header`、`parse_index`、`decode_block` / 受限解压。设置可复现语料、资源上限、超时与 crash reproducer；不要在没有验证支持时直接声称 Windows fuzz runner 可用。
- 已验证的 Windows runner：MSVC `/fsanitize=fuzzer`（`msvc-fuzz` preset，仅构建 `fuzz/` 目标）；目标、种子语料与运行命令见 `fuzz/` 和 [M1 记录](m1-validation.md)。普通构建的 `fuzz.replay.*` CTest 只重放种子语料，不等于 Fuzz。MSYS2 Clang / GCC 的 fuzzer 运行时未验证。
- Fuzz、Sanitizer、静态分析各自作用不同；固定的负面测试不能冒充 Fuzz，通过编译不能冒充动态检测。
- 只安装测试工具不等于完成测试；必须记录实际运行命令、工具版本、持续时间 / 用例和结果。

## 5. 公平且可重复的压缩实验

至少比较：

1. 单一压缩算法的多个有代表性等级（Zstd、LZMA2 等）；
2. 逐块实测选最小输出的基线（包括选择信息的归档开销）；
3. 随机种子搜索；
4. 结构化 / 局部优化搜索（实现之后）。

对照必须：相同输入数据快照、相同格式 / 库版本、**相同时间或计算资源预算**、可比的硬件和线程限制，报告完整归档尺寸与置信度 / 重复运行波动。

记录至少包含：输入清单 / 哈希、压缩后**最终归档字节数**、单纯编码耗时、搜索耗时、解压耗时、峰值内存、尝试次数、线程 / CPU、压缩库版本、编译器 / Release 参数、往返验证结果和种子。

不要用 Debug 结果做性能宣传，也不要只统计压缩 payload 或把搜索开销藏在“额外预处理”中。搜索无收益时应该输出已验证的最优合法候选，而不是损坏包。

## 6. 单项任务完成定义（Definition of Done）

交付前确认：

- [ ] 变更满足当前任务范围，架构 / 协议约束已核对。
- [ ] 执行了相关构建、格式化、单元 / 集成 / 负面测试；对修改过的编码器运行往返校验。
- [ ] 数据安全与资源上限没有退化，危险特性未支持时会拒绝。
- [ ] 涉及性能的变更有相同环境 Release 基准；涉及格式 / seed 的变更有兼容性 / 确定性验证。
- [ ] 未禁用失败测试、未吞错误、未掩盖风险；任何未运行项均写明原因和阻塞。
- [ ] 记录具体命令 / 结果、修改文件、需要安装的新工具以及后续最小任务。

**若任何“必须”项尚未通过**：交付状态只能标记为 **未验收 / 部分完成 / 阻塞**，不可用“完成”掩盖。
