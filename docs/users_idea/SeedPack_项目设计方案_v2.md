# SeedPack：基于种子驱动的可复现混合压缩系统

> **文档版本**：v0.2（项目构想与初步架构）  
> **项目名称**：SeedPack（暂定）  
> **项目状态**：设计阶段，压缩率优势尚未实测验证  
> **主要开发语言**：**C++23**（未来在工具链成熟时评估升级 C++26）  
> **图形界面**：Qt 6（与压缩核心解耦）  
> **构建与测试**：CMake、Ninja、CTest；主要 IDE 可使用 CLion

---

## 1. 项目定位

SeedPack 是一个面向**文件与文件夹**的实验性混合压缩软件。它不以创造全新的基础压缩算法为前提，而是接入多种成熟的压缩编码器，通过**种子驱动的确定性策略生成器**，决定分块、算法选择、参数及后续更复杂的数据组织方式，并探索能否通过搜索种子找到压缩效果更好的方案。

项目的两个核心方向同时成立：

1. **种子驱动、结果可复现**：在输入、元数据约定、程序版本、算法版本和配置固定时，相同种子产生相同压缩策略，并力求得到逐字节一致的归档。
2. **搜索更优压缩方案**：试验多个种子、衡量最终归档大小，在指定时间和资源预算内寻找压缩效果最好的候选。

**开发策略明确为“先少后多”**：第一阶段接入常见且成熟的算法，完成可靠的压缩/解压闭环；后续借助 C++ 对 C/C++ 压缩库的直接集成优势，逐步扩展至更多算法，必要时研究其内部参数或修改编码器实现。

**加密不是项目重心**。它可在压缩和解压系统稳定之后，作为独立的可选功能加入。

### 1.1 已确定的方向

| 事项 | 当前决定 |
| --- | --- |
| 核心语言 | C++23，后续评估 C++26 |
| GUI | Qt 6，独立于核心库 |
| 构建 | CMake + Ninja；使用自动测试 |
| 底层压缩 | 优先复用成熟 C/C++ 库，不重写现有算法 |
| 初期算法规模 | 少量常见算法，稳定后再扩展 |
| 核心创新点 | 种子到压缩策略的确定性映射、策略搜索与优化 |
| 最优目标 | **完整归档的字节数**，不是仅压缩数据部分 |
| 安全设计 | 内存安全、文件解析安全与数据完整性优先；加密后置 |

### 1.2 尚待实验确定的内容

- 哪些策略维度可以真正改善压缩率，以及改善幅度多大；
- 种子驱动方案相对于直接逐块最优选择的收益；
- 分块大小、分组方法、共享字典及跨块关联如何协同；
- 哪些多级压缩组合值得保留；
- 搜索时间、内存与压缩率之间的最佳折中。

## 2. 核心思想：种子是压缩策略的紧凑表示

令输入文件集合为 \(F\)，种子为 \(S\)，确定性策略生成器为 \(G\)，压缩器为 \(C\)：

\[
P = G(S, V, M)
\]

\[
A = C(F, P)
\]

其中：

- \(P\)：压缩策略；
- \(V\)：策略生成器的版本及兼容性约定；
- \(M\)：压缩前后均可获取的公开输入元数据（例如块编号、固定的分块规则等）；
- \(A\)：SeedPack 归档。

策略可以控制：

- **分块方式**：固定大小分块；后期探索内容定义边界；
- **压缩算法**：Zstandard、LZMA2、Brotli、DEFLATE、LZ4 或原样存储；
- **算法参数**：压缩等级、窗口大小、词典等；
- **分组方式**：文件聚类、相邻块合并、固实压缩（solid compression）；
- **字典配置**：是否启用共享字典、训练样本或字典参数；
- **多级压缩（实验性）**：按种子生成的顺序叠加算法，解压时逆序执行。

多级压缩通常**不能进一步缩小已压缩数据**，可能反而增加体积和耗时；这一功能只应作为可测量、可禁用的实验选项。

### 2.1 种子不是密码，也不是压缩数据本身

种子只决定**可重建的策略**，并不凭空包含文件数据。归档仍须保存压缩后的实际字节流，以及完整解压所需的索引和元数据。

若编码时某个决定依赖原始数据（例如“试完所有算法后，选最小的”），解压器无法仅凭种子重算这个决定。因此，必须：

- 要么使决定仅依赖种子及解压侧可获得的元数据；
- 要么把该决定所需的最小信息显式存入归档。

**可复现不意味着“无需索引信息”**：块边界、压缩长度、必要的算法标识和参数仍可能需要存储。

### 2.2 确定性要求

需要固定或明确版本化的因素包括：

- 文件枚举顺序、目录路径规范化、符号链接处理；
- 文件时间戳、权限等元数据的处理方式；
- 种子字节编码、伪随机数生成器和策略映射算法；
- 算法参数、压缩库版本及编码器行为；
- 多线程处理后的**归档写入顺序**；
- 二进制序列化格式、字节序与整数编码规则。

同一版本的解压器应能够按归档记录的格式/策略版本解开旧包。**跨版本可解码**比“不同版本编码器永远产生完全相同字节”更重要；两者需要分别测试。

## 3. 最优种子搜索

寻找目标：

\[
S^* = \arg\min_{S\in\mathcal S} \operatorname{Size}(\operatorname{Archive}(F,S))
\]

`Size` 指**最终完整归档大小**，计入种子、索引、算法配置、字典、文件元数据与校验信息。

### 3.1 初始搜索流程

1. 固定输入文件清单、格式版本和测试预算；
2. 生成候选种子；
3. 通过确定性的策略生成器得到候选配置；
4. 压缩、统计最终归档大小和耗时；
5. 保留当前最优种子及实际压缩结果；
6. 在达到尝试次数、时限、CPU/内存预算或用户中止时停止。

### 3.2 逐步增加优化能力

- **随机搜索**：作为简单、可复现的基线；
- **有约束的策略采样**：避免显然无意义的组合；
- **局部搜索 / 变异**：围绕优秀候选调整分块、分组、算法参数；
- **粗筛 + 精测**：先用样本筛选，再对完整输入验证；
- **候选缓存**：对相同输入块、相同编码器和参数复用有效结果（确保缓存键完整）；
- **并行搜索**：不同候选使用独立压缩上下文；
- **多目标权衡**：可分别提供“最小体积”“压缩速度优先”和“平衡模式”。

### 3.3 必须验证的限制

若每个数据块彼此独立，且算法选择仅决定该块体积，则**直接逐块测试并选择最小输出**往往比随机搜索整个组合更可靠。SeedPack 的搜索价值更可能体现在：

- 内容感知分块与块边界；
- 文件聚类和固实压缩；
- 字典训练、共享字典及跨块依赖；
- 相互影响的压缩参数、内存与时间约束。

项目不预设“种子搜索一定优于单一算法”，而以实验数据检验。

## 4. 压缩算法接入路线：先常见，后广泛

压缩算法生态中有很多成熟的 C 或 C++ 实现。选择 C++ 的一个主要理由是：**可以直接使用 C 头文件和 ABI 调用现有库，也便于调试、静态/动态链接，或后期修改编码器源码**。但实际构建仍需处理各个库不同的依赖、许可、平台适配和错误模型。

### 4.1 建议第一批接入

| 算法/格式家族 | 典型实现 | 选择理由 | 阶段 |
| --- | --- | --- | --- |
| **Zstandard (Zstd)** | `libzstd`（C） | 通用性强、速度/体积选项丰富，适合主力基线 | 第一批 |
| **LZMA2** | LZMA SDK / `liblzma`（C/C++） | 偏高压缩率场景，适合对照实验 | 第一批 |
| **Brotli** | Brotli（C） | 提供不同编码策略与参数空间 | 第一批扩充 |
| **DEFLATE** | zlib（C） | 经典通用算法，适合兼容性和基线比较 | 第一批扩充 |
| **LZ4** | `liblz4`（C） | 高速路径、可用于速度优先模式 | 第一批扩充 |
| **Store（不压缩）** | 自行实现 | 避免对不适合压缩的数据造成额外膨胀 | 从 MVP 起必备 |

**MVP 最小组合**：先用 **Zstd + LZMA2 + Store** 做完压缩、解压、随机种子和归档闭环，再接入 Brotli、DEFLATE、LZ4。此处是推荐顺序，不是不可改变的约束。

> 注意：LZMA2 是算法/编码方式，不应与 `.xz` 容器等同。每个适配器须明确使用原始流、库自带容器或其他形式，并记录必要参数和解码信息。

### 4.2 后期算法扩展原则

在基本功能稳定后，可以逐渐支持更多通用、专用或实验性算法，包括但不限于其他熵编码、字典压缩、快速压缩和面向特定数据类型的编码器。**不在第一版盲目追求算法数量**。

每个新算法需要通过统一的接入标准：

1. **编解码功能完整**，能往返恢复原始数据；
2. **明确授权与许可证**，允许预期的分发方式；
3. **可重复构建**，拥有可追踪的依赖和版本；
4. **运行时资源受控**，可限制输入/输出大小、内存与耗时；
5. **良好的错误报告**，包括损坏输入、非法参数和不受支持的版本；
6. **有测试与基准结果**，证明该算法对某类数据有价值。

第三方插件机制可在后期设计，不宜在最初阶段为此增加复杂度。

## 5. C++23 技术选型与内存安全策略

### 5.1 为什么选择 C++23

- 能直接接入大量 C/C++ 压缩库，减少跨语言 FFI 和胶水层；
- Qt 6 的 C++ API 成熟，便于开发 GUI；
- 方便调试压缩器内部行为，后期可深入研究源码；
- 使用现代 C++ 标准库和工具建立可维护、受约束的核心架构。

Rust 在编译期内存和并发安全方面具有实质优势。选择 C++ 并不否认这一点，而是判断**本项目的压缩库集成便利性**可以抵消部分需要额外投入的安全维护成本。该判断可随代码规模与实验结果重新评估。

### 5.2 项目级安全约束

1. **C API 只能出现在 `codec/` 适配层**；上层策略、归档和 UI 模块不直接持有第三方裸指针。
2. 所有压缩器上下文以 **RAII** 管理；销毁函数封装到自定义 deleter 或专用类。
3. 数据所有权优先使用 `std::vector<std::byte>`、`std::unique_ptr` 等；无所有权视图使用 `std::span`，严格控制有效期。
4. 解析归档时校验**长度、偏移、整数溢出、算法 ID、资源上限**，且先验证再分配/读写。
5. 每个并行任务原则上拥有独立压缩上下文；不要默认第三方上下文是线程安全的。
6. 错误通过清晰的返回类型（例如 `std::expected`）传递，不把第三方错误码扩散到核心层。
7. 禁止静默忽略库错误码；任何失败都不得输出伪装为成功的归档。
8. 解压文件路径必须防止绝对路径、`..` 越界写入、符号链接逃逸等路径穿越问题。
9. 通过单元测试、集成测试、模糊测试、静态分析及 AddressSanitizer（支持的配置）共同检测问题。
10. 压缩库本身的 C 实现仍可能存在缺陷：C++ 适配层的安全设计并不能替代依赖更新和漏洞修复。

**原则**：用架构限制潜在不安全代码的范围，不依赖 CLion 的静态提示来“保证内存安全”。

### 5.3 统一适配器接口（概念）

```cpp
struct CodecOptions {
    int level = 0;
    // 后续可加窗口、字典、算法专用参数等。
};

struct CodecError {
    int code = 0;
    std::string message;
};

class ICodec {
public:
    virtual ~ICodec() = default;

    virtual std::expected<std::vector<std::byte>, CodecError>
    compress(std::span<const std::byte> input,
             const CodecOptions& options) = 0;

    virtual std::expected<std::vector<std::byte>, CodecError>
    decompress(std::span<const std::byte> input,
               std::uint64_t expected_size,
               std::uint64_t max_output_size) = 0;
};
```

这是接口设计示意，不是直接可编译的完整代码；需要相应标准库头文件及具体实现。正式实现时还应考虑流式 API、字典参数、取消操作和输出缓冲复用，避免一律分配整块内存。

## 6. 系统架构

```text
SeedPack
├── core/                     # C++23 核心库（不依赖 Qt）
│   ├── archive/              # 归档格式、索引、完整性校验
│   ├── filesystem/           # 文件清单、路径与元数据
│   ├── chunk/                # 分块、块分组
│   ├── seed/                 # 种子编码、确定性 PRNG、策略映射
│   ├── codec/                # 压缩库统一接口及 C/C++ 适配器
│   │   ├── zstd/
│   │   ├── lzma2/
│   │   ├── brotli/           # 后续扩充
│   │   ├── deflate/          # 后续扩充
│   │   └── lz4/              # 后续扩充
│   ├── search/               # 搜索器、预算、结果缓存
│   └── benchmark/            # 压缩率、速度、资源统计
├── cli/                      # 第一阶段优先：命令行工具
├── gui/                      # Qt 6 桌面图形界面（后续）
├── tests/                    # 单测、往返测试、损坏包测试
├── fuzz/                     # 归档解析与解压模糊测试
├── third_party/              # 必要时维护受控第三方依赖
└── CMakeLists.txt
```

核心库独立于 Qt：这样 CLI、GUI、性能基准和自动测试共享同一套压缩逻辑，也避免 UI 层左右压缩引擎的生命周期和并发模型。

### 6.1 压缩流程

```text
文件 / 文件夹
  → 标准化文件清单
  → 分块 / 文件分组
  → 根据种子产生策略
  → 按块调用压缩算法适配器
  → 生成块索引与必要策略元数据
  → 校验并写入 SeedPack 归档
```

### 6.2 解压流程

```text
SeedPack 归档
  → 校验魔数、版本与资源上限
  → 读取种子 / 获取外部种子
  → 恢复策略及块索引
  → 调用对应解码器解压
  → 校验内容一致性
  → 安全恢复文件与目录
```

## 7. 归档格式草案

以下仅描述结构，不规定最终字节布局。

```text
┌──────────────────────────────────┐
│ Magic / 容器版本                 │
├──────────────────────────────────┤
│ 种子与策略生成器版本             │
│ （或“需外部种子”标记）           │
├──────────────────────────────────┤
│ 算法登记表 / 参数与兼容性信息     │
├──────────────────────────────────┤
│ 文件、目录和元数据索引           │
├──────────────────────────────────┤
│ 块索引：偏移、压缩长度、原长度等 │
├──────────────────────────────────┤
│ 可选的字典与辅助数据             │
├──────────────────────────────────┤
│ 压缩数据块                       │
├──────────────────────────────────┤
│ 完整性校验                       │
└──────────────────────────────────┘
```

格式设计要求：

- 使用固定宽度整数并明确字节序；
- 对扩展字段设置可跳过或可拒绝的兼容机制；
- 每个数据块记录可靠的边界、原始长度和压缩后长度；
- 对算法 ID、版本和选项进行稳定登记；
- 支持原样存储（Store）和未知算法时报错；
- 支持大文件分块和流式写入；
- 防止解压炸弹、越界读取和不受信任路径写出；
- 规划校验和/哈希以检测损坏（不将普通哈希当作加密认证）；
- 清晰规定是否及如何存储种子。

### 7.1 种子的两种模式

| 模式 | 作用 | 备注 |
| --- | --- | --- |
| **内嵌种子** | 解压无需用户额外输入，适合普通归档和基准测试 | 默认建议 |
| **外置种子** | 解压需要另行提供种子 | 可增加恢复复杂性，**不构成可靠加密** |

无论采用哪种模式，归档格式必须保留解码所需的信息，不允许因为缺少编码时才知道的决策而导致合法用户无法解压。

## 8. 运行模式与用户体验

| 模式 | 用途 |
| --- | --- |
| **快速/标准压缩** | 直接应用预设策略，无需大量搜索 |
| **指定种子** | 用户输入种子，生成可复现的压缩配置 |
| **最优种子搜索** | 给定时间、次数或资源预算，寻找当前最佳种子 |
| **实验/基准测试** | 比较算法、等级、分块、搜索方法和数据集 |
| **解压/验证** | 验证归档并安全恢复文件与文件夹 |

CLI 应优先实现，以便快速进行自动化测试和批量基准；Qt GUI 在核心稳定后增加文件选择、参数设置、进度条、压缩率曲线及搜索结果展示。

示例命令（**规划中的接口，并非现有可执行命令**）：

```bash
seedpack compress ./dataset -o output.spk --seed 12345
seedpack search ./dataset -o best.spk --time-limit 600
seedpack extract best.spk -o ./restored
seedpack verify best.spk
seedpack benchmark ./testdata
```

## 9. 基准测试与成功标准

**研究核心问题：种子驱动的结构化搜索，能否在可接受资源预算内，相比经典方法获得更小的归档？**

至少比较四组方案：

1. 单一算法与固定压缩等级（Zstd、LZMA2、Brotli 等）；
2. 逐块独立测试算法并选择最小结果；
3. 随机种子搜索；
4. 带局部优化或结构约束的种子搜索。

测试数据至少覆盖：源代码、文本文档、二进制程序、混合目录、图片、音视频、已压缩文件、大文件与大量小文件。

必须记录：

- **最终压缩包体积**与基线差异；
- 压缩耗时和搜索耗时（分开计量）；
- 解压耗时；
- 峰值内存、CPU 利用情况；
- 搜索次数、每次收益与最优值变化；
- 往返恢复是否逐字节一致；
- 相同输入/种子/环境的结果是否可复现。

比较时要控制**相同时间预算或计算资源预算**。不要仅凭“尝试更多次后体积更小”就断言系统更高效。

### 9.1 第一版验收标准

- 所有受支持的输入都能压缩、解压并通过哈希一致性测试；
- 同种子与相同环境多次压缩结果一致；
- 分块、索引和算法适配器通过单测与常见异常输入测试；
- 能量化报告与单一算法基线的体积、时间差异；
- 即使搜索无收益，也能正确保留并输出当前最佳候选。

## 10. 内存安全、数据可靠性与测试

虽然优先选择 C++，但应将安全与正确性约束作为架构的一部分：

- **静态分析**：CLion 检查、编译器警告、可选 clang-tidy；
- **动态检测**：支持的平台上运行 AddressSanitizer，必要时结合其他检测工具；
- **单元测试**：种子映射、索引序列化、边界检查、适配器错误处理；
- **往返测试**：`decompress(compress(input)) == input`；
- **损坏输入测试**：截断流、错误长度、伪造块索引、错误种子、未知算法；
- **模糊测试**：优先针对归档头、索引和解码入口；
- **资源限制**：限制单块解压大小、整体输出、内存消耗及文件数量；
- **并发测试**：多任务取消、失败收尾和缓存一致性。

不要仅因 CLion 没有提示，就认定代码没有内存安全问题；对第三方 C 库同样需要跟踪版本和安全修复。

---

## 11. 恢复复杂性与可选加密

种子控制的算法选择、分块和处理顺序，可能在缺少种子时增加手动恢复数据的成本。这可以视为**附带性质**，但不把算法组合数量等同于密码学安全强度，也不把外置种子替代加密。

**加密功能安排在后续阶段**：待基本压缩、解压、优化、归档格式和兼容性稳定后，再作为独立可选层接入成熟的认证加密算法及合适的口令派生机制。

设计原则是**先压缩，后加密；解密后再解压**。加密不应改变种子策略搜索的核心实现，也不应以自制密码算法代替成熟方案。

## 12. 分阶段开发路线

### 阶段 0：项目骨架与约束

- [ ] 建立 C++23 / CMake / CTest 工程；

- [ ] 配置编译警告、CLion 静态检查和可用的 Sanitizer 测试配置；
- [ ] 确定输入文件顺序和种子编码规范。

- [ ] 实现时间/尝试次数/内存预算和取消机制；

- [ ] 相似文件聚类与固实压缩；

### 阶段 4：更多算法与可扩展生态

- [ ] 根据基准收益接入更多开源 C/C++ 压缩算法；

阶段顺序允许按实际需求交叉推进，但**不要让 GUI、插件系统或加密功能阻塞基础压缩和搜索实验**。

## 13. 非目标与设计边界

第一版**不追求**：

- 自行重新实现所有压缩算法；
- 一次集成几十种算法；
- 通过复杂压缩链保证超越现有压缩软件；
- 把种子当作可信的密码学加密；
- 在未经测试的情况下保证跨版本完全相同的归档字节；
- 在核心逻辑未稳定前完成复杂的跨平台 GUI 或插件生态。

项目应当随着测量结果迭代，而不是为了增加算法数量或种子空间牺牲可用性与正确性。

---

## 14. 一句话总结

> **SeedPack 使用 C++23 构建可扩展的混合压缩引擎：先接入常见 C/C++ 压缩库，以种子确定压缩策略，再搜索更优种子；在完成可靠压缩、解压和内存安全约束后，逐步增加算法、探索高级优化，并将 Qt GUI 与加密作为后续功能。**
