# SeedArc：结构化种子与压缩策略搜索设计草案

> **文档状态**：构想 / 待实验验证（非已实现功能、非最终归档协议）  
> **项目**：SeedArc — Seed-Driven Adaptive Compression  
> **主题**：Structured Seed（结构化种子）  
> **建议基线**：C++23；核心引擎独立于 Qt  
> **定位**：在可复现混合压缩的基础上，让种子既能表示策略，也能支持局部优化、策略交叉与结果复用。

## 1. 核心想法

SeedArc 最初设想由一个种子确定分块方式、压缩算法、压缩参数等配置，随后搜索不同种子，寻找使**完整归档体积**尽可能小的方案。

进一步的改进是：**将种子划分成具有不同语义的字段**，每一段分别影响压缩过程中的某一类决策。这样搜索器可以只修改其中一段，尽量维持其余策略不变，而不必每次完全随机生成全新策略。

核心目标可以概括为：

1. **确定性**：固定规范化输入、种子、策略生成器版本、编码器版本和配置时，生成相同的策略；满足额外条件时，归档输出应逐字节一致。
2. **可搜索性**：可以整体随机采样，也可以针对单个字段进行局部搜索或交叉组合。
3. **可复用性**：只要某次策略变化没有影响某个块的输入、编码参数及依赖，就可以复用其已计算的压缩结果。
4. **紧凑性**：用相对短的种子编码复杂策略，尽量减少保存大量独立配置所需的元数据。
5. **可扩展性**：新算法、新字段和新的映射规则通过版本化机制演进，不破坏旧归档解码。

**注意**：结构化种子不是加密密钥，也不保证压缩率优于成熟算法。它是一种**策略表示与优化搜索机制**，其实际收益需要实验验证。

## 2. 候选方案：128 位结构化种子

先以 **128 bit（16 字节）** 为原型种子长度。候选划分如下：

| 字段 | 位宽 | 位范围（高位到低位） | 主要职责 |
|---|---:|---|---|
| Chunk | 16 bit | 127–112 | 分块方式、目标块大小和边界相关参数 |
| Group | 16 bit | 111–96 | 文件分组、相似块聚合及固实分组策略（后续） |
| Codec | 32 bit | 95–64 | 各块压缩算法的确定性调度 |
| Params | 32 bit | 63–32 | 压缩等级、窗口、字典等编码参数 |
| Variation | 32 bit | 31–0 | 块级扰动、实验性策略与后续可扩展决策 |
| **合计** | **128 bit** | | |

示意（每个十六进制字符为 4 bit）：

```text
┌─────────┬─────────┬──────────────┬──────────────┬──────────────┐
│ Chunk   │ Group   │ Codec        │ Params       │ Variation    │
│ 16 bit  │ 16 bit  │ 32 bit       │ 32 bit       │ 32 bit       │
├─────────┼─────────┼──────────────┼──────────────┼──────────────┤
│ 12AB    │ 0345    │ C0DEC0DE     │ 000A1F20     │ 9B7E42D1     │
└─────────┴─────────┴──────────────┴──────────────┴──────────────┘

完整种子：12AB0345C0DEC0DE000A1F209B7E42D1
```

以上只是**候选字段分配**，不是已经冻结的二进制协议：各字段具体取值、子字段布局、采样方法和是否保留全部 5 段，都需要原型测试后确定。首版未实现的 Group / Variation 功能必须有明确、无歧义的保留或忽略规则，不能在不同版本中悄悄改变同一个种子的含义。

## 3. 字段语义与映射原则

### 3.1 Chunk：分块策略

控制固定大小分块的块大小、边界参数；未来可扩展到内容感知分块。**分块变化会改变后续块的内容及编号，往往使大量已有缓存失效**，因此它适合较外层、低频率的搜索。

### 3.2 Group：分组策略

控制文件或数据块的分组方式，未来可扩展到相似文件聚合、固实压缩及共享字典作用域。首版如果尚未提供该能力，应固定为规范化的单一行为，不能提前假设有效果。

### 3.3 Codec：压缩算法调度

例如可在 Store、Zstandard、LZMA2 等已实现算法中，为不同块生成算法选择。建议使用明确版本化的确定性生成规则：

```text
codec_choice(i) = MapCodec(CodecField, block_id=i, generator_version, available_codecs)
```

其中 `available_codecs` **不能直接依赖某台机器恰巧安装了哪些库**；归档写出时使用的候选算法集合、排序和 ID 必须由版本化规范固定，或在必要元数据中显式记载，否则跨环境会产生不同策略。

### 3.4 Params：算法参数

负责压缩等级、窗口及其他编码参数。**对有自然顺序的参数应优先采用局部可解释的映射**：例如字段微调能引起压缩等级的小幅变化。不要把所有参数先整体哈希成完全无关的结果，否则相邻种子之间缺少可利用的局部性。

### 3.5 Variation：局部扰动与实验扩展

可以控制某些块级决策、局部变异或未来实验参数；但不得成为无版本定义的“万能随机字段”。其影响范围必须可以测试，且不应在未声明的情况下改变其他字段的既定语义。

### 3.6 重要规则：确定性不等于局部性

即使种子只改变 1 bit，若映射过程使用雪崩效应强的哈希，也可能使整个调度发生大幅变化。因此应明确区分：

- **可局部调整字段**：对有序参数做直接或分层映射；
- **随机化字段**：通过固定算法的伪随机映射，产生可重复但不要求邻近的选择；
- **跨块依赖字段**：明确依赖传播范围，不能错误地宣称“只改一个字段就只重压一个块”。

## 4. 两种种子如何产生不同策略

假设两个种子只有 Params 字段不同：

```text
种子 A： [Chunk][Group][Codec][Params A][Variation]
种子 B： [Chunk][Group][Codec][Params B][Variation]
```

设计目标是保留一致的分块和算法调度，只改变编码参数。若两个种子只在 Codec 字段发生变化，则可以保持分块和分组不变，专门探索算法选择。

这种“字段隔离”不保证最终只有一个数据块变化；是否能局部复用，取决于策略映射、字典与跨块依赖的真实设计。

## 5. 搜索策略

SeedArc 可逐步引入以下几种搜索方法，并始终保留公平的对照基线。

### 5.1 全局随机搜索

独立生成多个完整种子，压缩、验证并比较完整归档大小。它实现简单，可作为结构化方法的对照组。

### 5.2 分段局部搜索（Coordinate / Block-wise Search）

从当前最优种子出发，冻结其他字段，仅改变一个字段，测试新的候选并保留更优结果。例如：

```text
当前最优种子 S
   ├─ 只变 Chunk     → 测试 S_chunk
   ├─ 只变 Group     → 测试 S_group
   ├─ 只变 Codec     → 测试 S_codec
   ├─ 只变 Params    → 测试 S_params
   └─ 只变 Variation → 测试 S_variation
                          ↓
                保留经过完整校验的最优候选
```

这有利于观察某一类决策对压缩结果的影响，也便于记录实验。

### 5.3 分层搜索

可以探索从大尺度到小尺度的搜索顺序：

1. 外层尝试分块 / 分组配置；
2. 中层尝试压缩算法调度；
3. 内层微调编码参数；
4. 对可复用的中间结果进行缓存；
5. 在预算用尽时保存**已经验证**的最佳候选。

这是一种候选研究方法，并非已被证明是全局最优的搜索顺序。

### 5.4 交叉与变异（后续实验）

将两个表现较好的种子的某些字段交换，或只变异某个字段，形成新候选：

```text
父代 A：[Chunk A][Group A][Codec A][Params A][Variation A]
父代 B：[Chunk B][Group B][Codec B][Params B][Variation B]
子代 C：[Chunk A][Group A][Codec B][Params A][Variation B]
```

需要和相同预算的随机搜索、局部搜索进行比较；字段交叉本身并不保证更好的压缩率。

## 6. 缓存复用：减少重复压缩

结构化种子的一项潜在优势，是可以识别哪些计算真正受到候选变化影响。

```text
候选 A：
  块 0：Zstd  参数 P0 → 结果缓存
  块 1：LZMA2 参数 P1 → 结果缓存
  块 2：Zstd  参数 P2 → 结果缓存

候选 B：
  块 0：Zstd  参数 P0 → 条件满足时复用
  块 1：LZMA2 参数 P1 → 条件满足时复用
  块 2：Brotli 参数 P3 → 需要重新压缩
```

缓存键至少应能唯一确定：

- 输入块的身份及内容（例如可靠内容哈希与长度）；
- 编码器 ID、版本、精确编码参数与使用的流格式；
- 字典内容或字典身份、跨块历史依赖、预处理步骤；
- 与压缩结果相关的其他配置或规范版本。

**不能只使用 Seed 或 Block ID 作为缓存键。** 若块边界变化、字典重建或固实压缩引入上下文依赖，相关块必须重新计算。候选缓存还要受到内存 / 磁盘预算限制，不得无限增长。

## 7. 压缩包格式与解压约束

种子能推导策略，但不能替代压缩数据。一个归档仍需要包含：

- 格式魔数、格式版本、策略生成器版本；
- 种子（默认内嵌）及其编码约定；
- 文件树、分块与索引元数据；
- 解压所需的算法 ID、编码流格式及必要参数；
- 压缩数据、必要字典和完整性校验信息。

特别注意：如果编码器在压缩过程中**实际比较原始块后选择最小结果**，解压时无法重新看到原始内容，因此最终选择必须被明确记录，除非它可以仅从种子与已有元数据确定性推导。

正式冻结协议前需明确：字节序、字段位范围、种子文本格式、映射算法、算法注册表、版本演进和兼容策略。

### 安全边界

种子不是密钥，压缩调度的复杂性不能代替加密。解压仍要防范恶意归档：边界越界、整数溢出、无限解压膨胀、路径穿越和资源耗尽。可选认证加密功能属于后续独立阶段。

## 8. C++23 实现草案

先保持逻辑结构独立、易测试，不急着把所有字段硬编码进稳定公共 API。

```cpp
#include <array>
#include <cstdint>

struct StructuredSeed128 {
    std::array<std::uint8_t, 16> bytes{};
};

struct StrategyGeneratorVersion {
    std::uint16_t major{};
    std::uint16_t minor{};
};
```

建议的内部模块职责：

```text
core/
├── seed/
│   ├── seed128.*           # 解析、显示、字节序与校验
│   ├── seed_layout.*       # 版本化字段解释
│   └── strategy_map.*      # 种子 → 确定性策略
├── chunk/                  # 分块与边界
├── codec/                  # Store / Zstd / LZMA2 适配
├── search/                 # 搜索预算、局部变异、候选排序
├── archive/                # 归档序列化与安全解析
└── benchmark/              # 统一测量与报告
```

约束：第三方 C 库资源使用 RAII 包装；搜索任务默认持有独立压缩上下文；策略生成器禁止使用未定义行为、实现相关随机分布与不稳定容器遍历顺序。

## 9. 如何验证它是否真的有价值

### 9.1 最小对照组

1. 固定算法与固定级别（例如 Zstd、LZMA2 各自的基线）；
2. 在同样候选预算下，对每块遍历允许算法并选择最小结果；
3. 非结构化、均匀随机种子搜索；
4. 结构化种子的分段局部搜索；
5. 后续再比较分层搜索、交叉与变异。

### 9.2 评价指标

- **完整归档体积**：包括种子、文件索引、字典、校验与算法信息；
- 压缩与搜索的**总墙钟时间**、真正的编码时间；
- 解压时间、峰值内存、磁盘临时空间；
- 搜索尝试次数、缓存命中率、有效候选率；
- 正确往返率、同条件归档哈希一致性；
- 在相同计算预算下的多次重复实验分布，而不是只公布最漂亮的一次。

### 9.3 需要回答的研究问题

- 固定 128 位种子是否足以高效编码候选压缩策略？
- 字段语义是否带来可利用的局部性？
- 结构化搜索是否在**同等时间或计算预算**下优于随机搜索？
- 缓存复用节省的时间是否超过维护缓存的成本？
- 当加入共享字典、分组和固实压缩后，收益是否依然存在？
- 种子编码相对于直接保存逐块方案，是否真正减少归档元数据？

## 10. 分阶段实施建议

| 阶段 | 内容 | 交付证据 |
|---|---|---|
| 0：原型规范 | 明确 128 位字段草案、固定序列化与确定性映射测试向量 | 相同输入参数始终得到相同策略 |
| 1：最小闭环 | Store、Zstd、LZMA2；固定分块；种子驱动算法 / 参数；压缩与安全解压 | 完整往返及坏包测试 |
| 2：结构化搜索 | 全局随机搜索、字段局部变异、时间与内存预算 | 对照基准和实验记录 |
| 3：缓存与高级策略 | 缓存复用、分组、字典、策略交叉 | 与无缓存及简单搜索的公平比较 |
| 4：进一步扩展 | Brotli、DEFLATE、LZ4、更多算法；Qt GUI 与可选加密后置 | 兼容性、性能与安全验证 |

## 11. 目前明确不冻结的决策

- 是否固定为 128 bit，以及 16 / 16 / 32 / 32 / 32 的最终位宽划分；
- 字段是否采用完全独立的映射或部分相互约束；
- 采用何种确定性 PRNG / 哈希与具体抽样规则；
- 哪些参数适合直接数值映射，哪些适合伪随机映射；
- 是否为特定策略增加少量显式覆盖元数据；
- 搜索是否采用坐标下降、遗传算法或其他优化方法；
- 归档扩展名、正式二进制布局及兼容版本编号。

这些都应先通过设计决策记录（ADR）和原型实验确定，再纳入稳定协议。

---

## 一句话总结

> **SeedArc 的结构化种子，不只是让随机数选择压缩算法，而是让一个紧凑、可复现的种子表示复杂压缩策略，并允许搜索器按语义局部优化、复用未受影响的计算结果，最终在有限预算内寻找更小的完整归档。**
