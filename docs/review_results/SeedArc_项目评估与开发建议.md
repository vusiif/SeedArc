# SeedArc 项目评估与下一步开发建议

> 评估日期：2026-11-12  
> 项目地址：[vusiif/SeedArc](https://github.com/vusiif/SeedArc)  
> 评估方式：基于仓库源码、项目文档和测试记录的静态审查；**未独立编译或运行项目**。

## 1. 执行摘要

**建议：保留现有工程架构，正式进入 M4，但在实现 Seed 搜索前先固定 Seed 协议和基准测试。**

SeedArc 的核心方向并非重新发明 Zstd 或 LZMA2，而是在成熟压缩算法之上，通过可复现的 Seed 策略控制块级压缩方案，并研究在相同预算下能否减小**整个归档文件**的体积。

应当分别衡量两个目标：

1. **工程目标**：安全、可靠地压缩、校验和还原文件及目录。
2. **研究目标**：用可重复实验验证 Seed 策略相对于固定压缩参数方案的实际收益。

从最近一次仓库检查的信息看，**M2 和 M3 已完成，M4 尚未开始**。以较新的 `STATUS.md`、README、构建清单及 CLI 实现为准，不应依据较旧的仓库页面将当前状态误判为 M1。

## 3. 已有设计中值得保留的部分

- **清晰的归档格式边界**：已有版本、头部、索引、块描述和校验机制，应优先保持格式兼容性。
- **成熟压缩器复用**：已接入 Store、Zstd 和 LZMA2，避免重新实现底层压缩算法。
- **谨慎的解压安全策略**：包含路径检查、校验和分阶段写入/提交等机制，不应只为提高速度而删除。
- **校验与解压路径复用**：有助于减少实现分叉和潜在兼容性错误。
- **已有测试基础**：单元、集成、故障注入和短时 Fuzz 检查为 M4 提供了回归保障。

**总体判断：不建议大规模重构，优先用小接口扩展既有压缩管线。**

## 4. 优化建议与优先级

| 优先级 | 项目 | 建议 | 预期收益 |
| --- | --- | --- | --- |
| **P0** | 压缩基准 | 为代码、文本、图片、视频、混合目录建立 Store/Zstd/LZMA2 对照实验 | 判断性能改进是否真实、可重复 |
| **P0** | Seed 协议 | 固定 Seed 长度与编码、策略版本、确定性 PRNG、块 ID 语义、测试向量 | 保证长期可重现与跨平台兼容 |
| **P0** | CI 自动化 | 将已有构建、测试及关键回归接入 GitHub Actions | 防止 M4 破坏 M1–M3 成果 |
| **P1** | 策略隔离 | 抽象 `StrategyGenerator` 与 `BlockPlan`，不要让策略代码直接触碰文件 I/O | 降低耦合，方便实验与回滚 |
| **P1** | 兼容与异常测试 | 覆盖旧归档、未知版本、非法 Seed、截断文件、取消操作及跨编译器确定性 | 提升可靠性与可维护性 |
| **P2** | 性能优化 | 先 profile，再考虑 CRC32C、块 I/O、压缩级别和并行化 | 避免无测量依据的复杂改造 |

### 4.1 首先固定 Seed 协议

建议将 Seed 策略定义成近似如下的纯函数：

```text
BlockPlan = GeneratePlan(Seed, StrategyVersion, BlockId, BlockMetadata)
```

其中：

- `Seed`：使用明确的字节序和序列化规则；
- `StrategyVersion`：控制映射规则的兼容性；
- `BlockId`：稳定、明确的块标识；
- `BlockMetadata`：只使用协议允许的确定性数据；
- `BlockPlan`：输出所选 Codec 及其参数。

第一版只让 Seed 选择**块级 Codec 与压缩参数**，沿用现有固定分块和 Store 回退机制。暂不同时引入动态分块、复杂搜索、线程调度和自适应缓存。

> **关键提醒**：现有块索引已经存储 Codec/配置等信息。加入 Seed 本身不会自动节省空间；应以实际生成的整个归档大小（含头部、索引、元数据）判断收益。

### 4.2 建立公平的压缩对照实验

每一组实验至少记录：

- 数据集名称、类型、原始大小及内容哈希；
- 操作系统、编译器、构建类型、CPU 与内存；
- Codec、压缩级别、Seed、策略版本和搜索预算；
- **完整归档大小**、压缩时间、解压时间、峰值内存；
- 解压正确性与重复运行的结果。

至少比较以下方案：

1. Store 基线；
2. 固定参数 Zstd；
3. 固定参数 LZMA2；
4. 简单、无 Seed 的块级策略；
5. Seed 决策策略；
6. 后续 M5 的有限预算 Seed 搜索。

应严格保持数据集、运行环境和搜索预算一致，避免只展示最优样本或忽略额外元数据开销。

### 4.3 不要过早优化压缩性能

此前项目记录中的一个合成样本显示，较慢的 LZMA2 配置并未比 Zstd 获得更小文件。单个样本不能推导一般结论，但说明**更高的计算成本不一定意味着更高的压缩收益**。

可将 Zstd-3 作为日常默认配置的候选方案；最终仍应由多类型基准数据决定。

### 4.4 保留安全边界

校验、解码比对、暂存输出、路径检查和提交前验证等机制都有安全价值。若发现性能开销，应先测量，再优化实现，不应直接移除保护。

此外，**CRC32C 可检测偶发损坏，但不提供针对恶意篡改的密码学认证**。如果未来定位为处理不可信来源的归档，应明确安全模型并评估是否需要认证机制。

## 5. 建议的开发路线

### M4-A：研究基线与协议（第一步）

**目标**：在修改归档格式前，建立可测量、可复现的基础。

- [ ] 编写 `docs/seed-strategy-v1.md`，明确所有序列化与确定性规则。
- [ ] 定义固定 Seed 测试向量，覆盖边界 Seed 与不同块 ID。
- [ ] 建立 `research/benchmarks/` 数据与脚本结构。
- [ ] 保存 M3 固定参数方案的基准结果。
- [ ] 确认旧归档的解码兼容策略。

**完成标准**：其他开发者能够只凭协议文档复现相同的块策略计划，且有可信的 M3 基线。

### M4-B：最小 Seed 策略引擎

**目标**：接入 Seed，而不破坏原有归档管线。

- [ ] 新建 `core/seed/strategy.hpp` 与 `.cpp`（实际目录遵循项目当前组织方式）。
- [ ] 为 `StrategyGenerator` 定义纯函数或无副作用接口。
- [ ] 将块级 Codec/参数决策与 I/O、索引写入、安全提取解耦。
- [ ] 保留压缩无收益时的 Store 回退。
- [ ] 确保同样的输入、Seed 和版本产生相同的计划。

**完成标准**：Seed 归档可执行完整的 `compress → verify → extract` 往返。

### M4-C：确定性、安全与兼容验收

- [ ] 验证固定 Seed 的策略输出跨多次运行一致。
- [ ] 检查不同编译器/构建配置下的测试向量。
- [ ] 确认 M3 旧归档仍然可读取。
- [ ] 正确拒绝未知版本、非法参数和损坏数据。
- [ ] 所有原有测试继续通过，新增 Seed 测试全绿。
- [ ] 将核心回归检查纳入 CI。

**完成标准**：满足下方的 M4 验收清单，再进入 M5。

### M5：有限预算的 Seed 搜索

- [ ] 先实现简单随机候选搜索，而非复杂优化器。
- [ ] 限定候选数量、CPU 时间或其他可计量预算。
- [ ] 与固定参数和简单块级策略进行同预算对照。
- [ ] 记录成功和失败样本，防止选择性报告。
- [ ] 若收益不稳定或成本过高，优先简化策略而非增加复杂度。

### GUI-1：稳定核心之上的图形界面

GUI 应在 M4 核心验收后开发，优先覆盖文件选择、压缩/解压进度、取消、错误展示与结果汇总。不要让 GUI 直接承载 Seed 算法和归档解析逻辑。

## 6. M4 验收标准

| 验收维度 | 验收标准 |
| --- | --- |
| 确定性 | 相同 Seed、策略版本与块元数据生成相同 `BlockPlan` |
| 正确性 | Seed 归档可压缩、校验、解压，内容逐字节一致 |
| 兼容性 | M3 格式的旧归档仍能正常读取 |
| 异常处理 | 未知版本、非法参数、损坏索引和截断数据正确失败 |
| 回归质量 | 现有自动化测试及新增 Seed 测试通过 |
| 可测量性 | 基准脚本、数据集说明与原始结果可重复执行 |

## 7. 最值得立刻落地的三个交付物

1. **`docs/seed-strategy-v1.md`**：明确版本、Seed 编码、PRNG、块 ID、参数约束及固定测试向量。
2. **`core/seed/strategy.hpp` + `.cpp`**：实现与文件 I/O 解耦的确定性块级策略生成器。
3. **`research/benchmarks/`**：固定数据集与 Store/Zstd/LZMA2 对照基准，统一实验记录格式。

同时建议将 GitHub Actions CI 作为与以上任务并行推进的工程保障。

## 8. 最终建议

**SeedArc 当前应从“继续堆功能”转为“建立可验证的 Seed 策略与实验体系”。**

- **继续保留**：现有 Core、归档格式、安全校验和测试基础。
- **立即推进**：M4-A（协议与基线）→ M4-B（最小 Seed 引擎）→ M4-C（兼容与确定性验收）。
- **延后处理**：复杂 Seed 搜索、多线程压缩、大规模格式重构、GUI。

最终要回答的核心问题是：

> **在相同的时间和内存预算下，可复现的 Seed 策略能否稳定地生成比成熟压缩器固定参数方案更小的完整归档？**

只有通过跨类型、可复现的实验回答这一问题，SeedArc 才能进一步建立独特的技术价值。
