# SeedArc B2-r2 评估与 B2-r3 真实压缩验收计划

> 状态：B2-r2 纯计划行为验证完成（依据提供的观察记录）；B2-r3 待实施。  
> 说明：本文件不代表已经完成真实压缩、搜索收益或性能测试，也不代表独立审计或复现结果。

## 1. 结论摘要

B2-r2 已基本验证**文件级 Zstd 等级覆盖**在纯计划层的关键行为：作用域隔离、全局与文件级叠加、清除后继承当前全局值、插入重排不误匹配、目标删除或重命名时显式失败、无匹配 Codec 时安全无变化，以及大文件的覆盖范围正确。

**建议保留文件级覆盖作为 B2 的主要控制粒度，暂不引入块段级、单块级或候选 C。下一阶段进入 B2-r3，重点转为真实压缩链路、解码兼容性和可复现基准。**

在集成前必须澄清：`delete-reindex` 场景显示“9 块，改变块 105”。`105` 如果是当前数组位置则无效；如果是非连续的逻辑 `block_id`，则可能合理。应将 `block_index`、`block_id`、`file_key` 明确区分。

## 2. B2-r2 观察记录与评价

以下均为**拟议计划变化**，并非实际压缩结果。

| 场景 | 块数 | 相对当前全局，被文件覆盖改变的块 | 观察与评价 |
| --- | ---: | --- | --- |
| `combined` | 12 | `5, 6` | 仅目标文件的 Zstd 等级变化，符合预期 |
| `insert-reorder` | 13 | `5, 6` | 目标覆盖未因插入和重排迁移，符合预期 |
| `delete-reindex` | 9 | `105` | 文件覆盖仍匹配目标路径；需明确 `105` 的 ID 语义 |
| `empty.txt` | 129 | 无 | 空文件作为显式清单项，合法编辑成功但无块变化 |
| `single.txt` | 129 | 无 | 目标文件只有 LZMA2 块，修改 Zstd 等级不改变计划 |
| `large.txt` | 129 | 共 41 个目标 Zstd 块 | 大文件范围覆盖符合预期，需在真实负载下评估成本 |

`large.txt` 观察到的变化块：

```text
1, 3, 5, 6, 8, 14, 18, 21, 22, 23, 27, 29, 30, 33, 36, 37, 41,
49, 52, 57, 60, 62, 68, 70, 71, 75, 78, 83, 87, 91, 93, 97, 98,
99, 105, 109, 113, 114, 116, 117, 123
```

另有 10,000 块单文件单测，但当前没有峰值内存、生成耗时等性能数据，不能推断扩展性能。

### 2.1 叠加和清除语义

选中文件 `dir/b.txt` 的 Zstd 块 `5/6`：

```text
基础等级 3 → 全局等级 4 → 文件覆盖等级 6 → 清除覆盖后等级 4
```

其他文件的 Zstd 块 `1/3/8`：

```text
基础等级 3 → 全局等级 4 → 文件覆盖期间仍为 4 → 清除后仍为 4
```

因此，建议固定优先级：

```text
基础 Seed 计划 < 当前全局编辑 < 文件级覆盖
```

**清除文件级覆盖**的语义是“移除局部设置并继承*当前*全局值”，不是强行回到最初基础等级。

### 2.2 文件身份行为

- 插入或重排但保留原全局 ID：原 12 块的拟议计划保持一致。
- 删除其他文件并重编号：路径覆盖仍仅匹配 `dir/b.txt`，但基础 Codec 可随全局 ID 变化。
- 删除或重命名覆盖目标：旧覆盖明确失败，不会误迁移到其他文件。

这些结果证明了**覆盖目标匹配的稳定性**，但还没有证明**基础 Seed 计划在重编号后的稳定性**。

## 3. 需要明确的协议决策

### 3.1 区分三个标识

| 名称 | 推荐含义 | 核心约束 |
| --- | --- | --- |
| `block_index` | 当前块清单中的位置 | 范围为 `0..N-1`，可能因插入/删除改变 |
| `block_id` | 用于策略生成的逻辑块标识 | 可以不连续；如用于确定性派生，应规定稳定性规则 |
| `file_key` | 文件级覆盖的匹配键 | 推荐规范化归档内相对路径；规定大小写、分隔符与重命名语义 |

**待确认项：**`delete-reindex` 中的 `105` 究竟是 `block_id` 还是 `block_index`。如为前者，在输出中应改标为“逻辑块 ID”；如为后者，应修正生成/报告逻辑。

### 3.2 明确两类稳定性

1. **覆盖身份稳定**：其他文件的增删或重排不应让 `dir/b.txt` 的覆盖错误地应用到别的文件。
2. **基础计划稳定**：当目标文件内容及文件内块编号不变时，其他文件变化是否允许改变该文件的基础 Codec 计划？

建议：长期可研究使用稳定 `file_key`（或其规范化派生标识）和文件内块编号进行 Seed 派生，减少对全局编号的依赖。但**不要未经评估就变更现有映射**：先固定当前行为、增加对照测试，并明确新旧策略版本的兼容规则。

### 3.3 覆盖与归档元数据

需要区分：

- **编辑层**：用户如何配置全局与文件级覆盖。
- **策略生成层**：Seed 与文件/块标识如何形成具体 `BlockPlan`。
- **归档解码层**：提取端需要哪些 Codec、配置和参数信息才能解码。

原则：**提取时不依赖重新运行不确定性搜索**。归档应包含足以完成解码的具体 Codec/配置描述；是否还保存原始 Seed、覆盖策略及其版本，应以复现、研究和元数据开销需求来决定。不要在这轮直接冻结最终二进制格式。

## 4. 为什么暂不继续细化控制粒度

| 粒度 | 适合用途 | 当前判断 |
| --- | --- | --- |
| 全局 | 默认策略、对照基线 | 保留 |
| **文件级** | 用户可理解的局部调整、受控研究 | **作为 B2 主要粒度** |
| 块段级 | 大文件内局部优化 | 等真实压缩数据证明有需求后再评估 |
| 单块级 | 调试、搜索研究 | 暂不作为面向用户的主控件 |

文件级覆盖既解决了全局等级调整过粗的问题，又避免过早引入大量块级参数。但这仍然只是**功能性结论**，不能推出压缩率更高。

## 5. B2-r3：真实压缩集成与验收计划

### 阶段 A：冻结行为契约

- [ ] 澄清 `105` 的 ID 语义，统一日志与测试输出字段。
- [ ] 固定 `file_key` 规范化规则，以及删除/重命名目标后的失败行为。
- [ ] 固定优先级：基础计划 → 全局编辑 → 文件级覆盖。
- [ ] 固定清除语义：恢复**当前**全局策略。
- [ ] 明确无目标 Codec 时的行为：合法但不改变对应块计划。
- [ ] 明确全局重编号是否允许影响基础策略，以及版本兼容方案。

### 阶段 B：接入真实压缩链路

- [ ] 使用真实文件生成分块，不再仅依赖假设 `BLOCKS`。
- [ ] 将 B2 的结果传给实际压缩器，确认使用的 Codec 与 level 符合计划。
- [ ] 运行 `compress → verify → extract`，并对提取文件逐字节比对。
- [ ] 覆盖文本、源码、二进制、已压缩文件、混合目录及空文件。
- [ ] 验证无收益时的 Store 回退；记录“计划 Codec”与“实际归档 Codec”差异。
- [ ] 验证文件级覆盖不会改变非目标文件的**配置计划**；注意真实归档偏移、索引布局等整体字节仍可能变化。

### 阶段 C：兼容性与异常处理

- [ ] 旧归档仍可验证与提取。
- [ ] 新归档仅依靠保存的解码所需信息即可提取，无需重跑搜索。
- [ ] 非法策略版本、错误参数、截断或损坏的元数据能够明确报错。
- [ ] 路径安全校验、暂存提交等既有保护不因 B2 集成而退化。
- [ ] 相同输入、版本、参数和环境下生成一致的策略计划；如声明跨平台归档字节完全确定，另行做跨平台验证。

### 阶段 D：建立最小可复现基准

对每类样本分别测量至少以下方案：

1. 固定全局 Zstd-3。
2. 固定全局 Zstd-6。
3. 固定全局 LZMA2-6。
4. 全局等级调整（不启用文件覆盖）。
5. B2 文件级覆盖（记录覆盖选择理由及配置）。

至少记录：

| 指标 | 要求 |
| --- | --- |
| 完整归档字节数 | 包括头部、索引、Seed/策略元数据及各块数据 |
| 压缩时间 | 标明是否包含策略生成及候选搜索时间 |
| 验证/解压时间 | 保持测量口径一致 |
| 峰值内存 | 明确测量工具与环境 |
| 输入规模与文件类型 | 记录文件数量、总大小、真实块数 |
| 运行环境 | 编译器、构建模式、依赖版本、CPU、线程数 |
| 结果复现 | 保存数据集标识、参数、策略版本和原始日志 |

第一轮只需先确认 B2 真实链路正确，不应基于单次样本判断压缩收益。进入 A/B 搜索效率比较时，再控制候选数量或墙钟时间预算，使对照公平。

## 6. B2-r3 验收门槛

**功能验收（必须全部通过）**

- [ ] 文件身份/块标识语义已文档化，`delete-reindex` 歧义已消除。
- [ ] 全局与文件级覆盖叠加、清除、空文件和无目标 Codec 行为与 r2 一致。
- [ ] 真实文件压缩、验证、解压、逐字节比对成功。
- [ ] Store 回退、旧归档兼容、错误版本和异常输入测试通过。
- [ ] 现有测试套件通过，新增 B2 集成测试纳入持续集成。

**研究数据验收（用于进入后续搜索阶段）**

- [ ] 至少建立可重跑的多类型样本基线。
- [ ] 记录完整归档大小、压缩/解压时间与峰值内存。
- [ ] 将“功能正确性”与“压缩收益”分开汇报。
- [ ] 若搜索策略参与对照，明确并统一搜索预算。

## 7. 决策记录与不做事项

**本轮建议决定：**

1. 保留 B2 文件级等级覆盖，不扩展成块段级或单块级编辑。
2. 先解决标识语义和协议边界，再连接真实压缩链路。
3. 不根据拟议计划变化数量推断压缩率、性能或搜索优劣。
4. B2-r3 通过后，利用真实数据判断是否需要更细粒度或候选 C。

**本轮明确不做：**

- 不宣布 B2 比 A 更省空间或更高效。
- 不把实验编辑字段直接定为最终归档种子编码。
- 不把 10,000 块单测等同于完成性能测量。
- 不为尚未测量的性能热点进行大规模重构。

---

## 最终判断

**B2-r2 的文件级控制颗粒度已经足够用于第一版实际压缩实验。** 最有价值的下一步是完成 `block_id` / `block_index` / `file_key` 的语义澄清，随后进行真实 `compress → verify → extract` 集成测试。实际归档字节数、时间和内存的可复现数据，应成为是否扩展粒度及开展 Seed 搜索的依据。
