# SeedArc：B2-r4 结果评估与 B2-r5 实施计划

> **状态**：B2-r4 P0 诊断与基线对照完成（依据实验报告）；B2-r5 为待执行建议。  
> **日期**：2026-11-12  
> **适用范围**：Codec 分配、文件级等级覆盖、低成本自适应压缩与公平预算评估。  
> **证据基础**：`B2-r4 P0：逐块诊断与简单 Codec 分配基线`（DEV-009，2026-11-12）。以下“通过”指报告记录的结果，不代表本文作者独立重跑。

## 1. 执行摘要

**建议结束 B2-r4 P0 的诊断阶段，启动 B2-r5：低成本文件级 Codec 选择与公平预算实验。** 当前重点不应是扩大随机 Seed 搜索空间，而是证明简单、可复现且受成本约束的选择器，能否接近试压缩 Oracle 的归档大小。

B2-r4 解决了此前 text / mixed 压缩差距的主要归因：

- 与固定 Zstd-3（B1）相比，旧 B-r1（B0-current）在 **text** 上多 **65,594 B**，其中 **65,450 B（99.78%）** 来自将一个高度可压缩的文本块直接计划为 Store，**未尝试压缩**。
- 在 **mixed** 上多 **66,903 B**，其中计划 Store 带来 **66,759 B（99.78%）**；该部分包括高度可压缩文本块与可进一步压缩的 gzip 文件。注：报告中确有部分噪声或极小文件计划 Store，但对大小差距贡献为 0。
- 其余差异主要来自该样本中 LZMA2-6 与 Zstd-3 的块级结果；Zstd-4 相比 Zstd-3、归档头部和索引没有造成上述两个数据集的差距。
- B1-fixed-zstd3 已回收 text / mixed 上 B0 的全部空间损失；B2-file-codec 也达到同样大小，但采用了额外的编码侧试验。

**设计原则**：默认情况下，Store 应优先作为“尝试压缩后无空间收益”的回退，而非由与内容无关的随机分配直接选中；若将来希望主动跳过压缩，需要有经验证的特征或成本依据。

## 2. 本轮实验边界与工程可信度

实验复用 B2-r3 的五组磁盘输入（`text`、`mixed`、`source`、`binary`、`compressed`），逐文件 SHA256 与前一轮一致；固定 64 KiB 分块、单线程、统一归档字节计量。报告记录 **10 方案 × 5 数据 × 3 次重复**，总计 **150/150 次 compress → verify → extract 且逐字节还原**。

工程检查（据实验报告）：

| 项目 | 结果 |
| --- | --- |
| 完整归档对账 | 50/50 组通过；`archive_bytes = 96 B 头部 + data_bytes + index_bytes` |
| 旧方案一致性 | 8 个原方案、40 组归档与 B2-r3 的 SHA256 一致 |
| MSVC Release CTest | 35/35 通过，构建 0 警告 |
| MSVC ASan Release CTest | 35/35 通过，无 ASan 报告 |
| Clang UCRT64 Debug 定向构建 | 通过，0 警告 |
| `file-plan` 负面输入 | 11 项均按预期拒绝，失败后无归档 |
| GCC / UBSan / Fuzz / 非 Windows | 本轮未执行 |

**限制**：数据仍是自制样本与项目源码，未使用独立语料；每组仅 3 次，未控制缓存、预热和系统波动；时间是包含启动、计划、自检、输出的进程墙钟，当前不能据细小差异作性能断言。Seed / 覆盖字段尚未序列化（归档头部 `strategy_version=0`、`seed_length=0`），未来需要序列化的方案必须另计元数据成本。

## 3. 主要归档大小结果

单位：**完整归档字节（bytes），越小越好**。

| 数据集 | B0-current | B1-fixed-zstd3 | 固定 Zstd-6 | 固定 LZMA2-6 | B-file（旧覆盖） | B2-file-codec（仅 Codec） | B2-file-codec（含等级选择） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| text | 66,538 | 944 | 944 | 1,379 | 66,538 | 944 | **944** |
| mixed | 461,862 | 394,959 | 394,959 | 395,403 | 461,862 | 394,959 | **394,959** |
| source | 9,560 | 9,503 | 8,835 | 8,304 | 8,893 | 8,300 | **8,298** |
| binary | 393,646 | 393,646 | 393,646 | 393,646 | 393,646 | 393,646 | **393,646** |
| compressed | 393,834 | 393,834 | 393,834 | 393,834 | 393,834 | 393,834 | **393,834** |

### 3.1 text / mixed：B0 的主要问题是“跳过压缩”

| 数据集 | B0 - B1 差值 | 计划 Store 的差值 | 所占比例 | 其他差值 |
| --- | ---: | ---: | ---: | ---: |
| text | +65,594 B | +65,450 B | 99.78% | +144 B |
| mixed | +66,903 B | +66,759 B | 99.78% | +144 B |

对于 text，一个 64 KiB 的高重复文本块在 B0 中被直接写为 65,536 B，而 B1 将其压缩至 86 B。B0 的 `hash mod 3` 分配与内容无关，这种机制不适合作为面向实际压缩效果的默认 Codec 调度。

### 3.2 source：B2 能压得更小，但 Oracle 成本不可忽略

| 方案 | 完整归档 |
| --- | ---: |
| B1-fixed-zstd3 | 9,503 B |
| 固定 LZMA2-6 | 8,304 B |
| B2-file-codec（仅 Codec） | 8,300 B |
| B2-file-codec（含等级选择） | **8,298 B** |

B2 相比固定 LZMA2-6 仅减少 **6 B，约 0.07%**；本轮文件级 Zstd 等级覆盖的额外贡献为 **2 B**。这反映出按文件选择 Codec 确实可行，但不足以证明实际效率优于固定算法——B2 的选择需要多次试编码，不能只看最终写出的归档大小。

### 3.3 binary / compressed：没有观察到空间差异

所有方案完整归档大小相同，现有输入中的压缩无收益块按规则回退 Store。该结果支持回退正确性，但不足以推广至所有二进制或已压缩文件。

## 4. 对三类策略的重新定位

| 策略 | 定位 | 建议 |
| --- | --- | --- |
| **B0-current** | 历史/负面对照；展示无内容依据的随机 Store 分配问题 | 保留回归，不再作为推荐默认方案 |
| **B1-fixed-zstd3** | 简单、无 Codec 决策搜索的实用基线 | 作为 B2-r5 主基线；坚持 Store 回退 |
| **B2-file-codec** | 编码侧 Oracle：用多个真实试编码结果选优 | 作为空间参考上限，计入全部搜索成本；暂不当作低成本自动策略 |
| **Adaptive-file（待实现）** | 有预算的文件级选择器 | B2-r5 主研究对象；尽可能接近 Oracle，避免过度试压缩 |

> **不要将 B2 Oracle 误称为低成本智能算法或 Seed 搜索**。它使用当前 run 中 Zstd-3、Zstd-6、LZMA2-6 的真实结果作选择，报告估算成本约相当于额外三次完整压缩。现有块索引已记录实际 Codec/config，因此解码无需重跑选择；但未来若要保存 Seed 或编辑覆盖本身，仍须设计并计量相应字段。

## 5. 下一阶段：B2-r5 实施路线

### P0-A：冻结可复现基线

目标：保证后续“改进”可以被严格归因。

- [ ] 固定实验所用源码提交 / patch、编译配置、依赖版本、数据集哈希、工具二进制哈希。
- [ ] 保留 B2-r4 的 `raw.json`、`blocks.jsonl/csv`、`summary.json`、`attribution.json`、`file-codec-trials.json` 与计划文件。
- [ ] 对照重跑 B1、固定 LZMA2-6、B2 Oracle，确保完整归档大小及可复现哈希与既有记录符合预期。
- [ ] 将历史 B0 结果作为诊断回归，不再让它主导后续“自动策略是否有价值”的结论。

### P0-B：实现最小低成本文件级选择器

**建议第一版采用简单、可解释的方案，而非复杂机器学习。**

1. 默认每个文件使用 **Zstd-3**，逐块无收益时回退 Store。
2. 当文件达到最低大小阈值时，从文件中按**固定规则**选取少量代表块；避免只取首块导致误判，可从开头/中间/结尾抽样，但必须可复现。
3. 在规定的候选集合与预算内，比较 Zstd-3 与 LZMA2-6（有明确收益时再尝试 Zstd-6）。
4. 仅当预计能节省的空间**足以抵消可能增加的元数据与成本**时，才切换整个文件的策略；否则保持 Zstd-3。
5. 文件为空、只有一种无收益数据、预算耗尽、试编码失败时，采取确定性的安全回退，并记录原因。

**设计约束**：先冻结文件级控制粒度，不引入块段级新编辑字段；决策层输出既有 `BlockPlan`，尽量不改动安全敏感的编码、解码、归档索引与提交路径。

建议记录的决策证据：

| 字段 | 用途 |
| --- | --- |
| `file_key`, `file_block_index` | 文件身份与样本定位 |
| `selector_version`, `selected_codec`, `selected_level` | 可复现的决策语义 |
| `sampled_blocks`, `trial_codec`, `trial_level` | 试编码数量和候选 |
| `trial_input_bytes`, `trial_output_bytes` | 估计收益的依据 |
| `trial_cpu_ms`, `trial_wall_ms` | 决策开销 |
| `budget_limit`, `budget_used`, `decision_reason` | 预算与可解释性 |
| `archive_bytes`, `metadata_bytes` | 最终净收益与格式成本 |

> 这些字段可先存在研究证据文件中，**不代表都应写入归档**。归档的解码必要字段、策略复现字段、研究诊断字段要分开设计。

### P0-C：统一试编码与压缩预算

**比较原则：计入为了作出选择而付出的所有成本。**

比较以下四个主要方案：

1. **Fixed Zstd-3**：实用基线。
2. **Fixed LZMA2-6**：较高压缩率参考配置。
3. **Adaptive-file**：有限试编码预算的候选优化器。
4. **Oracle-file**：完整多配置试编码的参考上限，不代表相同成本级别。

每个方案记录：

- 完整归档字节数（头部 + 索引 + 数据 + 实际需要的策略元数据）；
- 决策/试编码耗时、最终编码耗时、两者合计墙钟与 CPU 时间；
- 解压耗时、峰值工作集或峰值内存（口径写清）；
- 测试过的候选数量、编码过的总输入字节量、预算耗尽次数；
- 成功解压与原文件逐字节一致、输出哈希一致性。

至少给 Adaptive-file 设置一个**显式、可重复的试编码次数或采样字节预算**；后续可以增加多档预算形成“归档大小—总时间”曲线。不要将 Oracle 的候选测试时间剔除后与 B1 直接比较。

### P1-A：独立数据与防过拟合

- [ ] 引入独立来源的源码、日志、JSON/CSV 等结构化文本、图片、常见压缩格式和中大型混合目录。
- [ ] 为策略开发集与最终评估集预先分组，禁止根据最终评估集逐文件调参。
- [ ] 兼顾极小文件、空文件、单一巨型文件、目录层级较深的情况。
- [ ] 将每个数据集原始字节、文件数、块数及内容类型与许可证/获取方式记录在 manifest。
- [ ] 单独列出失败或无收益的样本，不只汇总获胜案例。

### P1-B：确定性、身份稳定与元数据边界

- [ ] 在同一工具/依赖版本下，固定文件与配置得到相同 `BlockPlan` 与归档哈希。
- [ ] 文件重排、插入、删除测试：文件级选择以稳定的规范化 `file_key` 为匹配依据，避免因全局 `block_id` 变化误关联覆盖。
- [ ] 确认新策略不要求解码端重新搜索或试编码。
- [ ] 明确选择器状态属于“编码时决策”还是“需要长期复现的 Seed 语义”；前者未必需要归档化，后者需要版本化和序列化设计。
- [ ] 如果以后增加 Seed/覆盖元数据，基准记录必须实际计入其字节成本，禁止将“尚未序列化”记成零成本。
- [ ] 保留旧归档读取、安全路径校验、故障注入、Store 回退等既有回归。

## 6. 建议验收门槛（B2-r5）

| 维度 | 验收条件 |
| --- | --- |
| 正确性 | 所有候选通过 compress → verify → extract，逐字节还原 |
| 复现性 | 固定数据、版本、配置及预算产生一致决策；不一致须记录原因 |
| 预算控制 | 试编码次数 / 字节量与时间被完整统计，并能在预算耗尽时确定性回退 |
| 公平性 | 选择成本与最终压缩成本合并报告；Oracle 明确标为参考上限 |
| 归档核算 | 完整归档大小严格对账；未来的必要元数据计入大小 |
| 独立评估 | 开发数据与评估数据分离，展示分数据集表现及无收益案例 |
| 工程回归 | 现有测试、非法计划输入、安全提取和旧格式兼容保持通过 |
| 研究结论 | 同时报告相对 B1 的空间改善与成本增量；不只报告最小字节数 |

**通过标准建议**：B2-r5 交付一个可以复现、预算明确、正确性无回归的 Adaptive-file 原型及完整基准报告。**不预设必须优于 Zstd-3**；若低成本方案不能稳定产生净收益，也应如实记录，并据此决定是否继续 Seed 搜索。

## 7. 推荐架构与暂缓事项

```text
输入文件及固定分块
       │
       ▼
策略决策层
  ├── Fixed Zstd-3
  ├── Adaptive-file（有限预算）
  └── Oracle-file（研究参考）
       │
       ▼
BlockPlan（file_key、块、Codec、等级）
       │
       ▼
现有生产压缩核心
  ├── 真实编码与 Store 回退
  ├── 校验和索引
  └── 安全归档 / verify / extract
```

当前**暂缓**：新块段粒度、复杂随机 Seed 搜索、GUI、大规模并行优化、归档格式冻结。只有在真实语料与公平预算评估支持其价值时再升级优先级。

## 8. 最终决策

**B2-r4 的问题定位已经足够明确：旧随机分配把可压缩块直接放入 Store，是 text / mixed 的主要空间损失来源。** 简单的 B1 已消除损失。B2 Oracle 在 source 样本上进一步减少少数字节，但为此付出了额外试编码成本。

下一步应当优先回答：

> **在相同、明确计量的资源预算内，低成本文件级 Codec 选择能否在独立数据上比固定 Zstd-3 更划算，并接近 Oracle 的归档大小？**

如果答案是肯定的，继续研究可复现 Seed 策略才具备更扎实的工程与实证依据；如果答案是否定的，保留固定 Zstd + Store 回退作为可靠默认方案仍然是有价值的结果。
