# SeedArc 项目代码审查与优化建议

- **项目地址：** https://github.com/vusiif/SeedArc
- **审查日期：** 2026-11-11
- **审查方式：** 基于前述公开源码与文档的静态分析；未独立完成本地克隆、编译、测试或漏洞复现。

> **结论摘要：** SeedArc 的研究方向值得继续，但当前更重要的是完成可靠的归档闭环，而非提前优化压缩算法。优先处理归档解析和安全恢复的端到端设计、资源预算模型以及文档状态一致性；随后再通过可复现基准判断种子搜索是否具有真实压缩收益。

## 一、项目现状与总体判断

SeedArc 使用 C++23，目标是通过版本化种子生成压缩策略，组合成熟压缩算法，并在有限计算预算内寻找更小的**完整归档**。

根据前述审查时看到的公开代码与文档：

| 里程碑 | 状态 | 说明 |
|---|---|---|
| M0 | 已建立 | 工程框架与基础设施 |
| M1 | 已有实现与验收记录 | 实验归档头部、块布局校验、路径校验、Windows 安全写入原语 |
| M2 | 待完成 | 完整 Store 归档的打包、索引解析、验证和恢复 |
| M3 | 待完成 | Zstd / LZMA2 编解码 |
| M4 | 待完成 | 确定性种子和可用 MVP |
| M5 | 后续研究 | 搜索策略、压缩收益与性能实验 |

CLI 目前主要支持帮助和版本查询；压缩、解压等用户功能尚未形成完整可用流程。

现阶段应优先保证：

1. **安全 I/O 的边界正确性**：异常退出、冲突路径、恢复失败不应损坏现有用户数据。
2. **归档格式和资源限额的一致性**：不可信输入必须受完整的资源预算约束。
3. **种子搜索的实际收益**：判断搜索成本是否换来了完整归档体积的可重复改进。

## 二、问题与优化优先级

| 优先级 | 位置 | 发现 / 建议 |
|---|---|---|
| P1 | `core/filesystem/safe_output.cpp` | 单文件安全提交已有实现；M2 仍需设计整次解压的失败清理与事务语义。 |
| P1 | `core/archive.cpp` | 已有头部和块布局校验；完整索引、文件到块映射和 payload 验证仍需补齐。 |
| P1 | `README.md`、`STATUS.md`、开发文档 | M1 进度描述不一致，应统一状态来源。 |
| P2 | `core/include/seedarc/archive.hpp` | 单项限额已有，但建议建立统一的累计资源预算模型。 |
| P2 | `safe_output.hpp/.cpp` | 单次写入大小受 4 MiB 限制，后续应采用有界流式写入。 |
| P2 | `error.hpp` | 用户主动取消与真实 I/O 失败的错误码应分离。 |
| P2 | 构建与测试 | 建议将多工具链测试、端到端测试和故障注入持续集成。 |
| P3 | `core/archive.cpp` | CRC32C 逐位计算可优化；应先测量瓶颈再实施。 |

> **注意：** 上表同时包含当前可确认的问题和未来里程碑的设计风险。尚未实现的功能本身不等于当前存在可利用的漏洞。

### 2.1 安全写入：需要升级为完整解压事务（P1）

**代码位置：** [safe_output.cpp](https://github.com/vusiif/SeedArc/blob/main/core/filesystem/safe_output.cpp)

现有 `write_new_file()` 已考虑临时文件、CRC 校验、Flush、读回验证及无覆盖提交，适合作为单文件安全写入原语。

但若未来一次解压需要输出 100 个文件，前 70 个成功，第 71 个因磁盘空间不足失败，单文件原语并不会自动撤销之前成功写出的文件。

**建议：**

- **解压到新目录：** 尽可能先在受控临时目录中完成全部文件恢复和完整性验证，然后以无覆盖方式提交整个目录。
- **解压到已有目录：** 使用创建清单记录本次创建的文件、目录；失败时仅清理可证明属于本次操作的对象。
- 明确区分**原子提交**与**尽力回滚**：对于已有目录，多文件操作通常不能保证与单次目录重命名相同的原子性。
- 加入磁盘满、取消、权限变化、路径冲突及异常中断的故障注入测试。

**预期收益：** 避免解压失败后留下难以识别的部分结果，降低用户数据损失和清理误删风险。

### 2.2 归档解析：形成完整、统一的验证路径（P1）

**代码位置：** [archive.cpp](https://github.com/vusiif/SeedArc/blob/main/core/archive.cpp)

目前的 `validate_block_layout()` 可校验调用方提供的块描述符，例如偏移、重叠、长度、总输出及 codec ID，但它尚不等同于完整的归档索引解析。

建议统一处理流程：

```text
读取固定头部
    ↓
验证格式版本、字段范围、整数运算及基础预算
    ↓
解析索引和文件条目
    ↓
验证路径、重复项、文件/块映射、全部引用和范围
    ↓
按资源预算有界解码
    ↓
验证输出长度、校验和及完整性
    ↓
安全写入并提交
```

**重点校验项：**

- 索引长度、字段数量、偏移和加法/乘法是否溢出。
- 文件路径是否安全，是否有大小写折叠或规范化后冲突。
- 是否存在重复文件条目、重复块引用、悬空引用、块重叠或未声明的数据区域。
- 解码后的每块及累计输出长度是否符合声明与限制。
- 解码器不应根据不可信输入进行无限制内存分配。
- `verify` 与 `extract` 应共享解析和完整性校验逻辑，仅在输出动作上分叉。

### 2.3 项目状态文档存在冲突（P1）

涉及文件：

- [`STATUS.md`](https://github.com/vusiif/SeedArc/blob/main/STATUS.md)
- [`README.md`](https://github.com/vusiif/SeedArc/blob/main/README.md)
- [`docs/development-plan.md`](https://github.com/vusiif/SeedArc/blob/main/docs/development-plan.md)
- [`docs/m1-validation.md`](https://github.com/vusiif/SeedArc/blob/main/docs/m1-validation.md)
- [`cli/main.cpp`](https://github.com/vusiif/SeedArc/blob/main/cli/main.cpp)

前述审查发现，`STATUS.md` 将 M1 标注为完成验收，但 README、开发计划和 M1 验证文档仍保留较早状态；CLI 的未实现提示也沿用 M0 描述。

**建议：**

1. 以 `STATUS.md` 作为当前里程碑的唯一状态来源。
2. README 只保留简短进度摘要和 `STATUS.md` 链接。
3. 验证文档若属于历史记录，应注明“验证当时状态”，而不是默认为当前进度。
4. CLI 中的提示语改成不依赖某个里程碑名称的描述，或随发布版本自动同步。

这是投入小、收益高的调整，尤其有利于多人及 AI Agent 协作。

### 2.4 资源限制：统一累计预算（P2）

**代码位置：** [archive.hpp](https://github.com/vusiif/SeedArc/blob/main/core/include/seedarc/archive.hpp)

前述代码中的默认值包括：

| 参数 | 默认上限 |
|---|---:|
| 索引区 | 16 MiB |
| 文件条目 | 100,000 |
| 块数 | 1,000,000 |
| 数据区 | 8 GiB |
| 单块 | 4 MiB |

这些上限不能简单视为能够同时达到。例如每个块如果至少消耗 48 字节索引空间，则 100 万块仅最小块记录就约占 **45.8 MiB**，超过了 16 MiB 的索引区上限。现有组合约束已经能够拒绝不一致配置，因此这不是已确认的整数溢出漏洞。

**建议：**

- 对最大索引大小、文件数、块数和记录最小大小建立明确、可解释的相互约束。
- 增加累计内存、总解码输出、文件句柄、临时磁盘空间和运行时资源限额。
- 明确每项预算在哪个阶段扣减，并确保错误路径能够正确释放资源。
- 用边界测试验证“刚好等于上限”和“上限 + 1”等情况。

### 2.5 大文件处理与错误码（P2）

**代码位置：** `safe_output.hpp/.cpp`、`error.hpp`

当前 `write_new_file()` 要求调用者提供完整内容缓冲并限制单次写入大小为 4 MiB。它适合 M1 原型，但不适合作为最终的大文件恢复接口。

**建议将内部接口演进为有界流式会话：**

1. 创建受控临时文件。
2. 逐块解码并写出，同时增量计算校验值。
3. 每块、每文件及总体积都执行预算检查。
4. 验证成功后再执行无覆盖提交。
5. 取消、错误、崩溃恢复分别定义清理规则。

此外，用户主动取消目前被归入 `io_error`。建议引入独立的 `cancelled` 错误码，以便未来 CLI、GUI 和自动化客户端准确区分取消与真正故障，而不必解析错误文本。

### 2.6 测试、CI 和 CRC32C 优化（P2–P3）

前述项目记录包含 MSVC、GCC、Clang、ASan 和短时 Fuzz 测试，但本次没有独立复跑这些测试。

建议引入 GitHub Actions，至少覆盖：

- Windows / Linux 核心构建与 CTest。
- Release、Debug 和可用平台上的 sanitizer 任务。
- 故障注入：磁盘写入失败、取消、路径冲突、权限失败。
- 归档往返：空归档、空文件、多个小文件、大文件、损坏索引及截断数据。
- 格式解析 Fuzz 和回归样本存档。

CRC32C 当前采用逐位处理。可在基准测试确认它是热点后，尝试查表或 SSE4.2 硬件实现，并保留跨平台软件回退。

## 三、压缩算法层面的关键研究风险

SeedArc 最关键的创新假设是：**版本化种子产生的策略，是否能在相同计算预算下，稳定改善完整归档大小。**

需要特别区分：

- 伪随机种子可以紧凑地描述压缩策略。
- 它并不会直接增加原始数据的可压缩性。
- 更多候选尝试可能得到更优结果，也可能只是消耗 CPU、内存和运行时间。

建议至少设置以下实验对照：

| 实验组 | 目的 |
|---|---|
| 单一算法、固定参数 | 基础压缩基线 |
| 逐块选择最优编码器 | 验证混合编码是否有收益 |
| 随机种子搜索 | 验证搜索本身的收益 |
| 结构化种子搜索 | 验证结构化策略是否优于简单随机搜索 |

所有方案应控制：

- 输入数据集和划分方式。
- 总搜索时间、CPU 线程数、内存预算。
- 压缩库版本、构建选项与运行环境。
- **完整归档大小**，包括头部、索引、种子、字典及其他元数据。
- 解压速度、峰值内存和重复运行的稳定性。

建议预先设置可证伪的研究判据：如果结构化种子在多个代表性数据集和相同预算下不能稳定超过固定参数或随机搜索，应优先重新审视种子到策略的映射，而非继续增加搜索复杂度。

## 四、建议开发路线

### 阶段 1：低成本一致性修复

- [ ] 统一 `STATUS.md`、README 和里程碑文档。
- [ ] 为取消动作增加独立错误码。
- [ ] 明确 M2 的归档、事务和资源限制设计约束。

### 阶段 2：完成 M2 Store 归档闭环

- [ ] 完整索引序列化与解析。
- [ ] 安全路径、冲突、块引用与完整性校验。
- [ ] 大文件有界流式读写。
- [ ] 新目录提交与已有目录失败清理策略。
- [ ] `pack`、`verify`、`extract` 端到端测试。

### 阶段 3：自动化质量保障

- [ ] 建立 Windows / Linux CI。
- [ ] 增加故障注入、异常中断和损坏归档测试。
- [ ] 持续保存 Fuzz 发现的回归样本。

### 阶段 4：完成 M3 编码器集成

- [ ] 集成 Zstd、LZMA2。
- [ ] 确保 Store / Zstd / LZMA2 的确定性往返和预算保护。
- [ ] 建立单算法、逐块择优的性能基线。

### 阶段 5：M4/M5 种子与搜索研究

- [ ] 固化种子版本与策略映射。
- [ ] 比较固定参数、逐块择优、随机搜索和结构化搜索。
- [ ] 依据压缩率、时间与内存数据决定优化重点。

## 五、最终结论

**当前最值得投入的不是大规模架构重构、GUI 或复杂搜索算法，而是 M2 的完整归档闭环。**

现有源码已经在整数边界、安全路径、Windows 无覆盖写入和单文件故障处理方面体现了比较谨慎的设计。但这并不能等同于完整归档系统的安全性已经得到验证，因为面向不可信归档的端到端解码和恢复流程尚未完成。

推荐顺序为：

**同步文档与错误模型 → 完成 M2 → 引入持续集成与故障测试 → 完成 M3 → 用真实实验评价 M4/M5 的种子策略。**
