# SeedArc 第一轮种子计划对照评估与下一轮实验建议

> 文档类型：设计评估 / 实验规划  
> 日期：2026-11-12  
> 状态：建议稿，尚未决定最终种子编码或归档格式

## 1. 结论摘要

第一轮实验的方向合理：先验证**输入字段变化是否产生可理解、可预测的计划变化**，再开展压缩率和搜索效率实验，避免把“计划有变化”误判为“压缩效果更好”。

建议：

1. **保留 A（随机块级计划）**：作为未来自动搜索的候选生成器，而非主要的手动编辑方式。
2. **保留 B（Codec + Rank）**：作为可控策略和基准对照的基础，优先扩展为**全局默认 + 文件级覆盖（B2）**。
3. **暂缓精细块段控制（B3）和新的候选 C**：先确认用户是否真正需要细粒度调整，以及文件级策略能否满足主要场景。
4. **分开测试可用性、正确性和性能**：本轮观察不能用来判断 A 与 B 的压缩率、搜索效率或公平优劣。

> 核心方向：让 SeedArc 能自动探索压缩策略，同时做到**可复现、可比较、可解释**。

## 2. 第一轮实验：已知事实与限制

### 2.1 实验条件

- 所有字段是**候选 r1 实验编辑格式**，不是最终归档种子或编码。
- `BLOCKS` 为假设的固定 12 块清单，不读取真实文件。
- 两组都只生成了**拟议压缩计划**，没有执行实际压缩或解压。

### 2.2 观察结果

- **A**：`value` 从 `0` 改为 `1`，12 块中 **10 块**的拟议计划变化。
- **B**：`codec` 保持 `0`，Zstd `rank` 从 `2` 改为 `3`（实际等级 `3 → 4`），LZMA2 `rank` 保持 `6`；12 块中 **5 块**发生变化，均为原来的 Zstd 块，Codec 分配不变。

| 块编号 | A 修改前 | A 修改后 | B 修改前 | B 修改后 |
| --- | --- | --- | --- | --- |
| 0 | lzma2-2 | store | lzma2-6 | lzma2-6 |
| 1 | zstd-2 | zstd-2 | zstd-3 | zstd-4 |
| 2 | store | zstd-14 | store | store |
| 3 | zstd-9 | store | zstd-3 | zstd-4 |
| 4 | lzma2-7 | store | lzma2-6 | lzma2-6 |
| 5 | zstd-13 | store | zstd-3 | zstd-4 |
| 6 | zstd-1 | zstd-19 | zstd-3 | zstd-4 |
| 7 | store | lzma2-4 | store | store |
| 8 | zstd-4 | zstd-14 | zstd-3 | zstd-4 |
| 9 | lzma2-4 | lzma2-3 | lzma2-6 | lzma2-6 |
| 10 | store | store | store | store |
| 11 | lzma2-1 | zstd-19 | lzma2-6 | lzma2-6 |

### 2.3 这轮**不能**得出的结论

- 不能说明 A 或 B 的**实际压缩率**更好。
- 不能说明哪种方式的**搜索效率**更高。
- 不能推断 Store 在真实压缩时的**无收益回退次数**。
- 不能估计完整归档大小、搜索耗时或峰值内存。
- 不能根据变化块数判断谁更“随机”或谁的搜索空间更优；两者的表达能力、采样分布和编辑动作不同。

## 3. A 与 B 的设计取舍

| 维度 | A：随机块级计划 | B：Codec + Rank |
| --- | --- | --- |
| 输入语义 | 改 `value`，重新生成候选计划 | 改指定字段，按规则改变等级/Codec |
| 本轮影响范围 | 10/12 块变化，涉及多 Codec | 5/12 块变化，仅 Zstd 等级 |
| 用户可预测性 | 低 | 高 |
| 自动搜索多样性 | 潜力高，依赖具体采样规则 | 相对受限，但适合系统遍历 |
| 局部手动控制 | 当前无法精确点改单块 | 当前无法只改某个 Zstd 块 |
| 结果解释 | 较难追溯效果来源 | 较易做单因素对照 |
| 适合用途 | 自动探索候选方案 | 手动配置、基准、可解释优化 |
| 关键风险 | 变化范围大、搜索结果难解释 | 控制粒度过粗、难适配异质数据 |

### 3.1 A：适合自动搜索，但不等于可逐块编辑

**优点**

- 一个输入扰动可生成多个差异较大的块级压缩组合。
- 可能探索人工不容易想到的 Codec/等级搭配。
- 若生成算法严格定义且固定版本，同一输入可复现相同计划。

**缺点**

- 改动一个 `value`，可能影响许多无关块，用户难以控制影响范围。
- 找到更好的候选后，难以解释具体哪些变化带来了收益。
- 若候选间差异过大，局部改进难以复用，搜索可能低效。

**重要区分**：A 可以给不同块生成不同等级，但**不意味着用户能只编辑某一指定块**。当前更准确的描述是“整体重新采样块级计划”。

### 3.2 B：适合受控实验，但目前过于粗粒度

**优点**

- 字段含义明确，可预测 Zstd `rank` 调整会影响哪些块。
- 更容易开展单因素实验，研究某种 Codec 的等级是否值得提高。
- 可枚举的参数较少，便于建立基准和回归用例。

**缺点**

- 同一 Codec 的所有块统一受影响，无法按文件类型/数据特征区别优化。
- 对不同块使用不同等级的能力不足。
- 单个参数提升不一定能带来更小归档，尤其可能导致压缩时间明显增长。

**结论**：B 的可理解性优于 A，但这不等于 B 的压缩结果一定更优。

## 4. 控制粒度的四种方案

| 方案 | 作用范围 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **B1：全局 Codec 级** | 所有选定 Codec 的块 | 简单、参数少、便于基准对照 | 无法针对文件差异调整 | 必须保留为默认基线 |
| **B2：单文件级** | 某个文件中的指定 Codec/块 | 用户直观、适合混合目录 | 文件多时参数变多；小文件优化空间有限 | **下一轮优先** |
| **B3：指定块段级** | 某文件的一段块 | 局部精度高、便于热点调优 | UI、元数据、搜索复杂度增加 | 暂缓 |
| **B4：单块级** | 指定单个块 | 最精确、适合诊断 | 参数数目快速膨胀，不适合一般用户 | 仅研究/调试模式 |

### 4.1 推荐的分层策略

```text
归档全局默认策略（B1）
  ├─ 文件 A：继承全局设置
  ├─ 文件 B：覆盖为 Zstd-5（B2）
  └─ 文件 C：覆盖为 LZMA2-6（B2）
       └─ [后续可选] 指定块段局部覆盖（B3）
```

**优先级规则建议**：`块段覆盖 > 文件覆盖 > 全局默认`。这只是一种**编辑/生成计划的规则**，尚不是最终归档编码规定。

- 普通用户只用全局模式。
- 高级用户可指定部分文件的等级或 Codec。
- 自动搜索以后可将探索限制在某个文件或数据区域。
- 暂时避免每块都维护用户可编辑参数。

### 4.2 文件级是合理的折中，但也有边界

- 文件内容差异大时，文件级控制更接近用户思维模型。
- 单一大型文件内部可能存在异质数据，仅文件级策略不一定足够。
- 要注意同一文件可能被拆成多个块，文件标识与块编号映射必须稳定。
- 不应仅凭文件扩展名选择压缩策略；扩展名最多是启发式线索。

## 5. 字段语义与 Codec 扰动建议

建议区分以下四类动作：

| 字段/动作 | 期望语义 | 应影响的范围 |
| --- | --- | --- |
| `codec` | 改变目标作用域中的算法分配 | 仅选定作用域；不要意外影响其他文件 |
| `zstd_rank` | 改变 Zstd 压缩等级 | 仅选定作用域内的 Zstd 块 |
| `lzma2_rank` | 改变 LZMA2 压缩等级 | 仅选定作用域内的 LZMA2 块 |
| `value`（A 模式） | 对作用域内计划重新采样 | 明确告知将重新生成哪些块 |

建议在 UI 和实验日志中同时显示**编辑值与实际 Codec 参数**，例如：`zstd_rank: 2 → 3（level: 3 → 4）`，避免误认 rank 就是压缩等级。

**Codec 扰动范围建议**：

1. 默认采用**文件级**作为最小用户可控范围。
2. 允许全局批量修改，便于对照实验。
3. 将指定块段的 Codec 更改保留为高级实验功能。
4. 在每次变化后给出“预计影响文件数/块数”的预览；真实压缩后的 Store 回退另行统计，不混为一谈。

## 6. 下一轮实验计划（建议先做 B2）

### 6.1 目标

验证**全局默认 + 文件级覆盖**是否比现有 B 更符合用户理解和操作预期，同时检查该机制能否与 A 独立共存。

### 6.2 三个待比较方案

| 方案 | 操作例子 | 主要观察 |
| --- | --- | --- |
| **B1：全局修改** | 将所有 Zstd 块从 level 3 改成 level 4 | 用户能否预期影响范围 |
| **B2：文件级修改（首选）** | 只将“文件 B”内的 Zstd 块改为 level 4 | 未选择的文件是否保持不变 |
| **B3：块段修改（可选原型）** | 只将文件 B 的块 4–7 改为 level 4 | 作用域表达是否明显增加复杂度 |

> 注意：原第一轮只有 12 个假设块，没有文件归属。下一轮要评估 B2，必须先为测试块添加**稳定的文件归属**（例如 3 个假设文件，每个 4 块），否则无法真正验证“文件级”语义。

### 6.3 操作步骤

1. 保留第一轮 A/B 的结果作为对照，不改写其历史记录。
2. 为假设块补充 `file_id` 和 `block_id`，固定初始计划。
3. 先试 B1：只调 `zstd_rank`，记录预期与实际变化的块集合。
4. 再试 B2：仅对一个文件设置 `zstd_rank` 覆盖，确认其他文件无变化。
5. 让体验者解释每个字段的含义、预测影响范围，并记录误解点。
6. 有实际需求时再试 B3 的轻量原型，避免一次引入过多维度。
7. 根据语义评估结果决定是否调整 B 的控制粒度或引入新候选。

### 6.4 可用性提问

- 修改等级应该影响**同 Codec 的所有块**、**某个文件**，还是**选定块段**？
- `value`、`codec`、`rank` 的含义是否直观？
- 调整 `codec` 时，用户预计哪些块会变化？
- 变化范围是否可以在执行前正确预测？
- 是否需要“一键恢复全局默认”或“只重采样当前文件”？

### 6.5 功能验收标准

- [ ] 相同输入、策略版本和块清单生成相同拟议计划。
- [ ] B1 修改某 Codec 的 rank 时，其他 Codec 的块不受影响。
- [ ] B2 修改某文件时，其他文件的拟议计划不受影响。
- [ ] 文件级覆盖清除后，结果恢复为全局默认。
- [ ] 作用域越界或未知文件标识返回明确错误。
- [ ] 修改前后能够输出受影响块的差异列表。
- [ ] 文档始终将“拟议计划变化”与“实际压缩效果”区分开。

## 7. 后续压缩性能对照：如何保证公平

**功能性验证通过后**，再进入实际文件压缩实验。建议以相同数据集、机器环境、编译版本和搜索预算比较：

1. 固定压缩基线：`Store`、`Zstd-3`、`Zstd-6`、`LZMA2-6`。
2. **A**：在固定候选数量/时间预算下，使用随机块级计划搜索。
3. **B1**：在同等预算下，搜索全局等级组合。
4. **B2**：在同等预算下，搜索文件级覆盖组合。

### 7.1 必须记录的指标

| 指标 | 说明 |
| --- | --- |
| 完整归档大小 | 包含头部、索引、配置/种子元数据，不只统计压缩数据块 |
| 压缩耗时 | 单次候选的实际编码时间 |
| 搜索总耗时 | 包含所有尝试的候选，不只统计最终胜出者 |
| 解压耗时 | 衡量实际可用性 |
| 峰值内存 | 搜索及压缩过程中的峰值 |
| 候选总数 | 比较预算是否相等 |
| Store 回退 | 实际执行压缩后记录次数与原因 |
| 成功往返 | 解压输出与原始文件字节一致 |

### 7.2 公平性风险

- A 与 B 的搜索空间和采样分布不同，**相同候选数**只能作为一种预算对照，不能保证在数学意义上完全公平。
- 建议同时比较**固定总耗时预算**和**固定候选数预算**，避免某方案因单次压缩更慢而吃亏或占优。
- 多个数据类型、多次重复实验，报告中位数和波动情况。
- 比较的是**实际完整归档**，不能将“拟议计划更丰富”视为压缩收益。
- 搜索结果应该和不使用 Seed 搜索的固定参数方案比较，证明增加的复杂度是否值得。

## 8. 实现与格式层面的注意事项

- **固定映射定义**：随机数生成方式、种子解释、作用域、块顺序、Codec/等级映射和策略版本要明确，避免不同平台产生不同计划。
- **保留解码所需的信息**：提取端必须知道每个块实际使用的 Codec 和必要参数，不能依赖重新运行不确定的搜索过程。
- **分离编辑方案与归档编码**：B1/B2/B3 只是实验编辑体验，不必原样写入归档。
- **不要过早修改归档格式**：优先复用现有块级 Codec 信息，明确需求后才评估新增元数据是否值得。
- **区分计划与执行结果**：某块计划使用 Zstd 不等于最终一定使用 Zstd；实际编码可能因压缩无收益而回退 Store。
- **保存可追溯的实验记录**：测试数据版本、策略版本、输入参数、生成计划、运行环境与结果应相互关联。

## 9. 推荐执行顺序

### 当前轮：完成语义决策

- [ ] 收集用户对 A、B 字段含义的理解情况。
- [ ] 选择下一轮优先测试 B2（全局默认 + 文件级覆盖）。
- [ ] 为假设块加入文件归属，验证覆盖规则。
- [ ] 记录哪些局部调整需求 B2 无法满足。

### 下一轮：实现最小可用控制层

- [ ] 分离“生成计划”和“编辑/覆盖计划”的逻辑。
- [ ] 实现文件级覆盖、撤销覆盖和差异预览。
- [ ] 增加确定性、作用域隔离与边界条件测试。
- [ ] 决定是否确有必要增加 B3 或新候选 C。

### 再下一轮：开始真实压缩实验

- [ ] 选取真实文件数据集，运行固定压缩基线。
- [ ] 为 A、B1、B2 设置同一预算口径。
- [ ] 记录真实归档大小、搜索耗时、峰值内存和恢复正确性。
- [ ] 根据实验数据确定是否扩大策略搜索空间。

## 10. 最终建议

**保留 A，发展 B2，暂缓 B3 与候选 C。**

- **A** 提供自动搜索所需的候选多样性。
- **B1** 提供可解释、可重复的全局对照。
- **B2** 在复杂度和控制力之间取得合理平衡，是下一轮最值得试的方向。
- **B3/B4** 只有在实际发现文件级不足时再引入。

本轮应首先回答“用户是否理解和需要这种控制粒度”，**不要提前把任何候选设计确定为最终归档种子格式**。等语义稳定、测试通过且有真实压缩数据后，再决定是否把相应能力固化到长期协议中。
