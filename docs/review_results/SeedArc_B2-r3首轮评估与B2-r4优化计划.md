# SeedArc：B2-r3 真实压缩首轮评估与 B2-r4 优化计划

> **文档性质**：实验评估与下一轮开发建议  
> **数据来源**：B2-r3 首轮测试记录（用户提供）  
> **评估范围**：功能正确性、实际归档大小、Codec 分配现象、后续实验计划  
> **当前阶段**：B2-r3 功能首轮通过；进入 B2-r4 Codec 分配诊断与基线对照

## 1. 核心结论

**B2-r3 已证明真实压缩流程能够正确往返，但尚未证明 B 策略优于固定 Codec。当前最值得优先解决的是 Codec 分配效果，而不是扩大 Seed 搜索空间。**

- **正确性**：120 次 `compress → verify → extract` 全部逐字节还原；同一方案的多次运行生成相同 SHA256。
- **控制语义**：`b-cleared` 与 `b-global` 归档逐字节一致；实际 Codec / 配置与拟议计划按块核对；不划算的压缩块可回退到 Store。
- **文件级收益实例**：`source` 样本中 `b-file` 比 `b-global` 小 **667 B（约 6.98%）**；其余四种数据大小不变。
- **策略差距**：`text` 样本中 `b-global` 为 **66,538 B**，固定 `zstd3` 为 **944 B**；`mixed` 样本中 `b-global` 比 `zstd3` 大 **66,903 B（约 16.94%）**。
- **重要限制**：这只是自制样本和磁盘项目源码的首轮实验；未使用独立真实语料，未序列化 Seed / 覆盖字段，也未公平比较搜索预算。不能推出普遍性能、独创性或最终归档效率结论。

**建议：正式收尾 B2-r3 的功能验证，启动 B2-r4 的逐块诊断、简单 Codec 分配基线和更规范的性能评估；暂缓复杂搜索、块段控制、候选 C 与 GUI。**

## 2. 实验条件和解释边界

| 项目 | 当前情况 | 解读边界 |
| --- | --- | --- |
| 往返运行 | 共 120 次压缩、验证、解压，均逐字节还原 | 可作为本轮功能正确性证据 |
| 数据 | `binary`、`compressed`、`mixed`、`source`、`text` | 样本有限，不代表真实世界分布 |
| 方案 | `store`、`zstd3`、`zstd6`、`lzma6`、`b-base`、`b-global`、`b-file`、`b-cleared` | 固定算法与 B 的 Codec 分配不同 |
| 归档大小 | 包含头部、索引和数据 | **尚未包含 Seed / 文件覆盖元数据** |
| 重复次数 | 每组 3 次 | 样本量小，未控制 OS 缓存 |
| 时间 | 进程墙钟时间，包含启动、计划生成、自检和证据输出 | 不能单独视为压缩内核耗时 |
| 内存 | 压缩进程峰值工作集 | 不等价于跨平台可比的峰值常驻内存 |
| 复现性 | 同环境同组归档 SHA256 一致 | 尚未证明跨平台、跨编译器或跨版本一致 |
| 搜索 | 未执行受预算控制的 Seed 搜索 | 不得推断搜索效率或最优性 |

## 3. 归档大小总览

**单位：bytes，越小越好；比较的都是本轮完整归档文件。**

| 数据集 | Store | Zstd-3 | Zstd-6 | LZMA2-6 | B-base | B-global | B-file | B-cleared |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| binary | 393,646 | 393,646 | 393,646 | 393,646 | 393,646 | 393,646 | 393,646 | 393,646 |
| compressed | 393,834 | 393,834 | 393,834 | 393,834 | 393,834 | 393,834 | 393,834 | 393,834 |
| mixed | 788,968 | **394,959** | **394,959** | 395,403 | 461,862 | 461,862 | 461,862 | 461,862 |
| source | 35,426 | 9,503 | 8,835 | **8,304** | 9,559 | 9,560 | **8,893** | 9,560 |
| text | 393,644 | **944** | **944** | 1,379 | 66,538 | 66,538 | 66,538 | 66,538 |

> 加粗数值用于突出该数据集里的低值或与文件覆盖相关的结果，不代表全局性能排名。`source` 的 `b-file` 仍大于固定 `zstd6` 和 `lzma6`。本表尚未计算 Seed / 覆盖字段序列化后的净成本。

### 3.1 文件级覆盖：同 Codec 分配条件下的直接对照

这部分只比较 `b-global` 和 `b-file`，因此比拿 B 与固定算法比较更能隔离“文件级等级覆盖”的影响。

| 数据集 | B-global | B-file | 归档差值（B-file − B-global） | 拟议等级变化块 |
| --- | ---: | ---: | ---: | ---: |
| binary | 393,646 | 393,646 | 0 B | 3 |
| compressed | 393,834 | 393,834 | 0 B | 4 |
| mixed | 461,862 | 461,862 | 0 B | 3 |
| source | 9,560 | 8,893 | **−667 B（−6.98%）** | 1 |
| text | 66,538 | 66,538 | 0 B | 3 |

观察：

1. 修改拟议等级并不保证实际归档大小变化；某些块可能回退 Store，或者改变等级后输出仍同样长。
2. `source` 的 667 B 减少证明了文件级覆盖可以影响最终实际输出，但单个样本不能证明普遍收益。
3. `b-cleared` 与 `b-global` 完全一致，支持清除覆盖后继承当前全局配置的设计。
4. 未来若序列化文件覆盖元数据，必须用**净归档字节差**重新评价这 667 B 的效果。

## 4. 最值得研究的现象

### 4.1 Text：B 策略远落后于固定 Zstd

- `zstd3`：944 B
- `b-global`：66,538 B
- 差值：**+65,594 B**
- B 归档约为 Zstd-3 的 **70.5 倍**。

这说明在当前 `text` 样本和参数下，B 的组合没有取得好结果。但**仅凭归档总量无法确定根因**。

优先检查：

- 哪些块被分配到 Store、Zstd 或 LZMA2？是否存在大量可压缩文本被安排为 Store？
- 各块原始大小、候选压缩大小、最终写入大小分别是多少？
- 当前分块方式、Codec 分配和压缩参数中，究竟是哪一项造成主要差距？
- 固定 Zstd 和 B 使用的文件边界、块边界是否一致？若不一致，不能只归因于 Codec 选择。

### 4.2 Mixed：混用多算法并不天然优于固定算法

- `zstd3`：394,959 B
- `b-global`：461,862 B
- 差值：**+66,903 B，约 +16.94%**（相对 Zstd-3）

B 相较 Store 有改善，但没有超过固定 Zstd。首先应排除明显不合适的 Codec 选择；在没有逐块证据前，不必引入复杂“智能”调度器。

### 4.3 Source：覆盖有收益，仍未成为最佳方案

- `b-global`：9,560 B
- `b-file`：8,893 B
- `zstd6`：8,835 B
- `lzma6`：8,304 B

文件级覆盖相对 B-global 减少 **667 B（约 6.98%）**，但仍比固定 Zstd-6 大 **58 B**、比固定 LZMA2-6 大 **589 B**。

因此应保留 B2 文件级覆盖能力，同时改进其所依附的基础 Codec 分配。

### 4.4 Binary / Compressed：有效回退是好事，但不能说明策略优越

这些数据集里所有方案归档大小一致，符合难以继续压缩的数据经 Store 回退后的现象。应继续记录哪些块被回退、原因是什么、回退判定是否计入块级开销。

## 5. B2-r4 开发路线（推荐顺序）

### P0-A：建立逐块诊断报告

**目标：先解释差距，再改策略。**

每个真实块建议至少记录：

| 字段 | 含义 |
| --- | --- |
| `dataset_id` / `file_key` | 数据集与规范化相对文件路径 |
| `block_index` / `block_id` | 清单位置与稳定逻辑标识，不能混淆 |
| `raw_bytes` | 原始块长度 |
| `planned_codec` / `planned_level` | B 计划建议的编码器与等级 |
| `actual_codec` / `actual_level` | 最终归档索引中的编码器与等级 |
| `candidate_encoded_bytes` | 候选压缩块大小（若有尝试） |
| `stored_bytes` | 最终写入数据长度 |
| `fallback_to_store` | 是否回退 |
| `fallback_reason` | 回退原因，例如无空间收益或不满足策略限制 |
| `plan_source` | `base` / `global` / `file_override` |

导出机器可读 JSON/CSV，并给出按 Codec、文件、回退原因汇总的报表。优先分析 `text`、`mixed` 两组。

**验收条件**：能够从逐块数据解释总归档大小（包括头部、索引、数据与未来元数据），并清楚指出主要损失来源；不能仅凭猜测修改算法。

### P0-B：增加简单可解释的 Codec 分配基线

暂不定义新的 Seed 编码，比较以下三类策略：

| 策略 | 设计 | 用途 |
| --- | --- | --- |
| `B0-current` | 当前 B 块级 Codec 分配与等级规则 | 保留原样对照 |
| `B1-fixed-zstd3` | 对所有适用块使用 Zstd-3，无收益时回退 Store | 验证最简单统一策略 |
| `B2-file-codec` | 每个文件选择一个 Codec，随后允许文件级等级覆盖 | 测试文件级控制是否有实际价值 |

注意：每个方案使用相同原始输入、相同块边界、相同归档计量口径。若要比较 Codec 选择本身，必须控制分块策略；如果做端到端比较，则需明确全部差异。

**验收条件**：在 `text` 和 `mixed` 中，通过逐块数据证明差距来自何处；报告简单基线能否回收明显损失，而不是预设 B2 一定更优。

### P1：扩大测试集并规范测量

增加独立真实语料：源码树、日志、自然语言文本、PDF/图片/音视频等已压缩或难压缩文件，以及混合目录；覆盖小文件、单个大文件和大量小文件。

每次保存：

- 完整归档大小：头部 + 索引 + 数据 + **实际需要的策略元数据**。
- 压缩/解压墙钟时间；如果可行，另测压缩内核时间。
- 峰值内存，并标注指标定义和平台。
- 实际 Codec / 配置分布及 Store 回退数量。
- 操作系统、CPU、编译配置、库版本、数据集哈希及脚本版本。

使用更多重复、区分冷/热缓存或采用稳定的运行顺序，报告中位数与波动范围。没有充分统计证据时，不宣称微小耗时差异成立。

### P1：验证真实归档语义与兼容

- `compress → verify → extract` 严格逐字节还原。
- 重复执行时归档哈希稳定；如需跨系统保证，补做跨系统测试。
- `clear` 后归档与当前全局策略一致。
- 归档可在**不重新执行搜索**的情况下解码。
- 旧归档保持可读；未知策略版本或非法元数据明确报错。

### P2：再决定是否开始 Seed 搜索

只有在明确 Codec 分配基线和元数据成本后，再引入**相同压缩次数、时间和资源预算**下的 Seed 搜索对照；记录搜索时间、最终归档大小、成功率、波动与峰值内存。

不要把随机候选数量多等同于更强的压缩效果。

## 6. B2-r4 可执行验收清单

### 诊断与数据

- [ ] 增加逐块 JSON/CSV 报告，覆盖计划、实际输出、Store 回退和元数据。
- [ ] 明确 `block_index`、`block_id`、`file_key` 的语义。
- [ ] `text` 和 `mixed` 的归档差距能用数据复盘。
- [ ] 确认不同策略采用相同块边界，或清楚记录差异。

### 功能与兼容

- [ ] 保持既有 120 次往返场景或等价回归测试全部通过。
- [ ] 文件级覆盖只影响目标文件的目标 Codec 块。
- [ ] 清除覆盖后继承**当前全局策略**，而非最初默认值。
- [ ] Store 回退的实际 Codec 与归档索引相符。
- [ ] 解压无需重新执行 Seed 搜索。
- [ ] Seed / 覆盖字段真正落盘前，明确“实验归档”与“最终格式”的区别。

### 性能与研究

- [ ] 完成 `B0-current`、`B1-fixed-zstd3`、`B2-file-codec` 对照。
- [ ] 报告完整归档大小，不仅是压缩数据区大小。
- [ ] 报告元数据开销；若未实现序列化，明确标注缺项。
- [ ] 保存可复现命令、输入哈希、环境版本与原始测量文件。
- [ ] 对耗时差异保持审慎，不做超出样本的显著性声明。
- [ ] 在完成诊断前，不扩大 Seed 搜索或新增块段级控制。

## 7. 不建议现在做的事

1. **不立即开发更复杂的 Seed 搜索器**：当前 Codec 分配的明显差距还未解释。
2. **不把 source 的 667 B 当成普遍压缩优势**：当前仅是一个样本，不含策略元数据。
3. **不把固定算法与 B 的总体差异全部归因于文件覆盖**：两者 Codec 分配可能不同。
4. **不以毫秒级差距决定默认算法**：本轮仅 3 次重复，且包含进程启动与自检。
5. **不优先引入块段级控制、候选 C 或 GUI**：先保证基本策略有效、可解释、可复现。

## 9. 最终建议

> **B2-r3 可以完成首轮功能性收尾。B2-r4 最优先做逐块 Codec 分配诊断和简单基线比较，而不是搜索更多组合。**
>
> 先回答“为什么固定 Zstd 在 text / mixed 上大幅领先当前 B 策略”，再决定如何改进 B2 的策略空间，并用包含全部归档元数据的实际字节数验证收益。
